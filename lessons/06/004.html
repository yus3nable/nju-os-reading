第 06 课 · (入侵) 进程的地址空间；mmap, munmap, mprotect

探索真实进程：地址空间与 procfs

原片 00:19:53—00:29:03

我准备了 process address space explorer。prompt 从已经学过的概念出发：课堂上学习了 Linux 进程地址空间。

请做一个命令行工具，接收进程号，解析地址空间，说明每个部分；若是可执行区域，再反汇编第一个 kilobyte。进程号能定位运行程序，这是上节课的内容。为兼容课堂设备，还要求支持 x86-64、arm64，避免模型误以为我使用 x86。现在写一个 _start，在另一个终端运行 a.out。top 里能看到它占用 100% CPU，ps 则能查进程号。不必担心这些操作，也可以让 AI 完成。我是熟练工，上课时手动可能比模型生成 token 快；未来若有脑机接口，AI 也许更快。

到那时，手动熟练就没有意义了。告诉 AI 想运行 address-space 即可。先不看实现，工具已经把真实进程的整个地址空间打印出来。

这个二进制静态链接，从 0x400000 到 0x404000，有一段可读、可执行区域，标为 file mapping，对应 a.out。还能反汇编。这里先相信输出，若不相信，可以核对二进制，应该能看到对应文件内容。

此外，高地址、应该在栈下方，从……890000 到……898000，有 vvar、vdso。

第四段才是栈。看看地址，有 1e890000、C5 等，vvar、vdso 在下，stack 在上，都位于较高地址。

这比教科书模型多了一点。书上的说法没错，但 Linux 里，即使这个用 LD 直接链接的最小 a.out，只有一段只读可执行代码，连数据、只读数据都没有，地址空间也还有 vvar、vdso。Linux 用它们让一些系统调用无须陷入内核。以前我会带大家调试，比如 gettimeofday：频繁查询时间，每次进入内核会浪费很多时钟周期，系统就给每个进程地址空间放一小段代码。

这段代码实现系统调用，也能访问配套数据，vdso、vvar 分别承担代码和数据。比如 CPU 有精密计时器，加上操作系统维护的秒级时间、seconds、年月日秒，就能在不进内核时得到当前时间。也可以取得当前 CPU 编号。假设再给每个进程分一页、放进程号，getpid 就能直接读取，不必陷入内核。代码和数据映射用来加快调用，细节不要求掌握，先知道这种能力存在。再问 AI，工具怎样实现。

豆包开始读代码、思考。我备过课，所以可能比临时分析的模型快。工具接收 PID，解析 /proc 下该 PID 的 maps 文件，分析各内存区域，识别类型。

对可执行区域，使用 Capstone 反汇编 1 KB 内容。今天更需要知道操作系统能提供哪些能力。

prompt 没指定实现，只说学过地址空间，想从命令行 PID 解析它。先相信应该能做到，不必预先掌握解析方法。再花点时间看实现，就会知道 proc 下 PID 的 maps 描述了内存区域。可以找当前 Fish 进程的 maps，查看，甚至尝试编辑。procfs 在文件系统中保存进程相关信息，之前提过。

包括完整地址空间：每块从哪里开始、在哪里结束、访问权限，以及映射的文件。比如 libc、libm、libgcc 的部分内容就在进程地址空间，还有 vvar、vdso。

以前会让大家读 proc 手册，查 maps 每个字段的含义，再学怎样解析。

今天直接问 AI，也能完成；先知道事情可以做。
