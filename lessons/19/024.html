异步回调如何生成计算图

原片 01:08:00—01:12:04

就必须要等到所有代码都执行完，它才能执行下一个事件，当然你在这个事件里面，你可以比如说$.ajax，你可以去请求一个后端的某一个页面，然后你不知道它什么时候会回来，但是这个$.ajax 会立即返回，它会立即返回。然后剩下的部分仍然会继续执行。但是等到网页请求来了以后，它会创建一个新的事件。所以因为它并行在浏览器里。所以这个编程语言确实可以做这个设计，它禁止并行，没有任何的 blocking I/O，也就是说 JavaScript 里面没有你在操作系统课上的学生，那些 read 系统调用这些东西都是通通是不存在的，如果你想要比如说要请求一个网页。

你就要给它一个 callback，比如说在 success 的时候，success 的时候你要给它一个 callback，然后这个 callback 它本质上是一个函数，所以你要感谢 JavaScript 的函数式编程的设计，它把函数放进来。然后等到这个不知道什么时候。对吧，浏览器的实现自己会等等等等等等等等。当然在这个其中可能还有别的事件。比如说 click，对吧，你某一个东西 click 了也会有一个事件。然后当浏览器发现这个网页已经返回了的时候，它会再创建一个事件调用 function。

然后这个 function 又是运行到完成的，run to completion，它不能有任何的并行，所以每一个 JavaScript 的事件都是原子的，你永远不用担心它会和别人并行之中，也就避免了像 data race，这种 atomicity violation 这样的问题，这其实是描述了一个计算图。对吧，描述了计算图是说我要先做这件事，等到这件事情完成以后，我又创建一个新的节点。

当然这个时候它计算图很有意思，它有两种可能，一种是 success，一个是 fail，success 和 fail，然后在 success 的时候会执行一个函数，fail 的时候会执行另外一个另外的函数。但是实际上它只会执行一个分支，这个计算图，动态创建计算图的节点。这是JavaScript 的并发编程。然后就是这样的回调机制，callback 机制，事件完成以后。

课件中的嵌套回调片段；依赖 jQuery，省略号保留为课件中的未展开处理。

$.ajax({
  url: "/api/user",
  success: function(user) {
    $.ajax({
      url: `/api/user/${user.id}/friends`,
      success: function(friends) {
        $.ajax({url: `/api/friend/${friends[0].id}`, ...});
      },
      error: function(err) { ... }
    });
  }, ...
});

对吧，说数据返回以后，我再创建一个新的事件，调用我的函数，就带来了一个非常著名的词，叫 callback hell，叫回调地狱，为什么呢？因为如果你要做三件事，比如说第一，要登录，然后登录以后要 fetch 一个 friend，friend list，第三个你要 fetch 这个friend 的 feed。对吧，你的好友的动态，那你怎么办呢？因为它们三个之间是有依赖关系的，对吧，它们三个之间是有依赖关系的，那我就必须，这个计算图天生是这个所以我写的时候。我就得先请求登录。

然后登录会有成功和失败，对吧，失败我就处理，然后如果成功，我就要做这件事，然后成功完了以后，如果失败做这件事，成功做这件事，然后每一个都是一个函数，我就必须要把一个顺序的 ABC 的流程，一定要拆分成三个函数，而拆分成三个函数，我经常会，大家还经常会倾向于这样写。然后你就说 ajax 的时候，当我要做这件事的时候，我 success 的时候，我要创建一个函数。然后再调用下一个 API，再调用一个函数，也就是说，我如果要做一件事，我会创建无穷多级的缩进。你看我只是想要在 ajax。

做一个 ajax /api/user，成功以后调用这个 Friends，然后再调用这个结果是我每要做下一件事，我就会增加两级的缩进，很快这个代码就没有办法维护了，然后你就不知道，这个回调最后到底是什么样，然后你调试的时候会花去非常多的时间，这就因为本身一个顺序，非常经典的顺序的逻辑，一个顺序的计算图，硬生生的被拆分成了几个部分，它不能用我们编程语言里面的这个顺序结构，来描述先 A 再 B 再 C，它必须用这个方式，就带来了很大的编程上的困难。

然后我真的也是觉得很佩服地球上的人类，竟然可以在这么多年的时间里面忍着这样的很难用的 JS API。
