第 13 课 · 多处理器编程：从入门到放弃

共享内存并发编程的动机

原片 00:03:48—00:09:56

今天进入并发编程入门，标题叫“从入门到放弃”。这只是说法，并不要求大家放弃；课程会说明并发编程、多处理器并发编程会遇到什么困难，再用几次课讲怎样写出性能好、又不容易出错的并发程序。前面一直假设程序是一个状态机。

void http_server(int fd) {
  while (1) {
    buf = alloc_buf();
    nread = read(fd, buf, 1024);  // syscall
    handle_request(buf, nread);
  }
}

程序顺序执行：binary 二进制文件逐条执行指令，C 程序逐条执行语句。编译器把高级语言描述的状态机，转换成低级语言描述的状态机。

这种 sequential、顺序执行模型，写某些程序时会遇到明显麻烦。例如 HTTP 服务器：手机上的淘宝、抖音，从远端获取信息时都通过 HTTP 或 HTTPS。假设回到 2000 几年，想开一家叫淘宝的公司。

要上线信息系统，做一个网页，收到“请求淘宝首页”这样的请求后，把首页返回。按顺序执行模型，就会写出这样的 HTTP server。假想有个 fd，可以不断读取别人发来的请求，实际情况不完全如此。先分配 buffer，再从某处读取数据。

读完后处理请求。有时读数据要等很久，有时 handle_request 也耗时较长，例如需要读磁盘。程序可能既要读磁盘、读网络请求，又要计算。如果顺序执行，syscall 是 read，即使手上还有其他事，也不能直接去执行这个 read。

更准确地说，执行 read 后，没有数据就必须等，即使还有其他工作可做。说 CPU 被卡住、在空转并不准确，它只是没能处理那些本来可以处理的事，浪费了时间。这是引入共享内存并发编程的第一个动机：有没有办法同时做几件事，只要它们确实能同时进行？第二个动机是，现在系统都有多个处理器。

用 lscpu 看，我的树莓派也有四个 CPU，编号 0 到 3。大家的电脑可能有几十个处理器，机架服务器还可能有 128 或 256 核。无论哪种，硬件提供的都是共享内存模型，物理内存处在一个地址空间中，可以利用这个特性。

例如 CPU1 和 CPU2 都访问 1234 地址，CPU1 写进去，CPU2 过一会儿就能读到。怎样利用共享内存多处理器？前面举过例子：程序需要素数表，可以先算好，再 fork 100 份，得到 100 个进程，放到各个 CPU 上并行运行。可以做实验，看到 CPU 利用率达到 200%、300%，超过 100% 就说明这些进程确实同时工作。但收回 fork 子进程的结果很麻烦。例如把一个大区间分段，每段算出一个值，最后需要求和。

独立进程必须通过命名管道或匿名管道等机制，把数值送回父进程再相加，比较麻烦。能不能让多个进程共享内存？主进程中有一个 sum，fork 后的子进程直接 sum +=，把结果写进内存。父进程只需等待所有进程结束，再读取 sum。

这样既能求和，也能做更复杂的事情，例如同时处理多个网络请求。这就是引入共享内存并发的动机。
