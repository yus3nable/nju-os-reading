回顾：系统调用与应用生态

原片 00:00:00—00:03:48

上一节课我们讲了虚拟化的最后一次课，我们从最早的对吧从应用视角说操作系统就是一组 API，然后把这个 API 掰开来一点一点讲了很多的内容，然后但如果我总结一下的话你们应该能留下一个这样的概念，就是我们的整个计算机系统对吧，你看到的这样的一台计算机我的一台计算机或者你们手上的笔记本电脑，它都是从 CPU reset 开始的，它有一个最早的那个状态。

然后 CPU reset 开始以后程序就开始进行了，Firmware 会先把操作系统加载，然后加载以后操作系统会干一些事，比如说我上节课的时候讲了有一个叫 initramfs，它有一个文件系统的树，最早的操作系统就会把这个文件系统树加载到内存里，它变成一个文件系统加载里面的 init 程序。然后在这个之前其实我们也讲了到底什么是程序。对吧，execve 的系统调用，它会接收一个可执行文件，它是怎么被加载到内存上到加载到 CPU 上执行的，然后等到这个 init 程序再加载了真正的文件系统，你们磁盘上的文件系统的时候，再会执行一个系统调用，切换到一个新的 init 程序，就是我们在 pstree 里面看到的第一个进程，这个 systemd 就被创建出来了，然后它再用各种各样的系统调用，去创建你们看到的应用程序的世界，就是在屏幕上面看到的这一切。然后在这一切系统调用，从操作系统来看它就是一个 system call API。但是如果你想要构建这个应用生态的话，它还有一层一层的洋葱。对吧，我有 libc，一个有ISO 标准、可以移植的基座。

你写 C 程序就可以移植到很容易移植到其他的平台，甚至是那种微小的控制器，然后在 libc 之上还有很多的库函数，你们想要在终端上显示字符，想要读取字符对吧，想要访问屏幕，想要创建图形界面的，都是有相应的底层的库函数。然后在这个底层的库函数上面，又长出了很多应用程序的生态。对吧，JavaScript 的生态，Python 的生态，比如你们打开一个 Visual Studio Code，那它是Electron 框架里面，它是一个 JavaScript 的程序在运行。

但它会一路依赖到最底下的 libc，底层的库函数，然后这样的一个操作系统的设计对吧，它是一个 OS 的 API，或者我们叫它系统调用，它往上是整个应用程序的生态，也是越长越大的，它往下其实可以有兼容多个体系结构，这个学期的课程从 x86，因为以前我一般都是在讲台上的这台电脑上面，直接展示的，然后我今天我把它换成了我的一台树莓派，那它们两个就是不同的架构。对吧，一个是 x86，一个是 ARM64，还可以有 RISC-V 等等。但是不同的体系结构上，其实它跑的是同一个操作系统的 API。

你们也知道 Linux 内核是用 C 实现的，现在开始加入 Rust 的一部分，它用 C 实现的，C 本身也是具有一定的可移植性，它freestanding 的环境，你可以在 x86 上，也可以在 ARM64 上运行，那操作系统的这个 api，就是一个很好的中间层。对吧，我的底下的硬件，不需要知道上面的应用程序是干什么，它只要机械的执行指令就行了，然而上面的应用程序，甚至都不需要知道，它运行的是什么样的 CPU，因为我们的代码是 C 代码，都是可移植的，如果你写可移植的代码的话。

那它在 x86、ARM 上都可以正确的运行，而像 Linux 内核里面，体系结构相关的代码，是它其中相对比较少的一部分，总会有一些但是相对比较少，这样我们就构建了这个计算机系统的世界，所以你看到一个很好的抽象，你们回头再去回顾一下。比如说在复习的时候，回顾一下这个课程的内容，你会想到这个应用程序的世界，是怎么样一点一点被构造出来的，好。
