第 13 课 · 多处理器编程：从入门到放弃

优化级别、compiler barrier 与 volatile

原片 01:07:11—01:12:47

回到求和。原先得不到正确结果，这次分别用 -O1、-O2 编译两个版本。结果变了：sum 等于 N，运行很多次都一样。

用 -O2，sum 又看起来正确了。同一份代码，优化选项不同，行为差别很大，为什么？让 AI 读汇编。它处理时，先介绍控制编译器优化的两种办法。

while (!flag) {
  asm volatile ("" ::: "memory");
}

int volatile flag;
while (!flag);

这些方法在操作系统课上不推荐，也不要求掌握。不要随意依赖 shared memory 的行为。后面会讲，两个线程同时访问同一个内存地址，叫 race condition、数据竞争，在 C、C++ 中属于危险的 undefined behavior、未定义行为。确信代码会编译成什么二进制时，有时仍能利用这些特性。例如插入不可优化的 compiler barrier。

前面 SimpleC 中的 x++ 可以优化，遇到 syscall 就有了 barrier，不能跨过它优化。compiler barrier 也一样。这个 asm、clobber memory 是空指令，长度为零，却告诉编译器它可能修改任意内存，让编译器无法在内存意义上优化。

优化不能越过这个边界，前后操作不能合并。这是第一种办法，编译器 barrier。另一种是将变量标记为 volatile，禁止通过合并把访问优化掉。访问 memory-mapped register 时通常也需要 volatile。例如从设备读一个字节，丢掉，再读下一字节。

如果指针指向内存映射的输入输出端口，先读一个字节丢弃，再读一个放入所需变量，缺少 volatile 时，编译器会合并这两次 dereference、内存读取，但这里不能合并。volatile 可以指定保留这些访问。不过仍要提醒，不要随意依赖共享内存的行为，它很复杂，特别是不熟悉编译器时，很难知道它会怎样处理。

以前会取出汇编给大家讲，现在看 AI 的解释应该没有问题。-O1 做了循环优化：先 load sum 到寄存器，在循环中不断给寄存器加一，最后 store。也就是把 load 提到循环前，store 放到循环后。

循环耗时长，load、store 之间的时间窗口就很大。-O1 下，两个线程都先 load sum，各自运行很久，再 store，和山寨支付宝一样，都先读到余额足够，随后执行、相互覆盖。无论谁覆盖谁，最后只剩一份 N。-O2 则把整个循环优化掉，直接 load sum、加等于 N、store，只花几纳秒或几十纳秒。线程创建和操作系统调度有先后，两段代码碰到一起的概率很低，就得到看似正确的结果。这才危险。

测试 100 万次都正确，开心交付后，某天客户那里却挂掉，还不知道原因。并发、不确定性与各种机制交织，会产生很难理解的行为。编译器已经打破程序按 SimpleC 语句 12345 顺序执行的假设，后面还有更多麻烦。
