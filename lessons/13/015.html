第 13 课 · 多处理器编程：从入门到放弃

处理器也是编译器

原片 01:12:47—01:17:34

刚才的 sum 程序中，GCC 将点 c 编译为点 s 时，已经做过一轮改写：内联函数，把函数体粘贴到调用位置；参数是常数，就替换为常数；再等价改写，提高效率，删除死代码。但还没结束。大家写 NEMU，知道一种 CPU 模型。

有 register、memory，经过 fetch、decode、exec，就到下一个状态，是 deterministic 的。但这样的 CPU 太慢。前面连续 x++ 可以合并为 x += 3，CPU 也像一个编译器。例如 move，先令 rax 等于 1。

再令 rbx 等于 2，即 rax = 1 和 rbx = 2。这两条不必顺序执行，可以调换。在顺序程序中，最终结果一样，处理器只需在中断、IO 时向外提供正确数据，类似编译器保证 system call 收到正确数据。处理器还可以在一个时钟周期执行这两条指令，同时 decode 多条。cache line 有 64 字节，取指时已取到这片内容，为什么不顺便译码其他指令？所以 CPU 内部远比 memory、register 的简化模型复杂。

这个 internal 能 decode instruction1、instruction2、instruction3，动态分析数据流，知道指令 2 依赖指令 1、指令 3 依赖指令 2，把编译器的工作在电路上再做一遍。于是一个周期能执行两条、4 条，甚至 8 条指令。load、store 因 cache miss 变慢时，也可以继续取后面指令。分支预测器会猜后续执行路径，先执行不依赖当前结果的指令。两层编译器都可能调换指令顺序，共享内存模型中每次选一个线程执行一条指令的设想，在实际系统里无法完整描述这些行为。系统为性能付出了代价。

它已经超出简单 shared memory 的模型，没人知道 memory 到底是什么。看起来每个线程都有自己的 memory 副本，load、store 操作自己的副本，副本之间怎样交互由硬件厂商实现，软件并不知道。当然也有约束，至少要保证 eventual consistency：所有 CPU 都停止 load、store 后，各自的 memory 最终逐渐一致；或者执行某条特殊指令，要求某段内存一致，分布的内存再相互通信、达成一致。这会带来什么问题？

int x = 0, y = 0;

void T_1() {
  x = 1;      // Store(x);
  int t = y;  // Load(y);
}

void T_2() {
  y = 1;      // Store(y);
  int t = x;  // Load(x)
}
