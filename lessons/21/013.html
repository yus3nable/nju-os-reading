第 21 课 · 一个 Token 的旅程

实时、半离线和离线数据处理

原片 00:26:52—00:30:31

这样的时代背景，产生了数据中心里的海量分布式数据处理。回到请求到达 api.deepseek.com 的过程。大语言模型流行以前，很多应用就已经在做相近的事，包括实时小数据的增删改查，也就是 CRUD。现在 CRUD 工程师已经被 AI 彻底取代了。这些小数据处理包括淘宝下订单、发帖子并写入数据库、从数据库取出聊天记录，也包括用户鉴权、判断 API key 是否合法、记录弹幕在几分几秒显示，以及计算这次 API call 收多少钱。

计费还要看缓存是否命中，应该用哪种 pricing，是峰还是谷。这些都属于较小的数据处理。以 DeepSeek 为例，它本身还有一个完整的功能网页 DeepSeek.com，刚才看到，它的后台与 API 不太一样。网页保存完整聊天记录，今天聊完，明天还可以打开昨天的记录继续追问。

这些都是传统数据中心海量分布式数据处理的工作。除了增删改查，作为 shared application，即便只处理一家公司自己的业务，也需要半离线数据处理，比如周期性记账。前面讲过，并发数据结构很难设计，连一个 scalable 的 sum 加加都很困难。记账可能使用分布式数据结构，会存在延迟。

要反映到精确的日账单、月账单，真正计费时，可能还需要半离线处理。还有定期备份、数据看板，以及规模很大的离线处理，比如每轮要花几百万美元的神经网络训练、内容索引。分布式数据处理的诞生，就是因为 Google 当时已经能用分布式机器存下整个互联网，但存完还要运行程序，生成搜索索引。现在我发现自己用搜索越来越少了。

因为大语言模型也能搜索，可以直接给它更难的问题，让它帮忙解决。可能十年以前，掌握 Google 搜索能力就能成为超级个体，与别人有十倍的生产力差距；今天会用 Agentic AI，就有一百倍、一千倍的差距。Google、Meta、豆包、千问、DeepSeek，这些应用无一例外，都依赖数据中心。
