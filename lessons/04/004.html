第 04 课 · (Aside) LLM, Agents 和 Scaling Law

抽象设计与现场构建操作系统

原片 00:58:29—01:22:22

接下来讲技术部分：怎样用好大模型。刚才介绍过，它根据 context 输出下一个 token，一个重要机制是 self-attention、注意力。这也像人。看难数学题的题解时，经常会发现解题者注意到了自己没想到的地方。

如何用好大模型：attention engineering 与问题分解

一旦注意到那个条件，题就解出来了，推导都对，但自己没想到。人的注意力可以训练，能从问题结构、词语之间找到联系；困难时也要像 reasoning model 一样，推理、尝试。提示词工程，在一定程度上就是 attention engineering：让模型看见希望它注意的信息，引导正确行为。比如只让 AI 写小说，结果可能不满意；只说“写入党申请书”，所有 attention 就放在这几个字上。它作为读过大量书的模型，会写出中庸、平庸、平均的申请书，形式很好，却未必符合需要。此时要补个性信息，比如自己是什么人、希望怎样写，提供足够上下文，让 self attention 能关注这些内容。

今天仍需要适时帮助 AI 分解问题。虽然 Claude Code 的 Plan Mode 会规划，一会儿的例子也有计划，但分解能力仍是 AI 时代很需要的能力。一个 crazy 想法，直接交给 AI，可能只得到平庸答案；以独特视角分解，就可能得到可用、甚至达到产品要求的成果。这涉及构建合适的抽象。

软件工程中的复杂性分解

操作系统课就在讲这种抽象。比如 syscall 之上，有巨大的应用生态：原神、Steam 都在操作系统上运行，SteamOS 使用 Linux。它和课堂树莓派上的 Linux 一样，用 man 2 syscall 能查到这些接口，它们支撑每天在 Steam Deck、Steam 机器上使用的应用。

man 2 syscall
man 2 syscalls

syscall 下面可能是千万行代码的复杂、高性能操作系统，上面的生态也很大，中间接口却相对很小，实际需要用的更少。直接让模型实现操作系统，可能写着写着就失败。但仔细设计创新的抽象层，比如设想未来的 syscall 应该换一套形式，再带着 AI 实现，就可能做出下一代热门操作系统。

指令集也是经典抽象。底下是硬件，上面是整个 OS application、整个计算机世界。RISC、RISC-V，RISC 的 reduced，就是精简指令集。这是生态中的中间接口，在单个应用里也能用抽象分解复杂性。大家写程序，会把功能封装成函数。

比如想在校园提供外卖、送洗衣服等服务，挣点钱，首先要注册用户，写 register_user 函数，需要时直接调用。多个地方通过 function call 连接同一个 function 实现，也会增加维护负担。假设之前性别参数只有男、女，后来因多元性别的投诉需要调整，接口变化就可能 break 调用方，工程师要处理跨模块依赖。register_user 可以做成函数，但系统与 subsystem 之间的关系不可避免，需要仔细设计交互。让 AI 给一个平均方案，未必最适合自己的系统。

上课用的 Vibe-learning，采用了比较反常规的设计。如果让大家或 AI 直接实现课堂系统，很可能把内容做成内存数据结构，再搭前端网页，有左右边栏，点击按钮就传事件到另一处。但这样导出 lecture notes 会有些麻烦。

我把子系统之间的接口设成文件系统，也和教操作系统、展示 UNIX philosophy 有关。所有播放过的页面都保存在这里。

比如屏幕上“世界变了”这页，就对应这个页面。常规做法可以用函数调用，把 html 直接传给另一子系统；我选择把它存成文件。

这样前后端就解耦了。播放器按 VS Code，可以在另一处打开 VS Code；切换 slide 时，则只写文件，不必关心谁来使用。网页可以显示，其他程序也可以显示。接口就是一个目录，以及一份日志，记录 3 点 26 分切换到这个 slide show。

另一系统只需读取约定格式的日志，这个格式就是与其他 subsystem 之间的 protocol。遵守约定，就能正确显示幻灯片。我实际写的只有几行，播放器是 300 行 AI-generated 屎山代码，但复杂性被隔离了：它独立运行，不影响其他系统部分，只解析日志，再在终端打印。

这样按协议分离几个 subsystem，就能让 AI 分别实现，甚至多个 AI agent 并行实现工具。若是 monolithic 库，全部依靠函数互相调用，并行 agent 就有风险，两个 agent 同时改同一文件，还要处理冲突。架构设计好，更容易维护。

我觉得现在 AI 还不太擅长这件事。但既然算力就是智能，它也应该能做到；到那一天，人类的末日可能就到了。现在还剩一些时间，准备接受翻车：完全交给 AI，Vibe Code 一个 OS kernel，测试国产模型能力。

Hacking Day：现场尝试构建最小 OS kernel

先说一句话，让 GPT-5.4 生成分解任务。我暂时觉得，国产模型做好问题分解可能还需要时间。GPT-5.4 给了一份看起来不错的任务：实现 RISC-V 操作系统内核。注意，我假装完全不懂 RISC-V、操作系统，聊天时没有使用自己的相关 knowledge，内容都是它写的，包括启动内核、初始化 minimal run-time environment。

还要创建多个内核线程、实现切换、展示调度。它写了 working style，加入 think step by step。因为我说要在课堂演示，它要求每一步都解释清楚，并说明怎样测试。

一些要求来自我的自然语言 prompt，比如 keep the design tiny and explicit。我只说实现操作系统，没有给细节，它已经开始分解问题。

还列了 what to avoid，用“除非我问了”限制范围。Structure your help around 后面包括 a short plan、the next code change、a minimal test or demo，还有 preferred mindset。

接下来就可以准备下课了，随时接受翻车，也准备快进。看它思考，self-attention 仍在工作：先创建必要文件结构，列 plan list，开始调用豆包 Seed 2.0 Code。先测试模型，有问题还能处理。它准备写 Makefile、编译脚本和 linker 链接脚本，创建 src、include 目录。我用 yes 允许写文件。如果自己写操作系统，也会这样做。

这就是 AI 让人感到压力的地方。我有些操作系统、编程知识，也未必能做得更好。代码工整，像回到计算机系统基础课。它写了较长的 kernel.h、thread.h，知道 best practice，先写一些注释。

计算机系统基础框架也在做类似的事。有同学用过 AbstractMachine 版本吗？有。和现在 AI 相比，人类仍有一点设计优势。我们的 Makefile 有 make html，大家发现过这个小设计吗？我利用井号注释的特性。

把 Makefile 组织成分层结构，也能当文档读。AI 现在好像还不太会这种做法。它要实现两个线程，一个是 thread1。

另一个是 thread2。接着创建线程管理和上下文切换代码，还写了汇编。只要事情在人类世界已经 well known，有人做过，模型就能凭记忆里的操作系统知识来写，也可以参考找到的文档。

直接让 AI 写系统，一般不会设计成我这样，但提供技术文档，说明用文件系统解耦、整体怎样组织，self attention 就能理解意图，完成实现。看，它开始编译，和大家做计算机系统基础实验一样，改完 make，再发现错误。

错误是 cast a pointer from integer of different size，它思考后准备修复。以前我写框架也会遇到这类问题，只能查互联网、手册，自己充当索引。大家以后做产品，需要观察 Agentic AI 怎样工作，也要有适时介入流程的能力。

-#define UART_BASE 0x10000000
+#define UART_BASE ((uintptr_t)0x10000000)

-LDFLAGS := -T $(SRC_DIR)/linker.ld -nostdlib -nostartfiles
+LDFLAGS := -T $(SRC_DIR)/linker.ld -nostdlib

如果自己来，我不会那么自信地一下写完全部代码。它出了错，但不致命，我甚至认为它做对了。现在它报告成功：已经构建最小 RISC-V 操作系统，能在 QEMU 运行，成功切换两个线程。豆包还是可以的，它结束了。

模型给出的测试命令：

make clean && make all && timeout 5s make run

结果有点出乎预期。再运行 make 检查：50、51、52、53、56、57、58、59。我知道它打印 16 进制，应该没问题，确实意外。

这个过程有没有哪里不太对？如果由人构建，人类与 AI 的做法有什么差异？我的感受仍是 attention is all you need。可以看看上下文。

当前已经用了 26% 上下文。刚才模型基本线性执行：收到 do it，就开始做，attention 都集中在过去已经做过的事情上。比如运行 make，得到 error message，就尝试修复。它很倾向于按要求直接执行。

它会读取 CLAUDE.md，严格按指令写。但如果由我给大家构建操作系统，会先做抽象、搭基础设施，逐步实现，避免全部写完后再逐项修。也许模型相信自己的编程能力，我没有那么自信。我至少会要求 implementing a skill for running，打印 trace、log，准备辅助实现的工具。刚才中断它，也是因为 context 已经很长，它还是习惯不断 make all、make run。

它很像人，却暂时缺少一些处理习惯，未来也许会有。看到满屏输出，人会及时停止；它却要等 default timeout，比如一分钟，到那时已经输出太多日志。

日志都会进入上下文参与推理，有些浪费。不阻止，它过会儿也会想到加 timeout，但长日志已经留下。compact 能压缩，不过先做合适的 abstraction、test framework，即使只有一两行，也能改善：每次 build 后直接运行测试，获取反馈。

看看让它写 skill 会怎样，先让它继续生成。操作系统课也会展示许多正面例子。

下周开始，lab 里就会有 unit test framework。现在两周之内还来得及退课；继续上的同学会用到它。框架大部分 vibe coding，少部分由我们设计。未来希望整个课程 open source，有这些测试以后，就不必一直由我们维护。

作为做 system 的人，我会明确告诉 AI，需要这样的工具。不仅有 unit test，还应有验证工具，比如计算机系统实验引入的 differential testing，都是重要的人类经验。

这些经验体现在合适的 abstraction 里，也是这门课希望大家学到的内容。
