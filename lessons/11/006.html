Linux 加载器与初始栈

原片 00:28:58—00:35:20

需要记住这个概念：a.out 这样的二进制文件，是对进程初始状态的描述。进程需要内存，也需要操作系统准备的 initial process stack。a.out 描述代码、数据分别加载到哪里、采用什么权限。除了代码、数据和 BSS，也可以放入其他想加载的内容。加载通过 execve 系统调用实现。

execve 的 pathname 参数对应这个 a.out。我们也可以直接查看实现。我准备了 Linux 源码，还没有编译，共有 9 万个文件，可以直接向 Agent 提问。

老师说 binfmt_elf.c 里有加载器代码。面对 9 万个文件，又不熟悉这个 codebase，点开可能马上就被劝退。但只需要一个 prompt，Agent 就开始读了。这个文件共 2185 行，它每次读 400 行，控制大语言模型的处理能力。花一些 tokens，就能了解 ELF 文件的所有细节。

主要流程是检验数据结构的合法性，加载 program headers，映射 load 段，再创建 ELF tables。create_elf_tables 会在栈上布置 argc、argv、envp 和 auxv。

这就是前面讲的 initial process stack，还可以接着追问。我觉得在这个时代，需要对新概念保持敏感，第一次遇到时确保自己理解，再由它推出更多内容。这里看到 initial process stack 中有一个 sp。

还有 argc、argv、env，以及 auxv，即 Auxiliary Vector。auxv 对大家一直有些神秘，我上课也只是一带而过。还记得调 vDSO 时，讲过它是不进入内核的系统调用：操作系统内核在进程地址空间中映射一段内存，可以直接跳过去执行。vDSO 的地址就在 auxv 里，此外还有其他信息，Agent 都列出来了。

它还告诉你，ARCH_DLINFO 宏会插入架构特定的 auxv，例如 AT_SYSINFO_EHDR。这就是 vDSO 的入口地址。Agent 会到其他文件中找 AT_SYSINFO_EHDR，继续读 linux 内核。需要留意，这是九万个文件，也就是 9 万个文件。当然，这个大模型已有一些 linux 内核知识，算是训练得比较好。它找到了 x86 上 ARCH_DLINFO 宏的定义，以及当前进程 mm 的 context.vdso，代码都在这里，还会解释 vDSO 是什么。

它也会指出是哪一行代码设置的。这是一年以前还做不到的事。一年以前，Coding Agent 还经常不听指令，我得自己打开网页，给大家解释代码。

Agent 展示的 ARCH_DLINFO 片段：

#define ARCH_DLINFO do {                                      \
    if (vdso64_enabled)                                       \
        NEW_AUX_ENT(AT_SYSINFO_EHDR,                           \
            (unsigned long)current->mm->context.vdso);        \
    NEW_AUX_ENT(AT_MINSIGSTKSZ, get_sigframe_size());            \
} while (0)

我突然觉得，这么多年的努力好像全都没有了。在 Agent 面前，只要问出问题，它就能帮忙找到代码，不需要事先熟悉 codebase。我像大家这么大时，大概从 Linux 2.6.30 左右开始读内核代码，对这些内容还算熟悉。今天看，它比我知道得多、解释得好，还能提供情绪价值。看看刚才用了多少上下文。

实际用了 63K 上下文。假如模型有 100 万或 200 万上下文，能力会很强。Linux 内核这样的项目被人类管理得很好，模型只要加载相关代码，就能对着代码做 in-context learning，一边读，一边根据自己的判断得出正确结论。在 Linux 内核中修改代码，也能做得又快又好。

我觉得这也是件可怕的事。回到加载器，它把数据结构搬到内存中，提供 initial state，包括 argc、argv、envp、辅助向量的完整布局，以及一段段内存映射。
