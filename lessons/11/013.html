第 11 课 · 链接和加载

PLT、GOT 与位置无关代码

原片 01:22:17—01:29:20

还剩一点时间。

简单提一下动态链接怎样实现。这部分不要求掌握，了解一下即可。我用大家熟悉的 x86 指令集来讲。main 可以调用 foo，也可以调用 printf。foo 可能就在 a.out 中，例如 main.c 和 foo.c 链接成同一个二进制文件；printf 采用动态链接，链接时还不知道地址。编译器对两者一视同仁，给 main 生成的都是 call 指令。刚才说 32 位不准确，x86 无论 32 位还是 64 位，call 都有立即数，可以是四个字节、两个字节或一个字节。这里编译器会生成 call 00 00 00 00。

同时给出一个 PC relative32 的 relocation。无论 call foo 还是 call printf，都会生成 call 00 00 00 00 这样的指令序列。把 main.o 和 foo.o 链接成 a.out 时，就必须为这些 relocation 填上正确数字。

foo 已经在 a.out 中，位置已知，这个好办。

可以算出具体数字，使跳转到达 foo。printf 则不行，它可能在地址空间任意位置。64 位地址空间现在一般有 48 位有效，四个字节的跳转范围未必能到达 printf，何况此时还不知道 printf 的地址。怎样实现动态链接？编译器会生成一小段代码。

这段代码叫 printf@PLT，放在 a.out 中。call printf 会转为调用 printf@PLT，PLT 即 procedure linkage table。先跳到这个已知位置，再由 printf@PLT 查找 printf 的实际地址，这张表叫 Global Offset Table。

查到地址后，再 call printf。编译器用了一个聪明的 trick：无论调用同一链接单元、a.out 中的 foo，还是调用动态链接库，都生成相对跳转。ARM 使用 26 位立即数，范围为 128 兆；x86 使用 32 位立即数，可以寻址 2 兆——2G 的空间。这些地址都必须在链接出 a.out 时确定。

动态链接的函数在静态阶段无法确定地址，就在代码里增加 printf@PLT，因此能在 a.out 中看到 PLT。PLT 会查表，现在一般已经直接加载好这张表，两条指令就能查完。

接着用 call 指令跳过去，这就是动态链接的基本实现方法。不过，PLT 解决的是二级跳转，尚未解决数据访问。写一小段 x 等于 1 的代码：这个 x 究竟在另一个动态链接库中，还是在当前二进制文件中？此时还不知道。

a.c：

extern int x;

void foo() {
    x = 1;
}

使用不同编译选项，结果会不同。例如用 -fno-pic -c a.c，再加 -O2。no PIC 表示不生成位置无关代码，也就是知道它在这个位置。编译后看到，先算出 x 的地址，再直接用一条 store 指令写入。

如果改用 -fPIC，生成位置无关代码，就会增加一次间接访问：从 global offset table 中查出地址，再把值写进去，令 x 等于 1。

编译与反汇编命令：

gcc -fno-pic -c a.c -O2 && objdump -d a.o
gcc -fpic -c a.c -O2 && objdump -d a.o

这是当前系统设计中很无奈的一点。用 -fPIC 编译时，对所有 extern 外部数据，例如 extern int x，无论它是否在同一个库中、能否用短地址访问，编译器都会增加一层间接访问，带来一定性能损耗。需要一些 hack，告诉编译器怎样控制这个行为。

这部分比较复杂。
