验证共享库在内存中共享

原片 00:49:00—00:57:20

这是真的吗？老师上课提到这个结论，就可以让 AI 写程序验证。我准备了一个由 bloat 和 sample 两部分组成的程序。bloat 中有一段内联汇编，生成 10 兆的 nop，先编译一下。

bloat.c：

__attribute__((noinline, used))
void bloat() {
    asm volatile(
        ".rept 10485760 \n\t"
        "nop\n\t"
        ".endr\n\t"
    );
}

编译花的时间比预期长一些。看一下，这是一个 4 兆的……ARM 上一个 nop 是四个字节；x86 上一个 NOP 是 0x90，占一个字节。所以这里生成的文件有 40 兆大，libbloat.so 中有 40 兆的 nop 指令序列。sample.c 会先调用 dlopen。

这部分是 vibe coding 的：我要求加载 libbloat.so，再调用 bloat 函数，也就是刚才那段内联汇编。

sample.c 中的 main 片段：

int main() {
    // This is vibe-coded. Asked AI to load dynamic library.
    void *handle = dlopen("./libbloat.so", RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "dlopen error: %s\n", dlerror());
        _exit(1);
    }
    void (*bloat)() = (void (*)())dlsym(handle, "bloat");
    if (!bloat) {
        fprintf(stderr, "dlsym error: %s\n", dlerror());
        _exit(1);
    }

    bloat();
    printf("Executed bloat() at %p\n", (void*)bloat);
    sleep(1000);
}

执行完 40 兆的 nop 后，用 %p 打印执行的 bloat 地址。现在可以运行 sample，也可以放到后台。多运行几次，后台就有不少 sample，会看到它们打印的地址位于各自地址空间的不同位置。

这是地址空间随机化的结果。调用 mmap 时，如果没有要求必须映射到指定位置，它就会根据地址空间布局找一个有一定随机性的地址。虽然都在 7FF 这个范围内，bloat 的映射位置仍然不同。整个操作系统中，bloat 是否只有一份内存副本？先把这些进程都杀掉。一个 libbloat.so 有四十兆，创建 1000 个进程看看。直接开一个 agent，要求 run 1000 个 sample in background，连写脚本都不用单独要求。它写好脚本，并报告已在后台启动 sample 1000 次，看看有没有。

确实有 1000 个 sample，系统也没卡死。用 free 查看，机器有 8G 内存，现在用了 4.7G，这很正常：还开着 VS Code、Claude Code 和其他前台程序，其中一些占用来自 buffer、buffer cache。一千个进程如果各有一份，会占多少内存？

每个进程各占 40 兆，合计就要约 40G 内存。如果每个后台 sample 都有独立拷贝，系统早就出问题了，但现在仍然流畅。这就证明，sample 使用的这段很长的二进制库函数，在整个系统中，磁盘和内存都只有一个副本。还可以继续问。记得 /proc 下 pid 的 fd 吗？管道可视化中多次用它查看进程打开的所有文件。也可以看 mmap 的情况。例如查看 sample 进程 20542 在 /proc 下打开的文件描述符，再看它的 maps。

确实是 sample，也确实映射了 libbloat.so。那有没有命令行工具，能查看 sample 或 libbloat 到底被多少进程引用、libbloat 在系统中被打开了多少次？问 AI，会告诉你可以用 list open files。

它遍历 procfs，找到系统上所有打开的文件。用 lsof 查看 libbloat.so，就会列出所有打开它的进程，一共有 1001 个。多出的一个应该是 lsof 进程，我猜它可能也会打开一下 libbloat.so。

接着问：lsof 怎样找到 libbloat.so 的所有引用？用 strace，再 grep open，就能看到实现方式。它像 pstree 实验一样遍历 procfs，查看所有进程打开的文件，还会打开 maps，相当于把整个 procfs 扫一遍。

这样就找到了多少进程引用 libbloat.so。每个实验背后都有设计。pstree 看起来只是遍历 procfs，一句话就能让 AI vibe code；但如果自己在这个实验上花过时间……

再听这部分课，就会把知识联系起来。我仍然禁止直接用 AI vibe code 所有内容，大家还要自己写些代码，在 procfs 里多看一看。每次讲到某个命令行工具在 procfs 中做了什么，印象就会加深。慢慢也会像我准备这堂课时一样想到：proc 下 pid 有 fd，理论上就能找出系统中有多少进程引用 libbloat.so，实际也确实能做到。现在把 sample 全部杀掉。这次验证了动态链接库确实在进程间共享，既节省磁盘，也节省内存。
