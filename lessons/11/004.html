FLE 与二进制文件的等价表示

原片 00:12:38—00:22:59

每年我都会想，ELF 是对进程初始状态的描述，主要说明把什么内容搬到哪里、哪些位置需要重定位链接。它包含版本、体系结构等基本信息，内存各部分的数据及访问权限，以及调试信息、符号表和重定位信息。我们总能在等价的描述形式之间转换，这也是我上这门课时一直使用的基本原理。

最早讲非递归、递归汉诺塔时，我说可以从程序状态直接画出汉诺塔，就是把状态转换成另一种等价形式。我一直在做程序运行过程的可视化，例如 trace，把隐藏的信息用肉眼容易阅读的方式表达出来。现在 intelligence is cheap，只要知道这件事可以做，AI 就能生成代码来做。汉诺塔的 visualization 完全由 AI 帮我 vibe coding。前面还展示过管道：读取 /proc 下 PID 下的 fd，就知道进程打开了哪些文件描述符，再把文本转换成图形，就容易读一些。理论上，也完全可以把 ELF 转成肉眼容易阅读的格式，再实现一个加载器。想到这两点，就可以动手了。

可以 vibe coding，让 AI 来实现。

我每年都会讲一个叫 funny little executable 的格式。

这几年我一直在改进 funny little executable。它的想法就是自己定义一个描述二进制文件的数据结构。数据结构通常用什么表示？

minimal.fle 中的类型和符号表片段：

{
    "type": ".exe",
    "symbols": {
        "_start": 15
    }
}

可以用字符串、指针、field 表示，也完全可以转成 serialized 的 JSON 格式，用 key value 的 dictionary 或数组表达。我设计的二进制文件格式就是这样：不必像 ELF 那样在文件头放 \x7fELF，直接声明这是一个 .exe 文件。这里还有一些 symbol，例如 _start 在第 15 个位置。

这里是 ff，_start 在 15 的位置，后面是一些指令。头部的二进制符号表示这些是指令。我还实现了完整的编译器工具链，有 libc，可以把 c 语言编译成自己定义的 FLE 格式。

它也可以链接和加载。有兴趣的同学可以在 AI 指导下读代码。这个格式为 x86 设计，今天在 ARM 上运行不起来，但能看到我只是在 JSON 中引入几个符号，标明导出的符号和需要改写的符号，再把内容写在一起，视觉上就比较容易读。我觉得这个设计有趣，每年都在改进它，有兴趣可以看去年讲这部分的录像。现在，对 Funny Little Executable 有了新设计想法，马上就能实现：把设计说出来，通过 vibe coding 让 AI 帮忙实现。这也让我回头看这些年为讲课花的心思。大家觉得我的课有些特点，是因为每年我都会想，某个地方同学理解有困难，就应该加一层 visualization，或者做些事情让它更容易理解。

后来发现，这些想法都可以归结为：在等价的描述形式之间转换。设计一个合适的描述形式，其余工作交给 AI。无论喜欢命令行日志、visualize 的图形，还是方框和箭头组成的 diagram，都可以实现。也可以直接让 AI 读一个 ELF 文件，画成想要的框图。例如，给它一个 a.out。

再让它生成 SVG，正确展示内容。我对此有点兴奋，也有点怅然若失。前两天准备 slides 时，我在想，假如现在重新做 FLE，前面的 JSON 设计也不坏，相当于一个小的 DSL 语言。我的目的就是去掉 ELF 里这种指针结构。

课件中的 Markdown 格式示例：

# ELF [class=64 endian=le osabi=sysv machine=x86_64 type=ET_DYN pie=true entry=_start]
## PT_LOAD [flags=R|X align=0x1000]
### .text [type=PROGBITS flags=A|X align=16]
_start:
    48 c7 c0 01 00 00 00          # mov rax,1  ; sys_write
    48 c7 c7 01 00 00 00          # mov rdi,1  ; fd=1
    48 8d 35 {pcrel32: msg - . - 4} # lea rsi,[rip+msg]
    48 c7 c2 {u32: msg_end - msg}  # mov rdx,len
    0f 05                         # syscall

    48 c7 c0 3c 00 00 00          # mov rax,60 ; sys_exit
    48 31 ff                      # xor rdi,rdi
    0f 05                         # syscall
## PT_LOAD [flags=R align=0x1000]
### .rodata [type=PROGBITS flags=A|R align=16]
_msg:
    48 65 6c 6c 6f 2c 20 4d 44 21 0a # "Hello, MD!\n"

把 Offset 指针结构全部去掉，需要信息时，可以多占一些空间，让人更容易理解。那么，为什么不用 Markdown 做一个 ELF 格式？昨天我和 AI 对话，它给了这个设计：用 ELF 开头，把属性都放在后面的中括号里，包括 64 位的 ELF、小端机、System V 的 ABI、x86-64 等。

要加载到内存的一段，可以写成 PT_LOAD，标明可读、可执行。里面有 .text 节，节中有 _start 符号及相应代码，也可以写重定位。以前讲重定位时，那些什么 x86、relative PC32，大家可能都不记得了，我也不太记得。但这样写，马上就能看出 488D35 后面要放什么。

后面要跟一个四字节的小端整数，这叫 PC relative32。只要看出需要填一个数字就够了：msg 的地址减去点的地址，再减四。msg 和点都在同一个二进制文件里，地址都可以相对于文件头算出来。算出这个数字，再填进去，就是链接。编译时也一样：x86 的 call 指令有很多种，有很短的跳转，也有更长的跳转。一般在 a.c 或自己的 .c 文件中写一条 call 指令时，可以声称外面有一个 foo。即使不知道 foo 有没有定义，也可以在 main 中调用它。

声称外面有 foo，并不表示它一定有定义。假如从头到尾都没有定义，编译器在链接时就会报告找不到这个 symbol，无法链接。但在编译时，它已经可以生成二进制指令序列：一条 call 指令，后面留四个字节的零。这里这些零就相当于空出一个三十二位整数的位置。

这个三十二位整数，在例子里就是 msg 减点再减四的表达式。把内容以平坦的方式写进指令序列，问题就解决了。可以像我那样用 JSON、加一点 emoji 来吸引注意力，也可以用 Markdown，把代码内联进去。例如这条 mov 语句，把 len 赋值给 rdx。

它需要一个四个字节的常数，即字符串长度，用 msg_end 减 msg 来计算。这里需要有 msg_end 和 msg；链接时，所有符号都已安排位置，可以算出这个值，填入 32 位常数中，这就是链接。加载则按字面描述把相应内容搬到内存。例如，将 PT_LOAD 的内容以可读、可执行的方式搬到内存，用一个 mmap 系统调用就能完成。这就是链接和加载的基本原理。要读 ELF，可以在 AI 帮助下再去读。这部分只是复习，我不打算详细讲 ELF，现在也不需要掌握里面众多琐碎的细节。
