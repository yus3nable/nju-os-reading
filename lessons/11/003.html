ELF 为什么难读

原片 00:06:53—00:12:38

讲到 ELF，大家可能会想起被计算机系统基础课支配的恐惧。System V ABI 手册有几个部分规定了进程初始状态，包括 Process Initialization。应该是——对，3.4 有 Process Initialization，Figure 3.9 就是初始进程栈。

此外还有 Section 4，即 Object Files。大家上计算机系统基础课时可能试着读过。这份手册信息很多，每个东西都看不懂，很快就会关掉，考试却还要考。

印象中，每个同学都经历过痛苦的复习阶段。我曾找几个同学做过调研，问：“期末复习计算机系统基础的时候吐血了吗？”他们都说吐了，还觉得 CSAPP 连这一章也讲得比较枯燥，里面有很多细节。

理解这些细节需要专注。计算机系统基础课的老师也在“吐血”：一位老师说，第一次打开 PPT 时真的有点吐血；老师 B 说，根本讲不完，估计听懂的人也不多。我现在不上这门课了，这件事就和我没关系了。大家复习时有没有问过自己，为什么这么难，就没有办法了吗？肯定有办法。先想想为什么 ELF 难学：它是为了机器效率设计的数据结构，用来描述进程的初始状态。有很多段，需要说明从某个地址到某个地址，例如从 0x4000000 到某处，要加载到什么位置；还要描述读、写、执行权限，以及链接、调试信息、符号表等内容。为了机器效率，它连引用字符串的方式也和人讲解时不同。

比如上课讲一个叫 _start 的符号，我会直接说 _start。但 ELF 中的 _start 字符串不在引用它的位置，而在符号表里。直接编辑 /bin/ls，或者看过其他二进制文件，就会发现这些字符串以某种形式编码在文件中。这里看到的似乎是它的手册。

文件里有常量字符串和符号表中的字符串。这个 ls 可能没带符号表——对，没有带。那就自己写一个带符号表的程序，可以看到里面有 Scrt1.o 等奇怪的字符串。

还有 __libc_start_main 等字符串，它们都直接存在二进制文件中，但引用位置和字符串分开存放。需要使用 _start 时，可能在文件前面某处记录一个符号，对应 _start。ELF 怎样表示这种对应关系？需要一个 offset，说明该符号的字符串在文件的第 4587 个字节，也就是文件头加上 4587 个字节的位置。沿着这个类似指针的索引过去，才知道它是 _start。人读起来就很困难，即使用 readelf -a，也会看到大量这样的 offset。

加载内容或定位文件中的位置，都要靠 offset 计算，人脑很难算这些 offset。老师讲 ELF，讲到一个 program header 中有个叫 load 的东西。

再讲它的 offset 是多少时，大家的注意力可能就开始涣散了。为了高效，ELF 还有大量 bit field。例如，加载代码时通常可读、可执行、不可写；加载数据时则可读、可写、不可执行。这些信息都用 bit field 编码，需要先翻译成平坦的结构，人才能理解。

ELF 为机器设计，机器加一个 offset，或者把它 patch 成指向相应位置的指针，就能读到内容。人不适合像机器那样处理这种复杂结构。
