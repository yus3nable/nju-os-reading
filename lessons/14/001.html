从线程与系统调用回顾共享内存

原片 00:00:00—00:03:15

上一节课的时候给大家讲了多处理器编程从入门到放弃，从入门是最简单的一个线程库 thread.h 你们应该已经下载过代码并且运行过了，两个 API。一个是 spawn 你可以把一个函数作为一个线程运行起来，那它这段代码就和其他的代码可以并发和并行的执行，如果是一个多处理器的硬件的话，并且你确实可以验证它们是共享内存的，拥有独立的栈。

然后等到这个线程的 function 返回的时候，我们可以用 join 把它等回来，那这样你就可以实现多线程程序的使用了，但是你也发现如果你只依赖于线程库和共享内存的话，你甚至连一加一也不会求了，对吧？如果你有两个或者多个线程，你想要做 sum 等于 sum加一，你现在暂时是没有手段的，然后你甚至是连一二三这样的顺序你都数不出来了，因为有这个 weak memory model 的各种各样的奇怪的行为。所以我们不是教大家要去 hack 这种行为，而是要告诉大家：你们打开了一个魔鬼的盒子，对吧？为什么要在操作系统课里面讲并发呢？是因为 unix 引入了进程以后，虽然进程之间是不共享内存的，最早的时候 unix 的进程，你想，如果没有 spawn这个系统调用，如果只有 fork 和 execve，那 fork 出来的两个程序的副本，它就是独立运行的，拥有自己独立的地址空间，甚至在早期的实现里面，真的就是把内存一个字节一个字节拷贝了一份，那么 fork 和 execve 虽然不共享内存。但是系统调用的执行是共享内存的，如果我们的操作系统执行一条 syscall 指令。

那么 syscall 指令的行为实际上是一个跳转，它和你们普通的 jump 和 call 是很像的，只是它会附带一个权限的切换，也就是说当你穿过 syscall 的时候，你就从一个不信任的，对吧，所有的应用程序都是不信任的，你不能随便动计算机硬件的任何配置，包括 IO 的端口，包括中断等等，如果你动了，那操作系统的霸权地位就受到挑战了。但是当你，我们打一个比方，当你全身麻醉把自己交给医生的时候，那就相当于把这个程序交给操作系统的时候，又恢复到高权限的状态。而这个时候其实你想想。

每一个进程它在操作系统内执行的部分，就变成了一个线程，所以操作系统是最早的并发程序，一旦 syscall 开始执行了，比如说我可以一个进程，在 syscall 里面执行，read fd buff size，然后另外一个进程说，write fd buff size。然后这两个进程。比如说我现在在操作系统内核代码执行的时候，仍然是可能被中断的，对吧，依然是可以被中断的，然后那就带来麻烦了。对吧？p1 和 p2，不管他们是可能被中断，还是真的有两个处理器上运行的，p1 和 p2 的操作系统内核的部分。

如果这是同一个文件，就会出现我们上一节课讲的这种，1 加 1、1、2、3 数顺序的这些问题，所以操作系统，我们为什么在操作系统课里面讲并发，就是因为操作系统是第一个非常严肃的大型的，真正让人类感到头疼的并发程序，所以很多早期的和并发相关的结果，都是来自操作系统的研究者。所以我们就顺理成章的会在这里讲并发。好。
