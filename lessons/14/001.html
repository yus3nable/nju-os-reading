第 14 课 · 并发控制：互斥

从线程与系统调用回顾共享内存

原片 00:00:00—00:03:15

上节课讲了多处理器编程“从入门到放弃”。入门从最简单的 thread.h 线程库开始，大家应该已经下载运行过。它有两个 API：spawn 把函数作为线程运行，多处理器硬件上，这段代码可以和其他代码并发、并行执行；还能验证它们共享内存，各有独立的栈。

function 返回后，join 可以等待线程结束，这就能编写多线程程序。但只依赖线程库和共享内存，连一加一都难求对：两个或更多线程同时让 sum 等于 sum 加一，暂时还没有办法保证正确。weak memory model 的奇怪行为，还让一二三的顺序也数不清。课程要说明这些机制带来的麻烦，并不鼓励大家 hack 它们。为什么在操作系统课讲并发？unix 引入进程后，进程间原本不共享内存。只有 fork、execve，没有 spawn 时，fork 得到的两个副本独立运行，各有地址空间，早期实现会逐字节复制内存。但执行系统调用时，共享内存的问题又出现了。

syscall 指令类似 jump、call，是一次跳转，但同时切换权限。应用程序不受信任，不能随意修改硬件配置，包括 IO 端口、中断，否则操作系统的控制就受到挑战。进入 syscall 后，程序交给操作系统，恢复到高权限状态，就像全身麻醉后把自己交给医生。

每个进程在操作系统内执行的部分，都成了线程，所以操作系统是最早的并发程序。例如一个进程 syscall 执行 read fd buff size，另一个执行 write fd buff size。内核代码仍可能被中断，p1、p2 也可能实际运行在两个处理器上。

如果访问同一个文件，就会遇到上节课的 1 加 1、1、2、3 顺序问题。操作系统是第一个严肃、大型、让人头疼的并发程序，早期许多并发研究结果也来自操作系统研究者，所以课程会在这里讲并发。

long sum = 0;
void T_sum() {
    make_it_work {
        sum++;
    }
}
