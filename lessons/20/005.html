ILP Benchmark：依赖链与独立指令

原片 00:10:05—00:13:32

要证明这件事，可以让 AI 写一个测量脚本。以前上课时，我会展示这样的脚本，讲清自己做了什么，因为你们有一天可能需要自己写。现在我发现，今天已经不用自己写代码了，更需要知道的是：有办法写出这样的代码，以及怎样确认它是否正确。这次整个代码都是 AI 写的，起初犯了一些错误，后来自己修好了。

我让它做了一个 ILP Benchmark，即 Instruction Level Parallelism Benchmark，指令级并行测试。我们要测量的是，每次译码可以 issue 超过一条指令时，具体能达到多少。

我尝试在这个 CPU 上运行不同的程序。比如不断给 W0 寄存器加1：因为始终修改同一个寄存器，下一条指令必须等待上一条，无法并行执行。理论上，如果 CPU 实现得好，instruction per cycle 可以接近 1；实现得不好，比如你们实现的五段流水线 CPU，可能就到不了 1。

dep 内联汇编中的 AArch64 指令片段；%w[n] 为循环计数操作数，其约束和另一架构分支未列出。

mov w0, #0
1:
add w0, w0, #1
add w0, w0, #1
add w0, w0, #1
add w0, w0, #1
subs %w[n], %w[n], #1
b.ne 1b

还有一些程序修改不同的寄存器，比如 R0、R1、R2、R3。可以预期，这会触发指令级并行，让四条指令同时执行。我直接让 AI 帮忙统计 instruction per cycle，它就能写脚本、调用正确的工具。即使不知道 Linux 里有个工具叫 perf，也可以让它完成。我在 lecture notes 中也介绍过 perf。

perf 可以度量程序的各种行为，包括 cache miss 数量，用这些信息诊断性能问题。我们编译运行，先看结果。感兴趣的话，可以打开 Claude Code，让它解释程序到底做了什么。

现场输出中的 IPC 列；完整指令计数与 cycles 保留在上图。

variant  IPC
dep      1.50
ind      3.00
fp       3.00
neon     3.00
mix      3.00
imul     1.50

我希望大家听完课后，能找到感兴趣的问题继续了解。比如，这个测量 IPC 的程序如何实现？最上面的 DEP 程序有 dependency，不断执行 W0 等于 W0 加 1，竟然在我的树莓派上也跑到了 1.5 的 IPC。混合一些指令时，一个时钟周期可以执行三条指令。

程序通过 perf 得到执行的 instruction 数量和 cycles，也就是总时钟周期数。你们在自己的机器上会看到不同结果，这与 CPU 的实现有关。这门课不讲体系结构，我就不深入解释了。
