从系统调用到 libc 与程序入口

原片 00:01:59—00:08:02

操作系统与应用程序之间只有很小的一组接口，叫 system call，也就是 syscall。操作系统中有进程、文件，以及编程时能用到的各种设备，例如显卡，都是操作系统中的对象。访问这些对象必须经过 system call。

今天会调试一段代码，它与通常用 svc、syscall 这样的指令进入内核有些不同。访问操作系统内部对象或功能，都需要通过 system call。

直接用 system call 写程序会很麻烦，代码也冗长。例如 write to a file descriptor 需要文件描述符、buffer、count 三个参数，每次都要计算 buffer 长度。希望用高级语言提供的机制简化这些操作，于是有了 libc。

libc 与 C 紧密绑定，C 又与 Unix 紧密绑定，因此 libc 中能看到 Unix 的影子。例如，struct FILE 与文件描述符紧密相关。

自己实现 libc 的原理也不难理解。最早展示过 void _start，通过它可以控制程序入口。用合适的 freestanding 编译选项，豆包可以给出，就能不链接任何库函数。得到的最小二进制文件除了这个函数的代码，什么都没有。程序从这里开始执行，就从 0 开始接管了整个程序。

接下来想以 argc、argv、envp 调用 main。为此需要知道 argc 是多少、argv 和 envp 在哪里。

还记得 main 的函数签名吗？有一年期末考试让大家补全 int main，竟然有同学写不出来，让我有点尴尬。参数写成两个 star 也是对的。

声明另一个地方有 main 函数，就可以在这里调用。调用遵循指令集体系结构的 calling convention，把 argv、envp 这些指针和 argc 放进正确的寄存器，再通过跳转指令进入 main。

现场输入的入口代码片段；参数取得过程尚未填写。

int main(int argc, char *argv[], char *envp);

void _start() {
    // ...
    // argc = ?
    exit(main(argc, argv, envp));
}

main 可能正常返回，也可能通过系统调用退出，或者调用 libc 的 exit；正常返回时，就进入这里的 exit。这是上次看过的代码。控制 _start，就能控制整个程序。C 有 Foreign Function Interface，也就是 FFI，支持两种方式：一是直接调用符合 calling convention 的汇编代码，只要调用规则与 C 兼容，就可以直接跳过去。可以把任意一段汇编声明为 void f，接收两个参数，int x、int y。该函数只需从正确寄存器中读出值，实现对应功能。另一种方式是在 C 中直接写 inline assembly，即内联汇编。

这样 C 代码就能执行系统调用。可以理解为 syscall 之上有 libc，不过并不完全严谨，因为二进制文件也可以直接访问 syscall。说 libc 通过 C 的 FFI 调系统调用，也不绝对严谨。

我觉得可以先接受这个说法：通过 C 的 FFI 调用系统调用，访问操作系统对象，在此之上得到 libc 这个平台无关的抽象层。虽然它与 Unix 设计紧密绑定，例如 struct FILE 与文件描述符相关，但任何给人用的操作系统，总应有访问文件的功能，也总应提供实现 fopen、fseek、ftell 的方式。

底层无论是 Linux、Windows，还是微控制器上很小的操作系统，都可以有 libc。手表、手环基本都有 libc，树莓派 Pico 这样更小的设备也有。它们底层的 System Call 可能与 Linux 不同，对上暴露的接口却基本完全一样，提供了通用的抽象层。

有了 C，就可以构造自己的应用世界，例如编译 Python 或其他语言。
