第 10 课 · 调试 C 标准库

编译选项与 JavaScript Source Map

原片 00:19:30—00:27:33

上次调试失败，需要在这里加 -Og 和 -ggdb，当然那天用的是 -O1。后来保险起见，我又加了 ASFLAGS，却发现没用。可能豆包最初没有加，也可能是我后来 hotfix 抢救时加错了位置，没有意识到应该加在 CFLAGS 中。

config.mak 中的配置行：

CFLAGS = -Og -ggdb

后来加上这两个选项，整个 musl libc 就有调试信息，可以调试了。调试信息主要用于将 PC 映射回源代码，基本每种语言都有。C、C++ 的 addr2line 和调试信息本身没有源代码，需要把 .c 文件放在正确位置，GDB 才能读取。

有些语言的做法不同，例如 JavaScript。写 TypeScript 后，不能直接在 JavaScript 虚拟机里运行，因为它不认识这种语法。JavaScript 有一系列 transpiler，类似 compiler，我不确定中文该怎样翻译，暂称转译器。它们把 TypeScript 转成没有类型标注的 JavaScript，再把新版本 JavaScript 转成旧版本。新版本中的 async 等语法，旧版本并不支持，需要转译为 20 年前浏览器也能运行的形式。

转译后的代码才进入浏览器运行，类似高级语言逐步翻译成汇编。调试时，console 可能显示红叉，提示某个值不能是 null，打开教务系统等网页也可能看到。要调试这种问题，就需要类似 debug info 的映射，从底层 JavaScript 的某一行，找到原始源代码中的对应行。

为了方便，这种 debug info 可以脱离原始源代码 repo 工作。C 的 GDB 运行在操作系统上，有目录可用，假设目录中存在源代码很自然；JavaScript 进入浏览器后，沙盒中没有整个项目目录。例如，我调试课程网站时，为了显示出错行，Next.js 会显示友好的框，指出哪一行、哪个变量出错，给出函数调用栈，并在下面显示代码。有时看一眼代码就能修复。为支持这种功能，JavaScript 可以把源代码直接存储在 debug info 中，相当于 C 中执行 readelf -a a.out 时，看到完整的所有源代码。于是有了这两天的事件：我下载了五十几兆的 cli.js.map，其中就是所有 Claude Code 的源代码。

这是这两天最大的事件。我粗略看了一下，觉得还是挺屎山的。网上很多文章称赞其设计，但我看到的大多是正常设计，也有不少屎山内容；当然有些内容值得看。文件大到 Vim 插件都不能用了。例如有一行注释：checks if input matches negative keyword patterns。

从中能知道程序出错后，程序员怎样骂它，我觉得这显然不好。我似乎没找到这个函数的调用链，像是没有函数调用它的死代码，但不确定发生了什么。还可以看整个 UI 的实现：它是 React 实现的 text UI。感兴趣可以看看怎样异步处理 LLM 的 tokens。拿到 cli.js.map 后，仍然无法直接 build 运行，因为它缺 package.json，项目不完整。

很快有人补出了可运行版本，但 build 会执行脚本；如果对方在依赖中投毒，就有危险。最近有一起有名的投毒事件影响 Claude Code。我不确定安装是否有问题，安装应该不会；build 某些版本时会引入恶意包，执行脚本，可能泄露重要信息，例如 LLM token。下载运行这些项目，尽量放在干净沙盒中，直接在自己的电脑上运行有潜在安全风险。我还注意到，他们的持续集成竟然没有用 Claude 检查信息泄露。任何项目，例如 musl，都可以让 Claude 检查 information leak，检查源代码、credentials、API key。发布前，可以让 Claude 这样的 agent 至少扫描一遍包中有没有潜在 API key 泄露。

它 grep 各种 pattern 查找潜在 API key 泄露，方法比我聪明。早些年，无数公司因为把数据库密码、admin 密码 check in 到 GitHub，遭到脱库。

现在更多是开发者不小心把 API key 暴露在源代码中，传到 GitHub 后被滥用。我觉得 Anthropic 至少应该在 release 前让 agent 做一次这样的检查。豆包最后告诉我：看起来是标准 libc 源码发布版，没有发现 API key，仓库安全。但相信这样的结论也有风险，有时相信 AI，就会弄错。
