第 10 课 · 调试 C 标准库

调试信息、性能采样与 Sanitizer

原片 00:27:33—00:35:16

debuginfo 能提供什么能力？汇编意义上的程序状态是 register 和 memory。例如一条 call main 指令，main 对应一个地址。

程序有 RDI、RSI、PC，也就是 RIP 等状态。ELF 或 a.out 中的 debuginfo 能帮助恢复源程序信息，例如 call main 时，RDI 是 int 类型的 argc。类型信息也包含在 debuginfo 中。

debuginfo 很复杂，为什么需要虚拟机？C 有 bit field，可以在 struct 中定义 32 个有名字的变量，每个只占一位。调试时要打印其中某一位，就需要指令集从 32 位整数中提取一位，来源也可能是寄存器。

例如，argc 是 int，可能位于 RDI 的低 32 位，debuginfo 帮助恢复这些信息。从汇编二进制状态重构源代码状态，就能实现很多功能：addr2line 从 PC 地址返回源代码行，也能做 stack unwinding，实现 backtrace。在 GDB 中，有多层函数调用时，用 bt，也就是 backtrace，就能看到当前这一瞬间，谁调用了谁，一路怎样调用过来。

不仅能恢复 top frame，还能恢复 C 语言模型中的完整函数调用栈，便于在 GDB 或可视化调试器中理解程序。也可以实现 trace 和 profiler。前面多次用过 strace，它能追踪程序所有 system call。musl libc 编译出的程序，system call 很简短：exec 之后只有一两个与系统相关的调用，随即执行程序。换成 gcc，系统调用就多得多。

即使用 gcc -static test_debug.c 静态链接，再 strace ./a.out，也能看到 readlinkat、getrandom 等调用。

这些调用在上面的 musl libc binary 中没有。system call trace 某种程度上是操作系统提供的功能。有 debug info，还可以每隔一小段时间暂停程序，查看当前状态；既可由操作系统完成，也可在应用层实现，像游戏修改器一样。例如每隔一毫秒或更短采样一次，再通过 debug info 恢复调用栈，就能得到 flame graph，也就是火焰图。图中横轴是时间，展示调用栈随时间的变化：每调用一个函数，上面就增加一层；函数返回，就减少一层。

通过采样，大致知道函数调用的分布，哪些函数耗时最长。底部有些部分一直没动，例如 main 从进入开始就处于调用栈中，直到程序快结束才 pop 出去，之上逐层形成 flame graph。

采用均匀采样，就能大致分析性能；strace 则记录所有系统调用。一般程序大部分时间花在少量函数上，通过采样就能找出性能瓶颈。可以与大语言模型讨论这些工具，导出 trace，也有对应的 perfetto 标准。如果程序 crash，有了汇编意义上的程序快照，同样能在一定程度上调试它，甚至修改一些值，例如 PC，让程序继续执行。大家用过 sanitizers 吗？我已经不太会古法编程了。这个程序表面运行正常，实际有错：p 已经 free，之后仍然使用；多线程程序中，还可能有其他线程介入。

现场输入的程序（第二行末尾有冒号）：

#include <stdio.h>
#include <stdlib.h>:

int main() {
    int volatile *p = (int *)malloc(4);
    *p = 1;
    free(p);
    *p = 1;
}

后面会讲到，这叫 use-after-free，释放指针后继续使用。p 本身的值没有变化，free(p) 后那块内存在地址空间意义上可能仍能访问，程序未必 crash，却可能造成严重问题。这是 undefined behavior，可能导致安全漏洞。加上 -fsanitize 等于 address，结果就不同了。

启用检查的编译选项：

-fsanitize=address

它会报告 heap-use-after-free on address。AddressSanitizer、ThreadSanitizer 等 sanitizers 都能利用调试信息，在诊断报告中恢复更多源代码信息。有了 debug info，今天就可以实际调试这些程序。
