第 10 课 · 调试 C 标准库

指令跟踪为何陷入重试循环

原片 01:06:47—01:10:58

刚才省略了一些实现细节，因为课堂逐条讲汇编太花时间。我还让 AI 生成了一段代码，用来获取 gettimeofday 执行的完整指令日志。

我觉得以后的操作系统课可能不需要我这样的老师，人工智能比我做得更好。我只需告诉大家存在这种机制：不陷入操作系统内核，在进程地址空间内直接 call 对应代码，它就能运行。用调试器可以查看完整代码，记录 gettimeofday 的所有执行指令。这里没装 debug info；安装 Linux 内核 debug info 后，也能调试对应源代码。即使没有源码，也能用 gdb script 记录指令。我给的 prompt 是：进入 __kernel_clock_gettime 时开始记录，出来时停止。刚才运行这个程序，看起来又翻车了，函数一直循环执行相同的指令序列。为什么？

可以问 AI：为什么正常运行的 gettimeofday 能中止，debug 时 trace 指令序列却不停？CPU 每次时钟中断，都会给 clock 加一，相当于 clock tick 的 count 依次增加。

gettimeofday 的代码很短，调用过程中几乎不会遇到 clock 加一。先读一次 clock tick，记在寄存器中，再读一次；两次相同，说明没跨过一次 clock tick 加一，就认为读到了正确、稳定的值，可以据此计算精确时间。如果两次不同，就再试一次。AI 已经读出指令序列的含义，课堂上我也能分析，但要花很多时间，它做得很快。这类似 sequence lock，读取 clock count 时会取一个 sequence count。

Agent 引用的指令片段：

+32:  ldr w7, [x3]
+92:  ldr w4, [x3]
+96:  cmp w7, w4
+100: b.ne +32

+32 时读到 w7，+92 时再读到 w4，随后 compare。两次 tick 不相等就重试，相等才继续。单步执行时，每条指令间都有很大延迟，循环就一直无法结束。AI 找到了正确答案，也让我们从二进制指令序列理解了 gettimeofday 的实现。
