硬件视角的操作系统

原片 00:09:19—00:51:49

来听课，也许还能学到一些内容。先复习上一节的应用视角，它已经勾勒出整个 big picture。我们有一个 C 程序。

复习软件、硬件和操作系统

这个 C 程序是一个状态机，就像汉诺塔程序。它最终变成 a.out，也是状态机，不过每步执行一条指令，C 语言每步执行一条语句。a.out 运行在操作系统上。操作系统里有许多对象，a.out 文件本身是对象，它运行形成的进程也是对象，此外还有其他进程和对象。操作系统又运行在硬件上，硬件同样是状态机。

中间通过编译器等知识把它们联系起来。a.out 里有一条特殊指令 syscall，不同体系结构的写法不同，但行为基本一致：把程序控制权完全交给操作系统。就像全身麻醉，彻底失去意识，醒来时请求已经完成；比如请求割掉一个肾，醒来后肾就没有了。这可以帮助理解应用视角。但操作系统终究运行在真实硬件上，今天从硬件视角来看。

今天先建立概念，知道有什么。硬件视角可以直接概括为：硬件不知道有没有操作系统，也不知道跑的是哪种操作系统，它只负责执行指令。上学期写 NEMU 模拟器时，就是这个模型，没有操作系统概念，只有指令集体系结构的 specification。手册规定 add、move 等指令怎样把状态变到下一个状态。某些指令稍特殊，比如可能实现过的 int、interrupt、int 0x80，行为和 move、jump 不同；out、in 还可能与外界交互。这些指令可以用来实现操作系统，但硬件不知道上面跑的是什么，完全可以运行其他程序。这涉及计算机系统中常说的抽象，也就是隔离上下两层。

这是 computer system 里狭义的抽象。上节课的 syscall 就是一种抽象。可以看看手册，当然今天不必像我一样用传统方式查找。这里有完整列表，列出 Linux 提供的所有系统调用。

有些调用从 kernel 1.0 就有，有些较新，从 4.9 才开始提供。每个 System Call 执行相对确定的行为，像一台小手术，对身体做一件明确的事情。

比如把我改造成机器人，完成后放出来，继续做自己的事。通过这组精简接口，程序几乎能实现任何事情。比如从操作系统读数据，再在应用层处理、画图、构建图形界面，或执行游戏逻辑，底下的操作系统不必知道。少量 syscall API 就能支撑整个应用生态，上节课强调的正是这一点。

肉眼看见的应用，以及后台看不见的程序，比如插入 U 盘后自动在桌面创建快捷方式的程序，都是如此。syscall 不需要知道上面有什么，这就是隔离复杂性。接口上下都复杂，中间接口却简单。比如 read、write。大家有没有想过，为什么 printf 有时输出到屏幕，有时又输出到文件？

代码和生成的二进制完全相同，都是 printf，但运行时能重定向到文件，甚至另一个终端。底下的实现很复杂，虽然看到的系统调用只是 write，带一个文件描述符参数，也叫 fd。后面会详细讲文件描述符。

文件描述符能指向操作系统里的对象，可能是文件，也可能是其他东西，才实现了 printf 的这些用法。抽象层上下都很复杂：操作系统要画出一个像素，需要驱动显卡，显卡还得通过线接到显示输出，应用看不到这些复杂性，只需知道要做 write。操作系统也不必知道上面的应用生态，linux 内核上可能运行 Android、云服务，也可能是树莓派上正在使用的课堂系统。

硬件也通过指令集体系结构提供抽象，只暴露 Move、Add、Interrupt、OutIn 等基础功能。内部其实很复杂，设计高性能处理器系统是很难的。大家做过简单的 RISC-V 处理器。

今天的实际系统，一个时钟周期可以执行多条指令。虽然状态机模型按顺序执行，但比如 Move 1 到 RAX，再 mov 2 到 RBX，两条指令没有数据依赖，不需要对方的结果，写入目标也没有冲突。数字电路的逻辑门、触发器本来就并行工作，只要寄存器有两个读口、两个写口，理论上就能在一个时钟周期完成这两条指令。

电路上可以做到。现代计算机硬件可以理解为实现了一个指令级编译器：指令不断译码后，动态做数据流分析，判断哪些指令可以并行，再同时执行。底层很复杂，上面的操作系统和应用生态也很复杂，中间只是指令集这个很小的抽象层。我觉得抽象层设计是 Agentic AI 时代的重要能力。下一节可能会讲这套系统的设计。设计好，上下都容易扩展；设计不好，改一点就可能需要整个项目重构。但低年级同学只听这句话也没用，需要广泛了解设计。比如最近小龙虾很火，有没有在 AI 帮助下读一读它是怎样构造的？平时实现功能，可能只想到写函数、调用函数。

如果需要扩展，却不知道未来的需求，系统该怎样设计？大家可能还没设计过支持插件的系统。VSCode 就支持插件，身边还有许多系统，除了提供功能和服务，也允许扩展。我觉得这是现在用 Agentic AI 做产品的重要能力。有人开玩笑说，程序员 vibe coding 只能做备忘录、记账之类的应用。

刚用 OpenClaw 时，大家可能停留在基本功能上；有好的抽象层，上面就能发展更广泛的应用生态，现在就可以开始学。再回到计算机系统：硬件是执行指令的机器，状态就是内存和寄存器的数值。

计算机系统的状态机模型

初始状态由系统设计者规定。CPU Reset 信号到来后，处理器进入约定状态，比如 PC 等于某个确定的值，之后开始执行指令。每次状态迁移，从 PC 地址取指令、译码，再按手册执行。这个描述准确，但还有省略。对应用程序模型，加上 System Call 就够了；要在硬件上实现操作系统，细节还不够。比如写 jmp .，点表示当前位置。

每次跳转都回当前位置。如果硬件严格只有刚才的模型，操作系统就再也干不了别的事情，整个系统会死机。那是课堂上为了方便理解而做的简化，真实系统还要复杂一点。

系统内部状态与外部物理世界

再展开一些。计算机系统的状态分两部分：系统内和系统外。内存、CPU 插在主板上，寄存器封装在 CPU 里，主板又处于物理世界。所以除了计算机内部状态，还有物理世界状态。这台树莓派每一瞬间都有内部状态，同时也位于教室里，可能和人交互。

假设连接了摄像头，执行 in 指令，从摄像头读取一个像素，存入 AX 寄存器。那下一状态的 AX 值就来自物理世界。只有一个像素的相机也有用。以前 NES、任天堂小霸王游戏机上有个著名的打鸭子游戏，是很早的体感游戏：用一把枪对着屏幕射击。

它怎样判断有没有击中？枪里是一台只有一个像素的摄像机。扣扳机后，计算机知道开枪，在屏幕上输出两帧，一帧白、一帧黑。如果相机检测到一白一黑，就认为命中；检测到两帧黑，就认为没命中。

模型包含物理世界的状态，而计算机不能完全控制物理世界。怎样访问它？靠线。计算机通过物理导线连接外部传感器。CPU 还有 interrupt、reset 等信号线。reset 在后面。

GPIO 控制引脚电平

树莓派这边的线有点挤，可以看到一排针脚，和图里一样。有些针脚供电，有些能用程序控制。想让计算机和物理世界交互，一行代码就能做到。

比如 gpio_set_value、GPIO_23，可以把 23 号引脚的电平拉高或拉低。计算机世界没有魔法：用面包板接一个发光二极管，写循环先设成 1，隔几百毫秒设成 0，再反复切换 1、0，就能看到它闪烁。有了 GPIO 概念，其余可以问 AI。比如让它查本机有哪些 GPIO 接口，它就开始运行命令，用到 gpioinfo。先知道计算机和物理世界相连，再追问怎样连接。即使 Computer Science 训练很好的人，也不可能熟悉所有领域的工具。

AI 有这些知识，也能查手册、上网搜索，效率比我们高。一百万上下文能一次读很长的文档。看它运行命令，我就学到了：gpioinfo 可以查看系统 GPIO 情况。

它还知道这是树莓派 500 的一个变体，列出了芯片型号和 GPIO 控制器。刚才那排针脚并非系统里唯一的 GPIO 控制器，只是供用户连接外设的部分。可以购买超声波传感器、摄像头，也能接机械手，一行 C 代码就能写电平，用起来很方便。

接上外设，就可以做能走的小车、机械手。GPIO 也用于内部硬件，比如 SPI 总线、按键、蓝牙、WiFi。AI 最后说一共有 111 个 GPIO，但只有 2 到 27 可供我使用。CPU 内部状态通过线连接物理世界，IO，也就是 input output，是重要的一组线。另一种重要的线是 interrupt，中断。为什么死循环程序不会卡死整个系统？按原模型，死循环会永远出不来。但还有这根物理信号线，可以低电平触发，也可以边沿触发。只要没有关闭、屏蔽中断，信号到来时，无论 CPU 正在做什么，即使执行 jmp .，也会强制跳到另一个位置。

时钟、按键、网卡收到数据包，都能通过中断信号，让处理器中止当前程序。这赋予操作系统控制地位，因为应用程序不能关闭中断。回去可以让 coding agent 写一段汇编，尝试在自己的应用程序里关中断。以前我会在课上演示，现在可以直接让它做。

它会写 inline assembly。过去，system programmer 要花很长时间学内联汇编，这是我们比较骄傲、别人少有的知识。今天 AI 已经写得很好。一行汇编就能尝试关闭中断，但程序运行到这条指令时，会出现 segmentation fault：应用程序没有管理中断的权限。

大家应该学过 x86 的 clear interrupt、set interrupt，它们可以修改处理器的某个状态。在 RISC-V 中，对应 CSR 里的某个 bit，决定是否响应中断。操作系统代码有权限关闭中断。

如果操作系统关闭中断后遇到 bug，进入无限循环，就真可能死机。这些都是对状态模型的补充。启动初始状态也更明确了：S0 是 CPU reset 后的初始状态，通常中断关闭。为了节省电路，某些寄存器的值不定义，另一些规定为零或特定值。

CPU Reset 与初始状态

比如 PC 一定要有特定值。CPU reset 后，许多寄存器还没完全初始化好，但 CPU 已经和物理世界相连，外部随时可能发来中断，所以初始时一般关闭中断。大家见过老式机箱吗？这可能就是代沟了。笔记本死机怎么办？以前可以拔电池，现在电池内置，焊在里面，一般要长按电源键足够久。

这个动作靠主板电路实现，软件不负责。长按一段时间后，电路强制向 CPU 发送 reset。以前我们可能还买不起市面上的笔记本，用的是台式机，机箱上都有 reset 按钮。无论程序处于什么状态，有图形界面也好，正在操作 GPIO、播放音乐也好，按下 reset 就会触发复位，和大家写电路时的 if 一样。

每个寄存器下个周期的值，都要根据 if reset 决定。为什么要配 reset 按钮？那时电脑经常死机，到处是 bug、漏洞和病毒，一会儿还会讲一个著名病毒。我觉得历史很相似：革命性产品刚出现时，往往不好用、不可靠、漏洞很多，但人类总有办法逐渐补好。

今天手机、电脑已经很少频繁死机。那时却常常游戏运行到一半就死机，硬件不可靠，软件有 bug，也可能感染病毒。这和今天 OpenClaw 很像，各种不可靠；本地模型可能陷入无限循环，反复说同一句话，让人恼火。但我觉得这些问题终究会解决。今天觉得大语言模型慢，也许以后有办法让推理更快。

担心 OpenClaw 安全，不敢放自己的数据，也有可能解决；我们已经看到一些可能一劳永逸解决问题的技术途径。需要时间，也需要足够多人获得资源支持来做。大家身处很好的时代，虽然可能担心 AI 终结程序员，读过“软件工程已死”，怀疑学这些有什么用，但这也意味着新时代开始。可以想象回到没经历过的 1980 年代或 1990 年代的中国。

那时买三块钱、五块钱一张的盗版光盘运行游戏，机会遍地。我觉得今天也是这样。

从处理器手册理解实际的 CPU Reset

现在知道了初始状态、状态迁移、与物理世界相连的状态和中断线。过去可能讲到这里就结束，因为这些话都 make sense，大家相信，老师也说服了大家。今天还可以往前问：真实机器是什么样？x86、arm、RISC-V 的 CPU reset 分别怎样？可以直接问大语言模型。以前我作为 system programmer，为建立这些概念，大四一整年都在读英特尔手册。

那本手册几千页，详细说明处理器每个 bit、每条指令的作用，读起来很枯燥，还要从大量信息中筛选。比如 mov 和 XOR，对我来说基本属于同样的内容，需要略过；有些指令实现了还没完全理解的机制，就得四处找资料。

这个过程很痛苦。以前上课总会展示这一页手册，里面清楚写着 CS、IP 寄存器的状态，哪些 undefined，哪些初始化为零，都是厂商规定。今天不必先打开手册，直接问 AI。它说的都对——也未必，不会绝对都对，只是典型的系统 configuration。RISC-V 和 ARM 中，厂商都有一定决定权。回答里能看到 MMU 禁用、缓存禁用等描述。

还有高特权模式、中断关闭。我感觉 GLM 刚才有些回答可能是幻觉，应该不对；给它正确手册，应该能得到正确回答。但以前读手册也没白读，它帮我理解处理器能做什么，操作系统怎样使用处理器。像大模型一样，我经历了漫长的预训练，现在是后训练、微调，用过去知识理解新东西。今天可以换一种学法。我准备了一个代码 demo，起点就是这里的 prompt，把它交给 Claude Code，要求写硬件代码。

执行指令、中断与输入输出

这个模型还能解释以前没接触过的问题，比如多处理器。今天从手机到电脑，几乎都是多处理器，单处理器一般只在嵌入式开发板或自己做的小 CPU 里见到。我上学时，能买到的商用处理器几乎都只有一个处理器，Intel 的多处理器系统才刚出现。这个模型也能理解多处理器，而且状态模型比想象中简单。

比如 CPU0 有自己的寄存器，各 CPU 共享内存。现在的处理器叫 shared memory 处理器，可能采用 NUMA，也就是 non-uniform，有些 CPU 访问内存快，有些慢。喜欢数码、看游戏 CPU 评测的同学可能见过：英特尔有超大核、大核、小核时，有些核心的内存访问延迟会比其他核心大。

不同处理器之间共享内存的速度也可能不同。概念模型是每个 CPU 有独立寄存器，共享一份内存；实际实现还有共享缓存等。

状态是这样，迁移呢？把第一个处理器的寄存器和内存放一起，就是一个单处理器系统；换成第二个寄存器集合和同一内存，又是一个。可以先把每次迁移理解为选一个 CPU，执行一条指令。这个模型还不完全准确，讲并发时会深入说明。当前状态下，可以选 CPU0、CPU1 或 CPU2，各 CPU 也可能响应中断。有中断、多处理器以后，每次状态迁移都有多种可能，不再只按固定方式取指、译码、执行。并发程序运行多次，结果可能每次都不同。要精确理解，就得不断考虑执行指令还是响应外部中断，分支很快变多，难以掌握。

这些机制让系统功能强大，也带来复杂性，精确理解越来越难。回顾状态和迁移：硬件不知道有没有操作系统，只提供底层机制和抽象，让软件调集多个处理器的资源。

硬件视角的操作系统小结

硬件有确定的 reset 状态。多处理器的 reset 更复杂，一般先启动主处理器，控制它的代码，再用其他方式启动剩余处理器，比如发送核间中断。这些属于底层硬件细节。硬件只提供足够的机制，包括中断、IO、执行指令，无须知道有没有操作系统。上面的操作系统就是普通程序，开始执行后先做初始化，后面会讲这个启动过程。

启动时能看到日志，Windows 则会转圈。完成初始化后，操作系统成为系统调用和中断的服务程序。虽然仍在内存中，通常却不占用 CPU 执行；中断到达或应用执行系统调用时，操作系统代码才开始执行。

初始化后，它作为服务提供者，创建出应用程序的世界。这就是硬件视角的操作系统。
