第 03 课 · 硬件视角的操作系统

调试 Firmware

原片 01:23:17—01:35:28

还有一点时间，再看一些代码：43 年以前，IBM PC 在 1983 年开始确立的 Firmware，怎样加载操作系统。这已经是历史，今天不会这样做了。刚才 ARM 的最小程序就展示了，可以直接把任意代码作为 Firmware 运行。

IBM PC 的启动扇区约定

也有开源 Firmware，比如 RISC-V 的 OpenSBI，可以在 AI 带领下调试，观察现代系统的启动方式，今天没时间讲了。1983 年的情况更简单。CPU Reset 约定 PC 等于 FF0；对 x86 而言，是 CS、IP 等于确定的值。随后 Firmware，也就是 BIOS，开始执行，按顺序扫描存储设备。这就是 A、B、C、D 盘的由来，按驱动器 ABC 的顺序扫描。如果 A、B 软盘驱动器里插着可启动软盘，就先从这种移动介质启动，C 盘排在后面。那么，怎样识别启动盘？

早期的规定很简单，不需要学很多门课。存储设备可以看成 byte array，也就是字节数组，逻辑上按 512 字节一组。上面可以有 DOS、Games、Basic 等，也有文件系统。但 Firmware 只检查第一个 512 字节尾部有没有 0x55、0xAA。这两个数比较特别，一个是 010101，5 是 101。

A 是 1010，所以这两个字节是 0B01010101 和 0B10101010。

当然可以选其他数字作签名，这里约定了这两个。看到签名以后，Firmware 把这 512 字节加载到内存 0x7C00，设置 CS、IP 对应 0x7C00，再跳到第一条指令。这样就完成了从固化在 ROM 的 Firmware 到软件的交接。512 字节里是 boot loader，也叫启动引导器。假设磁盘上还有操作系统的 ELF 文件，引导器再把 ELF 加载到内存执行。以前这部分代码也会讲，现在先不讲细节，只想说明计算机没有魔法。用一个 printf 就能构造字节序列：开头是 EBFE，也就是 EB FE。

接着是 508 个字节的 0，最后是 0x55、0xAA。得到 a.img 后，用 QEMU 启动，能看到 booting from hard disk，字有点小。

CS、EIP 对应 7C00。任何磁盘镜像，只要满足 BIOS 约定，就能被识别。但把这两个字节顺序换成 AA55，再运行，屏幕信息变了：boot from hard disk 失败，不再是 bootable device。

它继续扫描其他设备，包括 CD、DVD 和网络启动，全部失败，最后显示 No bootable device。刚才用很小的一条命令，确实创建了可以启动的启动盘。

早期规定就这么简单，像 OpenClaw 一样，把东西放进去，给好权限，就运行了。早期 firmware 的行为也容易理解，还能实际调试。

从 CPU Reset 跟踪固件加载

刚才已经看过从 CPU reset 开始的指令序列，知道自己的小段代码怎样执行。理论上，CPU reset 时，这 512 字节还没加载到内存，firmware 里必然有一段代码，把它们从磁盘读进来。手册、网上资料都讲这个过程，但还可以进一步问：能不能看到加载发生？从第一节课起，我一直想展示，计算机里能想到的事，通常就有人能做到，大家需要敢想。比如在 8086、80386 上，Firmware 到底用哪条指令，完成从磁盘到内存的加载？

可以观察。这里准备了代码和一个小镜像，和刚才类似：开头 EBFE 是死循环，后面有 11 22 33 44。

末尾也有正确的 55、AA，才能识别成启动盘。运行效果和刚才一样，在 QEMU 里用 info registers，能看到 EIP 是 7C00。退出后还可以调试。要知道哪条指令把磁盘数据加载到内存，可以用 GDB 的 watchpoint。问大语言模型，它也会建议用 watchpoint 观察数据变化。

GDB 初始化脚本与 watchpoint

watchpoint 可以设在任何位置。everything is a state machine，固件也是普通代码，其执行和操作系统、应用程序一样。理论上能在模拟器中给 0x7C00 内存设 watchpoint，也能在 7C00 设 breakpoint，判断何时跳转到这里执行。还可以让 AI 写命令，每次停止时打印 0x7C00 附近内存，一条命令即可。以前这些是 System Programmer 的重要能力：知道能做什么、怎样找系统问题。计算机系统基础第一个 PA 的第一个实验，就是实现 watchpoint。

大家可能实现后没用过这个 feature，也不清楚用途。它是很有用的调试设施，可以观察程序运行中访问的数据。现在执行 make debug，会先启动 QEMU。

再启动 gdb。当前机器是 arm64，所以要用 gdb-multiarch 调试 x86 代码，启动时执行刚才的 gdb 脚本。运行 make debug，程序停下，此时 watchpoint 还未生效，7C00 附近的内存都是 0。

因为是 16 位代码，反汇编结果不太正确。不过单步执行时，能看到 7C00 附近的内存从 0 开始，每次两个字节，逐渐加载到正确位置。

还能查看所有寄存器的值，包括 PC、IP。CS 是 F000，说明现在执行的是固件代码。遇到不懂的地方，可以直接问 AI 为什么。
