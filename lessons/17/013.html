第 17 课 · 并发 Bugs 和应对

LD_PRELOAD、锁依赖图和 LockDep 演示

原片 00:38:02—00:42:30

可以用 LD_PRELOAD，把每次 Mutex lock、unlock 替换成自己的代码。我们以前用过这个机制，做过修改器。

动态加载时覆盖原有 API，就可以像 strace 一样打印 lock、unlock 日志，再通过管道交给 check.py，检查系统有无潜在死锁。这样的程序叫 LockDep。还可以边 Trace 边检查，无需再接另一个程序，只要维护一个数据结构。

假设有 A、B、C、D 多把锁。T1 先上 A 再上 C，我们就记录 A、C、D；线程 2 先上 B 再上 D。某天有线程先上 D 再上 A，图中就形成了环。这成为一个数据结构问题。

每发现一条新边，就检查图中有无环，由此判断是否存在潜在循环等待型死锁。这里有 LockTrace 和 LockDep 的代码。LockTrace 完全是 Vibe Coding，我没有管细节；只要知道 LD_PRELOAD 可以 override 动态链接程序的符号，剩下的麻烦可以交给 AI。不过仍建议大家学习实现细节。

pthread_mutex_lock 包装函数中的日志片段：

in_trace = 1;
fprintf(stderr, "[trace] thread %lu: acquire  %p\n",
        (unsigned long)pthread_self(), (void *)m);
in_trace = 0;

int ret = real_lock(m);

in_trace = 1;
fprintf(stderr, "[trace] thread %lu: acquired %p\n",
        (unsigned long)pthread_self(), (void *)m);
in_trace = 0;

return ret;

可以 trace 正常的上锁、解锁程序，观察 acquire、release，也可以 trace the dining philosopher，看每个线程 acquired 哪一把锁。

我还让 AI 直接实现 LockDep 检查。刚才用 printf 打印 lock、unlock，现在它用很直接的方式维护这张图。

lockdep.c 中的依赖矩阵和线程状态字段：

static int edge[MAX_LOCKS][MAX_LOCKS];

/* per-thread: stack of currently held locks */
static __thread int held[MAX_HELD];
static __thread int nheld;

/* recursion guard */
static __thread int in_lockdep;

接着检查图中有没有环。我不知道它用了哪种算法，这是算法课的内容。这里要看的是用 LD_PRELOAD 检查程序：一个能够通过的 test 没有报错日志，有 64 个线程。

100 轮上锁都没有发现顺序问题。再运行 philosopher，这次触发了实际死锁，但 LockDep 已经提前发现问题。

第二次运行正常退出，没有发生死锁。多运行几次，看起来都没有问题；压力测试即使跑 100 万次、1000 万次，也可能觉得程序正确。像大家写 Malloc 时，可能已经提供了自认为非常 stressed 的 workload。

但只要没触发那条罕见路径，问题仍会漏过。LockDep 每次运行都能检查到 ABBA，因为每次上锁都会记录本线程的上锁顺序，并加入图中。软件工程就是 Harness Engineering。第一类问题是死锁。
