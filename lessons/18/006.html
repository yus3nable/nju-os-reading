回到 sum++：正确性与性能

原片 00:14:31—00:18:28

Anyway，我们还是回到继续讲并发，我们今天就又回到前几次课讲的一个问题，一个问题是 sum++，其实 sum++ 在并发编程里，是一个非常常见的 pattern，对吧，虽然这是一个过度简化的例子，我创建一个 T_sum。然后我在 T_sum 里面，获得一把互斥锁，在持有这把锁的时候做 sum++，这样我无论有多少个线程。比如说我一共加了 1 万次，那我最后一定会得到 sum 等于 1 万，这个互斥是可以正确的，然后这个模型，或者说这个比较简化的 overly simplified 的模型。

在实际中的意义是什么呢？在实际中，你被锁保护的部分很可能是一个数据结构的操作，一个数据结构操作，比如说你可以往 buff 里面写一个东西，对吧，就比如说你 printf 的时候，你有两个线程在 printf 的时候，他们是共享这个进程的一个 buffer 的，然后这个buffer 当然它有一把锁。

课件中的 T_sum，依赖课程线程库中的互斥锁接口：

void T_sum() {
  mutex_lock(&lk);
  sum++;
  mutex_unlock(&lk);
}

然后锁上这把锁以后，它就可以往这个 buffer 里面写东西，那两个线程就可以并发的，甚至是并行的，当然这个锁其实是阻止了并行，并发的往 buffer 里面写东西，然后你的 stdout 就可以看到不被打乱的正确的数据，这是一种非常常见的 pattern。然后另外的还有 pattern。比如说你有一个 key value 的 dictionary。然后你的 dictionary 里面你可以更新这个数据结构，那你只要这个锁保护住，这个数据结构就是安全的，然后在之前前几次课的时候。

我们也给大家做过这样的实验，对吧，我们对比了好几个做 sum++ 的实现，比如说我直接甚至直接用汇编语言，直接用汇编语言实现一个原子的 sum++，最快，这是最快的，因为我都甚至都没有获取锁和释放锁的过程，然后也有这种 pthread 的锁。然后用我们自己实现的 spinlock。对吧，一个我手写的，我不断地试图去桌上拿钥匙的这样的一个过程实现的 lock。

然后以及我们强行进入操作系统内核的，使用 futex 系统调用的锁，然后我们看到看到了随着线程数的增长，这个实验是在我的这台树莓派上跑出来的，随着线程数量的增长，我们每一个操作所花去的时间，像进入操作系统内核或者是 spin，每一次 sum++ 的时间都在增长，而这显然是一个很糟糕的事。

对吧，就相当于我线程越多，我的性能还越差，然后你看到随着线程的增加，比如说 4 个 8 个 16 个，我们的 mutex 和 atomic，基本上性能就保持不变了，对吧，性能就保持不变了，至少它不下降了。但是不下降，这也是一个很糟糕的事，为什么呢？理论上说，如果你的算法设计的非常好，当我多一个 CPU 的时候，如果我要花一秒钟，那我两个 CPU 我就应该花 0.5 秒，四个 CPU 就应该花0.25 秒。对吧，因为我给它分配了更多的算力，我们的每一个 CPU 都是独立的，它都可以独立的执行指令。独立地响应中断，那一个真正好的实现就应该能够把 CPU 的计算力 100%的给用起来，而你看到一个操作在一个 CPU 是最快的，两个 CPU 就变慢了，四个 CPU 变得更慢了，然后八个十六个开始不变了，就饱和了就不变了。所以这根本就不能说是性能好，这可以说是一个性能很差，非常非常差的实现，因为你真正想要的是，随着你 CPU 数量的增加，你每秒钟能够完成的操作要增加，而Mutex Lock 最好情况就是，你到某一个地方就到顶了。然后再增加它也不能。不会有任何的性能损失。
