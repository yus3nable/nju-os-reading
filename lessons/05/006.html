第 05 课 · 程序和进程；fork, execve, exit

输出 6 行还是 8 行：状态复制与缓冲区

原片 01:01:55—01:12:11

fork 让一些程序很方便，也会增加理解难度。以前每年期中测验都会换个形式考这类题：读程序，写运行结果。今年是否还考，我没想好。不过现在可以先运行看看。fork-demo 中，for 循环的 i 从 0 到 2，每次 fork，再打印 Hello。

编译运行，数出来 123456，共 6 个 Hello。为什么？需要用状态机分析。先展开循环，从 i 等于 0、fork 开始。

i 等于 0，fork、打印；接着 i 等于 1，再 fork、打印；i 等于 2 时不再执行循环。展开前后语义等价。现在再运行，1、2、3、4、6、7。

#include <unistd.h>
#include <stdio.h>

int main() {
    for (int i = 0; i < 2; i++) {
        fork();
        printf("Hello\n");
    }
}

把程序改写成这样。初始没有变量，PC 等于 1，执行 i 等于 0 后，PC 到 2，i 是 0。再执行 PC 为 2 处的 fork，状态怎样变化？fork 复制状态机，又是与操作系统交互的系统调用，需要把操作系统也画进来。

它完整复制进程状态，得到两个 PC 等于 3、i 等于 0 的进程。若写 t 等于 fork，两个 t 会不同，但这个程序没有 T，不保存返回值。

现在可以把两个相同状态写成乘以 2，暂时忽略执行先后，一起推进。第三步 printf 后，PC 等于 4，i 等于 0，两份程序各打印一个 hello，共两个。执行第四步，把 i 设为 1，得到 PC 等于 5、i 等于 1，仍乘以 2。第五步又是 fork，复制后 PC 到 6，I 仍是 1，状态数量乘以 4，因为两个进程各复制一次。

第 6 步是 printf，再打印 hello 乘以 4。前面两个，后面四个，仔细推导得到 6。现在统计一下，却出问题了。肉眼数 1、2、3、4、5、6，确实是六个，word count 应该也没错。

通过 wc -l 统计却得到 8 行

结果却让人困惑，可以问 AI。回想 CrazyOS，putchar 会先写 internal buffer；fork 复制的则是全部进程状态。豆包开始没能复现 6，做了不少尝试。我觉得 flush 后应该可以，最后它确实复现出 6。

绕了些路，终于得到正确结果。strace 显示，真正向操作系统写出、让人看到的字符，经过 write 系统调用。像 CrazyOS 的 putchar 一样，在 write 和 printf 之间，还有库函数。

大家写程序时，有没有遇到过：程序随后 crash、发生 segmentation fault，但之前的 hello 正常显示？

如果忘记换行，segmentation fault 前却什么也看不到。

调试时明明确信 printf 执行过，却没有输出。比如再加 while (1)，程序已经进入死循环，没有停下来，说明前面的代码确实执行了。

即使确定 printf 执行了，之后 crash，仍可能看不到内容。因为 libc 有缓冲区。终端默认 line buffer，遇到换行才用 write 写出，类似 CrazyOS；标准输出是文件、管道或其他对象时，则更 aggressive 地缓冲，可能攒到 4kb 或 8kb 再一次写入，减少 write 次数，提高性能。刚才的模型将 printf 视为立即输出 hello，漏掉了这个行为。在得到 8 个的版本里，i 等于 0 时，两份 hello 都先写进各自缓冲区。

再次 fork，缓冲区中的 hello 也被复制。每个副本再 printf，就变成 HelloHello，共 4 份，最后得到 8 个 hello。计算机没有魔法，但系统复杂。说 fork 是完整复制状态很容易，要做对判断，却得知道系统各部分的精确行为。

我觉得，百万上下文的 AI 能超越人类。人花很久训练出的系统问题直觉，它只要看到全部代码、注意力足够好，也能发现复制了 buffer。这道习题展示了这种情况。

它也帮助理解 fork 的实际行为，以及操作系统里的复杂性。
