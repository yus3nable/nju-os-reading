最小二进制与 initramfs

原片 00:49:24—00:56:35

准备了一个最小 Linux 案例。前面讲过最小的 x86-64 二进制文件，它先执行一个 Syscall。

例如打印 Hello World，这里输出的是 This is a Minimal Binary。不需要额外库函数，直接用系统调用打印，再调用 Exit 退出。这就是一个最小的 x86-64 二进制文件。

minimal.S：

#include <sys/syscall.h>

// The x86-64 system call Application Binary Interface (ABI)
//   System call number: RAX
//   Arguments: RDI, RSI, RDX, RCX, R8, R9
//   Return value: RAX
// See also: syscall(2) syscalls(2)

#define syscall3(id, a1, a2, a3) \
    movq $SYS_##id, %rax; \
    movq $a1, %rdi; \
    movq $a2, %rsi; \
    movq $a3, %rdx; \
    syscall

#define syscall2(id, a1, a2) syscall3(id, a1, a2, 0)
#define syscall1(id, a1)     syscall2(id, a1, 0)

.globl _start
_start:
    syscall3(write, 1, addr1, addr2 - addr1)
    syscall1(exit, 1)

addr1:
    .ascii "\033[01;31mThis is a minimal binary.\033[0m\n"
addr2:

可以编译它，得到 64 位、x86-64 的静态链接文件，即 Static Linked。在我的电脑上也能运行，为什么？

我的电脑用的是其他体系结构，加载器知道系统中有 QEMU，运行不同体系结构的二进制文件时，默认会进入模拟器。它模拟执行 Move 等用户态计算、内存指令，遇到系统调用则直接调用宿主操作系统的系统调用，这是个有趣的特点。问 AI 怎样控制第一个进程，它大概会给出这样的代码，先准备 initramfs。这个词表示初始的内存文件系统。第一个进程仍然要来自文件：还记得 man 2 execve 吗？第一个参数是 pathname，指向系统里的文件。

execve 可以执行 a.out、/bin/ls、/bin/bash，运行程序必须先有文件。但内核刚启动时，还不知道文件系统在 U 盘、磁盘还是别处，最早期的文件就放在 initramfs 中。

Makefile 的启动与编译片段：

run:
# Run QEMU with the installed kernel and generated initramfs
    qemu-system-x86_64 \
      -nographic \
      -serial mon:stdio \
      -kernel build/vmlinuz \
      -initrd build/initramfs.cpio.gz \
      -machine accel=kvm:tcg \
      -append "console=ttyS0 rdinit=$(INIT)"

minimal: minimal.S
    $(CROSS)gcc -g -S minimal.S > minimal.s
    $(CROSS)as minimal.s -o minimal.o
    $(CROSS)ld -o minimal minimal.o

initramfs 可以自己构建和控制。在 Linux 上用 apt update 更新软件包时，有时会遇到很慢的 update-initramfs，其他操作都快，唯独它慢，是因为某些软件更新后，还需要把新版本重新打包进最初的文件系统。

里面要包含第一个加载的程序。知道这个概念，就可以让 AI 帮忙 build initramfs，也可以要求它提供打包脚本。

Makefile 的打包片段：

initramfs: minimal
# Copy kernel and minimal from the host system
    @mkdir -p build/initramfs/bin
    sudo bash -c "cp /boot/vmlinuz build/ && chmod 666 build/vmlinuz"
    cp minimal build/initramfs/init

# Pack build/initramfs as gzipped cpio archive
    cd build/initramfs && \
      find . -print0 \
      | cpio --null -ov --format=newc \
      | gzip -9 > ../initramfs.cpio.gz

它是 fs，所以可以构造目录树，放入 /bin 等任何需要的内容，bin 中可以有 bash、init。Linux 代码硬编码了一系列路径，会在 initramfs 中依次尝试，例如 /sbin/init、/etc/init；前者不存在，就试后者。

之后再试 /bin/init，直到某次相当于 execve 的操作成功，第一个进程就被加载进 Linux 了。这个过程完全可以控制。这里的代码把目录树用 cpio 归档，再用 gzip 压缩，生成 initramfs.cpio.gz。

QEMU 启动时，-kernel 加载内核，-initrd 加载打包好的 initramfs。还可以给内核传入 rdinit 等于 /init，override 默认的硬编码路径，指定第一个进程为 /init。AI 解释得很好，现在 make run，就进入 QEMU 模拟器运行。

这里用了 -nogrephic 选项，没有 QEMU 图形界面。启动比大家的 Linux 慢很多，因为是在 arm 上模拟 x86。日志显示 Linux version 6.1.0、amd64，这是我从另一台电脑复制来的内核镜像。

它运行在 QEMU standard pc 上。大家见过 Linux 启动时消息不断滚动，某一刻屏幕闪一下，字体、分辨率突然正常吗？启动分为几个阶段，可以看看这个 minimal 加载时的情况。

内核运行四点八秒后，打印 Run /init as init process，符合刚才指定的行为。接着打印 this is a minimal binary，和直接运行 minimal 时相同，都是红色字，来自刚才的汇编。执行几条指令后，程序调用 exit，即 syscall exit。在普通操作系统中，这个进程退出没有问题，因为还有其他进程；但 init 退出，内核就会罢工，出现 kernel panic、Attempted to kill init，整个操作系统挂掉。

这里还有 call stack，系统已经挂掉。这也证明，我们确实控制了 Linux 加载的第一个进程。
