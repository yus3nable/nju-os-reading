fork 之后，文件和偏移量怎样复制

原片 00:59:14—01:07:16

但有一点是在操作系统课上告诉大家的，看起来简单的设计，在实际的操作系统里面，就会带来一些不小的麻烦，比如说我们刚才说，文件是一个字节数组，那比如说我现在有一个 log.txt，那么没问题，如果你们打开了一个文件。比如说你打开了这个 log.txt，现在是三号文件描述符，一，你写一个三号。然后你再写一个三，二，还是写一个字节，那你会在这个文件里面写下什么呢？会先写下一个一，再写下一个二。对吧，这个行为大家都是非常清楚的，如果你要写一个文件。你可以顺序地写。你往一个文件里写 hello。

再写 world，你会在那个文件里得到 helloworld，没问题，下面，你会想到 OK，那假设，假设文件就是一个字节数组，你在操作系统内核里面实现的时候，也真的是给它分配了一块内存，那我的 write 系统调用，也就是说，我的操作系统里面有个这样的 file 的结构体。然后它就有一个 buff。对吧，buff 是指向它的，然后我可以有一个 offset，offset 可能指向这。所以如果我执行这个 write 的时候，我会找到根据三。对吧。我们的那个地址空间。

0、1、2，好，根据我进程的这个文件描述符空间里面的 3，指向找到这个打开的文件，然后我知道 offset 我会写一个 1，然后我的offset 就会往后加 1，对吧，这个行为大家是可以接受的，这样下一次再写 2 的时候我就会写到后面的位置，麻烦是什么呢？麻烦是我在这个时候，我可以对进程做 fork，还记得 fork 是干什么的吗？fork 是把整个进程完整做一个拷贝，那所有的内存和寄存器的拷贝都容易。

write(3, "1", 1);
write(3, "2", 1);

对吧，内存和寄存器完全相同，除了父子进程那个 return 做返回值的那个寄存器，一个返回了他的子进程的 PID，一个子进程直接返回了 0，除此之外，在用户态，就是这个进程自己看来没有任何的区别，但在操作系统里就麻烦了，我有两个进程，那我能不能，现在是一个问题，如果我这样了，或者说我这样，我先写一个 1 对吧。然后我再 fork。然后我再写一个 2，那在这个时候，就有两个进程写 2 了。对吧，看起来这是一个顺序的程序，先做这个再做 fork。但 fork 完了以后。

世界上就有两个一模一样的进程，甚至我都不区分他到底谁是父亲谁是孩子，他们都要往这个进程里面写一个字符，那问题是，他们应该覆盖，还是应该写 2，这个程序执行完了以后，你应该看到的是一个 2，还是看到两个 2？对吧，这件事情其实是操作系统设计者的自由，我可以在复制这个进程的时候，我在执行 fork 的时候，我把这个 file 也拷一份。对吧，我把 file 也拷一份。然后 offset也拷一份，offset 也拷一份。好，那这两个 offset 都在这。那我就会得到一个 2。

我也可以在进程的这个 IO 空间上，我现在又有另外一个进程了，对吧，我一个 p2，这是 p1，好，那我把 p2 的这个 3，我可以做一个浅拷贝，比如做一个指针指向它，这样，我第一个进程写，写 2 的时候，它会写一个 2。然后这个 offset 就往后移了一个然后第二个进程再写的时候，我又写一个 2，又往后移了一个那你们觉得操作系统的设计者会采用哪一种方案呢？对吧，这才是现代软件系统，就是你任何，你实现一个稍微复杂一点的人的系统，都会面临的难题。fork 看起来很优雅。

对吧，我就是做一个复制，我讲的时候，你们可能没有意识到这样的复杂性，但麻烦的是，你一旦有这样的复制，在一个进程持有的所有的资源，你都要考虑它复制以后的语义是什么，对吧，它复制以后到底什么行为，那所以每一个 fork，就 fork 它会和每一个系统，几乎每一个系统调用，或者每一种操作系统的对象都会产生关联，带来巨大的麻烦。所以甚至有人已经一直在，在吐槽这个操作系统课，你们再也不要教 fork 了，这个 Paper 叫 A Fork in the Road，还是不少很有名的大佬写的文章。

我觉得挺有意思的，大家也可以去读一读，这意味着软件系统的每一处设计，都要非常小心的考虑和其他部分的交互，那我们 UNIX的设计者选的是哪一条途径呢？它会让 P1 和 P2 写出两个 2，它为什么要做这个设计呢？答案已经在这了，这可能是个 log.txt。

write(3, "1", 1);
fork();
write(3, "2", 1);

对吧，它希望的是如果我的父子进程，共享一个文件的时候，并且我以一个追加的方式写入的时候，我能够，对吧，我就是写文件的时候，我不会丢掉一个数据，或者让两者的数据随意的互相覆盖，因为覆盖一般来说都不是你想要的，对吧，程序员不希望父子进程在写的时候，能够互相覆盖对方的结果，甚至我先，相当于我先来我先写的我就会被后来的人给覆盖掉，这可能是一个程序员意义上非预期的结果。所以 UNIX 的设计者选择了把 offset 放在这儿做一个浅拷贝两个指针指向它，如果你想要得到一个深的 offset 独立的拷贝的话。

你需要把这个文件再打开一次，然后这也是 fork 它做很多默认行为带来的，它默认的时候父子进程所有东西都是继承的，这也带来了很大的麻烦，而 Windows 的 Handle 就设计的更好一点，它默认的时候 Handle 是不继承的，它和 UNIX 正好是相反的，然后你可以在创建一个 Handle 的时候，设置这个叫 bInheritHandles，或者你在程序执行到某一个点的时候，你可以选择这个 Handle，未来在创建 Spawn 一个新的进程的时候，它会要被继承下来。

所以 Windows 做了一个最小的权限原则，这其实是一个软件工程上面更好的设计，为什么呢？你想，如果你的父进程持有了一个非常敏感的文件，持有一个文件描述符，然后我在创建一个子进程以后，我可以通过 execve 去执行另外一个程序，如果我不小心忘记把那个敏感的文件描述符给关掉，那个子进程就有这个文件的访问权限了。所以这就是很危险的事情，我把一个不该让另外一个人访问的东西，给另外一个人访问了，它可能有一个 bug，甚至不是一个安全的漏洞，但就导致了它可能误写了一个系统中的文件。

所以在后来 Linux 引入了一个叫 O_CLOEXEC，来当作使得一个文件描述符在，在子进程创建的时候它不被继承，所以你看到操作系统演化到今天，它的 API 实际上也是千疮百孔的，不过好消息是，AI 其实对这些行为理解的都非常好。所以你们需要的是在遇到真实的问题的时候，能够意识到比如说这个地方有一个潜在的复杂性。然后你怎么样 reason about 这些程序的执行，这样就可以了，你有这个能力就 OK 了。好，这就是文件描述符相关的 API，我基本上讲清楚了。
