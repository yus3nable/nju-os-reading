第 02 课 · 应用视角的操作系统

观察真实应用程序

原片 00:58:51—01:27:55

操作系统上的所有程序都和 minimal 一样，共享完全相同的一套 system call。眼前的桌面、能显示图形的终端、窗口管理器，以及刚才打开的 vscode，对操作系统来说，所有运行进程看起来都是一样的。当然，调度策略可能有区别，某些进程优先级更高，资源会向它们倾斜。有时间也会讲 nice 机制：“越好”的人得到的 cpu 越少。

操作系统上的应用程序

从概念上看，所有这些程序都和刚才最小的 minimal 一样。先看看世界上有哪些应用程序。大家马上会想到日常使用的工具：没有 VS Code 的 Copilot、Cursor，可能就没法编程了。我现在觉得，没有 Claude Code，自己已经不会编程了。不过我觉得今天的编程还没有进化完全。我很少调前端，也很少 vibe code 前端，这次为了上课，被迫调了一下。

直接使用的 Applications

这是我调的网页前端，样式还只是勉强能用，之后会继续优化。框架用的是 Next.js，它有一个很好的特性：修改代码库后，效果立即反映到页面上。Claude Code 改完 CSS 文件，下一秒就能看到展示效果。

网页课件的浏览界面

调起来很方便。最初页面只有文字，没有任何样式。我先描述想要怎样的幻灯片，它做了一个，但幻灯片之间的间隔不对。我让它把间隔拉大一点，按下回车，几秒钟后就修好了，能及时看到程序最终的样子。

调整窗口尺寸后的页面布局

大概三分钟就调好了。后端编程好像还做不到这样：开发 GCC、Clang 时，我最多能要求 Claude Code 每次改完都运行测试用例，再看有没有通过；没通过，就让它继续修。平常用的 GCC、Clang、Node.js、GDB，今天上课也一直在用；还有更应用层的软件，比如直播推流的 OBS、看电影的 VLC、刚才打开的 Firefox。大家可能有点吃惊，但这些确实都和 minimal.S 一样。今天这节课就是想让大家理解这一点。不过，整个应用生态并非只有一个程序。

Coreutils 与系统工具

从应用视角看，操作系统是一组 API，今天看到的接口就是系统调用指令：x86 的 syscall、RISC-V 的 ecall，或者 SVC。应用程序只能看到这些接口，但上面还有许多层程序。直接使用 API、能独立工作的一组工具，叫作 Coreutils。我建议大家至少和 AI 聊一聊。以前上课，我总鼓励同学去官方网站读软件手册。

手册会列出 Coreutils 有哪些工具，比如 LS 这样基本的命令行工具，Claude Code 也经常调用。可以在网站上遍历 Coreutils、Binutils 的工具集；今天有了 AI，它也会耐心解释。

AI 列出的工具类别

Coreutils 有常用的 ls、拷贝文件的 cp、移动文件的 Move，以及打印文件的工具。grep 呢？grep 是单独的项目，不过 BusyBox 也会带一个 grep。还有各种系统工具。对其中任何内容感兴趣，都可以继续问。比如刚才用 GCC 编译，再用 LD 链接；LD 这个 Linker 就属于 Binary Utilities。要知道它还能帮忙做什么，现在不必自己寻找官方文档，可以给 Claude 加一个能读网页的 Skill。模型对现有工具，特别是开发者广泛使用的工具，了解可能比我还多。它读过文档和开源项目里的各种用法，而我只有自己的理解。

Binutils 的工具与用途

我通常需要时才回去查手册，大模型则已经看过这些资料，问它就能马上得到 Binary Utilities 的用途。计算机系统基础课用过很多，比如分析 ELF 文件，此外还有一些功能。

二进制分析工具的典型用法

比如 Strings 能从二进制文件中提取可打印字符串，Size 能查看文件中各部分的大小。这些工具在早期 Unix 时代就已经存在。今天学东西，不必像以前一样，费力对着大量英文手册。大家面对厚手册，第一反应可能是明天再读，到了明天又推到后天，最后一直没读，这很正常。AI 提供了一个好的起点，只要对内容有兴趣，现在就能开始做事。

这些工具按层次组合。在各种 utilities 之上，还有许多后台 daemon。比如 U 盘插到电脑上，桌面会自动创建一个图标。

后台 daemon 与图形多媒体服务

点开图标，就能看到 U 盘内容。但只有操作系统、没有其他程序时，插入 U 盘不会有这种反应。操作系统世界里看到的一切，都是某个程序和操作系统交互后完成的。查看当前系统的所有程序，会发现数量很多：比如 bluetoothd 管理蓝牙，cron job 管理定时工作。

可以设置每天或每几天做一次全系统备份。刚才说的 U 盘挂载，则由 udisksd 完成，d 表示 daemon，它在后台工作。后台还有许多服务，比如窗口管理器。虽然能在前台看到它，它也属于提供服务的程序。这些程序大多数时候独立工作。

进程树中的 udisksd

有时它们也和工具程序交互。在许多这样的程序之上，才是我们直接使用的 application。它们都是和 minimal.S 一样的普通程序，可以直接请求 OS 的 API，比如 SYS_exit，也可以请求操作系统与某个 daemon 通信。要显示图形界面，程序不会直接请求操作系统在 XY 坐标画一个 Pixel。如果每个程序都以为自己拥有整个屏幕，直接占用屏幕，就会乱套。

各个程序都直接向屏幕输出，最后怎么管理？为此，操作系统之上又构建了多层抽象。比如我现在的窗口管理器底下有一个图形层 Wayland，上面有 Sway。应用程序想显示窗口时，会通过 GTK 这样的库，把显示请求交给 Sway，Sway 再交给 Wayland，最后由 Wayland 和操作系统通信，把图形显示出来。

这是一个漫长的过程。年复一年，有些软件被创造，有些被淘汰，很多年后才有了今天容易开发应用的环境。有各种工具程序，Claude Code 日常也经常调用；还有后台服务，支撑网络配置、磁盘配置、自动更新等。刚才说它们都和 minimal.S 一样，用 file 查看，minimal 是一个 ELF 的 64 位程序。

应用程序与 minimal.S

因为这台树莓派是 ARM 架构，所以看到的是 ARM；大家的机器也可能是 x86-64。系统里其他程序也一样，比如 /usr/bin 下的 as，也就是 assembler，它也是 ELF64bit 的 Executable、ARM64 程序。所有程序都是同一类东西，但复杂程度不同，能打印 Hello World 的 minimal 就很小。要了解二进制文件，除了用 objdump 查看，有没有想过自己 hack 这个文件？我们来试试，告诉 AI，这是一个 minimal 的 binary。

minimal 的反汇编

这是一个 binary file，change its return value，看看它会怎样处理。它先运行程序，得到返回值 1，再调用 Coreutils 里的工具。首先用了 hexdump，它可以把任意文件，包括文本文件的实际字节序列打印出来。

请求 AI 将返回值改为 42

先运行程序并查看原始字节

也可以直接在命令行运行 hexdump。AI 把多种工具组合起来读取文件，找到 Hello World 所在的位置。想了一会儿，它又找到设置返回值为 1 的指令，刚才说 return 指令，实际是 mov 指令。它还能读懂 arm 机器码，这个我自己都读不懂。

AI 第一次提出的字节修改

它知道要改成 42，写出一条命令，我允许它运行。接着它又试了一次，发现做错了，不过应该能改回来。计算机世界没有魔法：汇编或 c 代码会变成二进制文件。

第一次修改后的返回值是 28

这个 binary file 就是字节序列，每个字节都对应程序中的某个部分，有合理的解释。实际修改这些字节，就能改变程序，也能把它改对。

修正为 ARM64 的 mov w0, #42

这次修对了，我很吃惊。直接让它用命令行工具 hack binary，它就完成了。我有点危机感，感觉很快就可以不用上课了；它只是暂时没想到还有这样的操作。

修正后验证返回值为 42

这让我想起以前的经历。刚才展示的二进制逆向，是学完计算机系统基础课后就能做的事。几十年前，五块钱能买一张游戏光盘。我在大富翁4 里发现一个隐藏的神秘文件夹，里面有一个神秘游戏，但难度太高。后来发现一个 GAME.SAV 文件，里面有一串神秘的 0x00，0x00，0x01，0x00。

它们代表进度。我 hack 这个 binary file，把一个字节从 00 改成 01，类似刚才改返回值。当时有个 01，把它改成别的值。42 是多少，28 吗？

第一次二进制逆向的经历

改成另一个数字，程序行为就变了。这是我很早以前第一次做二进制逆向。之后很久没有再做，直到接近读 PhD 时，才又做过一点。今天的世界变了，我觉得是 curiosity is all you need：知道世界上有什么，知道 syscall 上面有层层工具，就可以问 AI 有哪些工具。

Curiosity is all you need

再知道工具组合起来能做什么，就可以让 AI 带着做。我觉得，只要人能做成的事情，AI 都能做。想象回到小时候，告诉那时的自己：hack 存盘文件的方法，也能用来 hack Windows binary，任何 Windows 可执行文件都可以。嫌文件太复杂，也能像今天用 AI 一样，一点点分开研究、弄清楚。在 coding agent 辅助下，即使刚来上操作系统课的初学者，刚才那样的逆向能力也几乎和顶尖人类没有差距。

资深、熟悉 ARM 指令集的人当然会觉得这很简单，但 AI 做得很快，知道什么时候调用什么工具。代码可以自由组合、无限复用；有一个好工具，AI 马上就能学会用，只要给出正确的 prompt。我觉得世界发生了很大的变化。

使用 trace 打开应用程序

操作系统课也一样。相比 system call、file、file descriptor 这些概念，我觉得教大家用工具的思维更重要。再回到今天的主题：操作系统里的应用程序都和 minimal 一样，能证明吗？作为老师，我在这个领域有一定知识储备，也不会故意用错误的话误导大家，否则违背师德师风，会被开掉。但不能听到老师这么说，就觉得事情已经确定了。还可以追问：真的吗？能不能解释得更清楚？下一步就是打开真实应用程序，观察它是否确实通过系统调用完成事情。这里会用到 trace 工具。先写一个空程序，用 gcc 编译，和大家在计算机系统基础课做过无数次的一样，生成合法的二进制文件 a.out。

运行成功后，平常可能就结束了。但系统工具 strace，也就是 system call trace，可以打印程序运行中的系统调用序列。还有 library call trace 等其他 trace，也可以写自己的 trace。

gcc 的系统调用记录

现在还没看到全部调用，需要加上 -f 选项，把所有创建的子进程一起追踪。日志就更长了，能看到 gcc 开始读写文件、操作临时文件。

编译结束后删除临时文件

它创建临时的 .o 文件，处理完后，再用 unlink 系统调用删除。这样就能在一定程度上验证编译器的行为。教科书说 gcc 会经过编译、汇编、链接，但这些步骤是调用外部工具，还是全部自己完成？实现上两者都可以。可以在内存里准备好一切，最后直接输出 a.out；也可以启动外部进程处理。strace 展示系统调用序列，让我们知道实际发生了什么。在 AI 之前，我会这样讲：GCC 编译最简单的程序，执行了 2249 个系统调用，log 这么长，大家肯定不愿意逐个读。怎么办？先假设没有 AI，同学们听老师介绍 strace，知道它能打印任意二进制程序执行的系统调用序列。

完整日志包含 2249 行

打开日志，可能看一眼就关掉，因为看不懂，干扰项又多。这时 Unix philosophy 就能发挥作用：任意文本都可以经过一个工具，删除不需要的内容，得到另一个文本；再交给下一个工具继续过滤，或调整格式，让它更易读。以前我会这样做：如果对文件操作没兴趣，就把当前区域的全部文本通过管道交给 grep，去掉包含 AT_FDCWD、Current Directory 的行。原来的 2249 行经过 filtered，只剩 1700 个。

过滤文件相关调用后的日志

剩下 1700 个调用。如果对某一种感兴趣，可以继续 grep，比如 execve。它是启动另一个程序的系统调用。从中能看到，GCC 确实在尝试启动其他工具，比如查找汇编器。

筛选 execve 观察被启动的工具

一个路径没找到，就换下一个，直到找到并执行汇编器。这是以前的做法。今天也可以直接告诉 Claude Code，让它来分析。最近的模型很理解 Unix philosophy，知道怎样从环境中寻找相关信息。

让 AI 跟踪 gcc 及其子进程

它可以沿路径调用工具或直接读取文件，也能动态生成脚本。看，它开始用 strace -o strace.log，把输出更安全地写进文件。

AI 使用 strace 将结果写入文件

它接着分析 strace 输出文件里的各种系统调用。先让它继续分析，我们看下一个例子：图形编辑器，比如 VSCode。

编译器和图形编辑器的观察方法

这里用相对简单的 xedit。窗口有点小，但能看到它是一个文本编辑器，可以输入文本、保存文件，也支持键盘和鼠标操作，功能上和 VSCode 一样。

xedit 文本编辑窗口

收到键盘、鼠标操作后，程序可以执行自己想做的事情，具体行为由应用程序决定。同样可以记录它的调用。随便操作几下，再退出，就得到一个 xedit.log。

xedit 的 recvmsg 与 poll 调用

以前我只能分析日志来解释：xedit 虽然有图形界面，也不会逐像素直接画到屏幕。所有图形程序都直接绘制，屏幕就乱了。它采用消息通信，所以日志里绝大部分调用是 recvmsg、poll，涉及发消息和收消息。它会告诉另一个有权管理系统所有窗口的程序，在自己负责的窗口某个位置画什么，或者接收消息，得知窗口哪个位置被点击。

这些位置都是相对的，窗口从一个地方拖到另一个地方也没问题，底下的渲染器会绘制到正确位置。今天也能直接让 AI 读日志。这边的 gcc 分析终于完成了，它做得比我课上讲得好：我最多分析日志，再花五分钟在黑板上写，它连图都画好了。图里有进程父子关系，GCC 怎样调用编译器前端、汇编器、链接器，分别用了什么系统调用。日志都在上下文里，还能继续追问。
