编译与优化

原片 00:29:17—00:41:10

什么是程序已经讲清楚了一部分，当然还没有百分之百讲完，留了一点内容。现在可以谈编译器了。编译器把一个 .c 翻译成 a.out 之类的文件。

编译后程序的 CPUState

这里说的是广义的编译器，包括汇编器和链接器，把 .c 变成 a.out。a.out 的执行模型，就是计算机系统基础课里，指令操作 memory 和 register 的模型。早期的 C 语言编译器没有今天这么复杂。今天让大家看 GCC 源代码，可能都会拒绝。那时的编译器更像今天的 transpiler。用过 JavaScript 的同学应该见过很多 transpiler，它通过简单的语法变化，把一种语言转换成另一种形式，比如把新版本 JavaScript 变成旧版本 JavaScript。

最早期的编译器把语句逐条原样翻译成指令。后来大家发现，编译器可以改变程序的内部行为，未必需要原样翻译每条语句。最早在 70 年代，乃至更早的 60 年代，大家还没意识到这一点。当时的想法是，只要把语句原样翻译成指令，程序就一定等价；只要编译程序没有 bug，就像解释器或大家写的 NEMU 模拟器没有 bug，事情就做完了。但还有别的可能，比如写一个 X 等于 1 加 2 加 3。

如果后面不再使用 X，这就是死代码，可以删除。那么编译器究竟可以做哪些优化，哪些不能做？上完这节课，大家就可以回答这样一个问题：给定 a.c，考虑世界上所有可能的 a.out，也就是所有可能的 Binary 组成的集合。这个集合在理论上完全可以定义；不限制大小可以有无穷多个，限制某个大小以内则是有穷的。gcc -O0 会生成其中一个 a.out，假设它正确；gcc -O2 也会生成一个正确的 a.out。能不能定义这个集合的一个子集，包含所有正确的指令序列？问题有点抽象，看具体 examples 就有感觉了。

接着把结果写到寄存器里。这样写当然可以，但人看到代码，往往会想直接写 return 25——如果我没算错的话。没有必要写那么多指令，写成 mov 什么，25，再 return，就应该在预期的正确程序集合里。

直接返回 25 的汇编写法

写成 return24，就不在这个集合里了。编译器允许做什么、不允许做什么？先看实际结果。我准备了 O0 版本，可以看到它已经做了优化，常数表达式会直接计算。再看 F4，不需要完全看懂汇编，大致看一下：f4 中有 x = 1，先把 1 移给 W1 寄存器，再用 store 写给 X。这样的写入做了两次，而经过编译优化以后，store 只剩一条。

优化后的单次写入

编译器知道，对 X 连续做两次 x = 1，可以消除其中一次，效果不变。今天也可以直接让 AI 解释。它像一个人在工作，先列文件，再逐个读，重复刚才我做的事情。刚才 O0 版本先算出了常量 24。

但加 1 的操作保留了下来；O2 则直接算出 25，八条指令变成两条。这次上课用的是这样的树莓派。大家可能没听过小霸王学习机，那是我的童年回忆，长得和它几乎一样，不过大很多。任天堂的 switch，大家可能更熟悉，很多同学可能有。

switch 插卡带就可以运行游戏，我家小朋友也会用。我小时候的学习机也一样：当时不能卖游戏机，必须叫学习机，里面内置打字、basic 编程等学习软件，插上卡带就能运行游戏。这个树莓派是 arm64 系统，与手机、我现在直播推流的苹果电脑，以及应该每位同学的手机，采用相同的 arm 架构。它的汇编和大家学过的不同。计算机系统基础学的是 RISC-V 还是 X86？X86。有 RISC-V 汇编课吗？我觉得应该把计算机系统基础全部改成 RISC-V。大家可能不熟悉眼前的 LDP、LoadStore 等指令，但今天只要学过任意一种体系结构，知道指令的大致类型就可以了。比如 Move 有的可以访存，有的移动数据，另外还有算术指令、系统指令。在 X86 或 RISC-V 学过这些概念后，遇到 Arm，就可以让 AI 用 X86 的方式解释。这里不演示了，直接问它，能否把刚才几段汇编用自己能理解的 X86 方式解释，基本都能解释得很好。

再回到编译器。状态机执行时，许多操作只改变内部变量的数据。可以这样想：假设程序会中止，也不打印任何数据，编译器应该把它优化成什么？空程序。无论程序多复杂、做了多少事，只要永远不向外输出任何东西，理论上都可以全部优化掉。唯一不能随意优化的是一些特殊语句，比如编译器看不到其行为的外部调用。这是针对今天的编译器而言。

比如编译一段调用 printf 的代码，printf 以后才链接进来，编译时就不知道它的行为。它可能用汇编语言写成，执行后甚至可能让整个世界毁灭。计算机把电平、数据电信号送到外部时，后果可能无法预知。一个电信号就能驱动物理世界的变化，可能把核武器发射出去。

这些不能随意优化的外部调用，行为对编译器不可见。已知行为的内部操作，原则上可以改变；对外的行为必须保持原样。比如 printf x，把当前 x 变量的值作为参数传给 printf。

如果这次运行时 x 等于 1，传到外部的值就必须等于 1。按原程序解释执行会输出低电平，编译优化以后也必须输出低电平。编译正确，就是在任何输入下，输出序列都完全相同。这句话含义丰富，我说得也不够严谨，以后学编程语言的形式语义时会再学。暂时没完全反应过来也没关系，有个大致理解就可以了。这也说明了为什么要用状态机视角理解操作系统。编程语言学科诞生之初就一直在用这个视角，我觉得它甚至不应该到这门课才第一次出现：语言和机器都是这样构建的，天然存在这种映射。再往前想一点，还能发现更多问题。编译正确性不会考，大家听过即可。
