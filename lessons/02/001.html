第 02 课 · 应用视角的操作系统

什么是程序：解释执行与函数调用

原片 00:00:00—00:29:17

今天讲应用视角的操作系统。上一节课回顾了操作系统的发展历史，我相信已经在一定程度上说服大家：在人工智能时代，仍然需要坐下来学好操作系统。这个学期最重要的视角是，从应用程序出发，把操作系统理解为一组 API。今天再用一节课 overview 一下这个视角，主角是程序，先讲操作系统上程序的解释和编译。

操作系统上的程序

回顾操作系统的定义：operating system is a body of software in fact that is responsible for making easy to run programs。它让程序共享资源、和设备交互，也提供各种其他能力。操作系统提供的 API 能完成许多只在 C 控制台里用 printf 做不到的事情。了解这些 API，就能用操作系统做更多事情。我觉得值得学一学：知道操作系统可以做什么以后，就可以指挥 AI 调用这些 API，把事情做起来。

人工智能很强，但没有合适的 prompt，它就什么也不动。今天会把什么是程序讲清楚，精确到程序的每一个 bit 都是 well defined 的。大家也会第一次接触计算机程序的形式语义；我不专门讲这个概念，但会让大家感受到它的含义。上节课忘了说，整个学期使用的编程语言仍然是 C。

把 C 程序转换成 SimpleC

更高级的编程语言，其绝大部分内容都和操作系统无关。它可能在操作系统之上包装一层库函数，也有其他设计目标。比如写前端时，JavaScript 的很多设计围绕整个 DOM tree 的处理，TypeScript 有自己的类型系统，这些和操作系统的关系都不大。操作系统处在硬件与软件之间，我们要选一个尽量接近它的编程语言。汇编语言可以直接和操作系统交互，但又没法用来开发应用程序。我们选择的语言介于直接写机器代码的汇编和非常高级的语言之间；再往上，AI 可能只需要一句自然语言。C 离机器近，又能写应用程序，最早的整个应用生态也是用它构建的。大家入学第一个学期学过 C++，当然，当时学的相当于带 struct、有一点面向对象的 C 语言。

大家有没有这样的感受：C 语言提供了方便的写法，可以写 x= y + z + w 这样的长表达式，也可以把函数调用放进去，但任意复杂的表达式总能改写成每行只做一小件事的形式。比如先写 t1 = y + z，再写 t2 = t1 + w，最后写 x = t2。

条件判断或函数调用参数里的复杂表达式，都可以这样提出来。处理以后，任何 C 程序都能写成每行只做一小件事的形式。每次单步执行一条这样的语句，理论上就能对应到几条指令。大家在计算机系统基础课写过全系统模拟器：CPU state 包含每个寄存器和每个内存单元的值，根据 Program counter PC 取出该位置的指令，译码后执行。比如一条指令把两个寄存器的值相加，存回另一个寄存器。

C 语言里绝大多数程序也基本如此。有了 Program counter，也就是 PC，就像 GDB 高亮的那条语句，我们知道它要做什么，再执行它。分支、循环也可以这样处理。我总能把 C 程序改写得足够简单，让每个条件判断都直接使用一个布尔变量；复杂计算可以提到外面。Program Counter 到达判断的位置时，从 X 变量中取值：值是 true，就把 PC 跳到这里；值是 false，就跳到另一个位置。

这种语法的行为和跳转完全一样，while 循环也对应带条件的跳转。解释执行时，while 和 if 的处理方式相同。这就说明了为什么我说 C 语言是一种高级的汇编语言：改写以后，所有语法成分都能用几条明确的汇编指令表示，基本可以原样把 C 代码翻译成汇编代码，C 语言编译器也就很容易构建。

换成 JavaScript 或 C++，情况就复杂了。比如 C++ 通过 pointer 调用 foo，它做的事情可能比想象中多：foo 可能是虚函数。大家还记得虚函数吗？忘了也没关系，只要知道，很难立刻判断这样一行代码会翻译成怎样的指令序列。对象里有一个 vtable，也就是函数表。如果 foo 是虚函数，通过 pointer 调用它时就需要查表。

这种编译行为比 C 语言编译器复杂得多。C 的好处是，我们几乎总能直接把这样的 SimpleC 翻译成相应的汇编语言。

程序能写成这个形式，也就可以让大模型来帮忙。理论上可以写一个编译器，而且确实有人写过。我给了 CIL 的链接，这是一个老项目，有好几十年了吗？没有二十年，十几年了。它能把符合 C99 标准的程序编译成更简单的 C 语言，应该是用 OCaml 写的。我们以前做 research 时也用过它，把 C 改写成简单形式，再做程序分析、编译或其他事情。

今天可以让大语言模型帮忙。我想在课上讲怎样把 C 翻译成 SimpleC，又不想专门写编译器，写编译器太复杂。那就让模型先写一份大家熟悉的 Hello 代码。

myprintf 与 main 的代码

这是一个典型的 C 程序，也是操作系统上的典型应用程序。今天要说明的是，大家看到的所有应用程序，包括 VS Code、刚才打开的 Claude Code，以及显示这个桌面的程序，都和这样的 Hello.c 没有区别。

print_str 与 print_num

从学习编程的第一课起，大家就相信这一点，但可能直到今天的操作系统课，才会看到复杂程序怎样和操作系统交互。一会儿我会打开一个这样的程序。眼前这个程序当然也能翻译成 SimpleC，我们可以单步调试看看。

GDB 停在 main 的第一条语句

单步调试时，每条语句都很简单。putchar 会打印一个字符，这里先跳过。再进入后面的 print_num。平时不会这样写程序，因为显得冗余，但确实可以把每一行都改写成只做一件事、一次赋值，就像大家在体系结构或计算机系统基础课学过的指令集。printf、putchar 先不看。这样的改写意味着什么？

断点与 print_num 的单步执行

上次课说过，everything is a state machine。计算机硬件根据 register 和 memory 的状态执行指令，发生状态迁移。SimpleC 程序也是这个模型：一个 .c 程序执行一条语句，就进入下一个状态。看 gdb 的运行，好像它在解释执行刚才写的程序，尽管实际运行的情况不同。那能不能把程序的状态和迁移都打印出来？

以前做这件事挺费事，今天有了 AI，发现比想象中简单。我准备了一个小脚本，上面这个 prompt 是我写的，其余部分由 AI 生成。我一眼都没看，只是后来为了上课效果稍微改了一下。AI 告诉我用 gdb -q -x 这样的命令运行任意程序，比如运行 Hello。运行时它就［听辨不清，00:11:38］，不知道在干什么，还有一个小 bug，最后 crashed 了。我感觉它的 error handling 没做好，但运行完以后能得到一个 trace.log。

跟踪脚本运行时的 GDB 输出

以前说硬件是一个 state transition system，大家花了整门计算机系统基础课实现虚拟机，才相信这一点。今天说 C 语言也是一个 state transition system，可能还有些不相信，自己也暂时做不到，但 AI 马上就能帮忙。给它任意程序，它都能找出状态和迁移，比如刚才的 print_num。

trace.log 中的状态与语句

看这个状态，C 和 D 各自有值，format 是一个指针，指向某个位置。也可以把它指向的字符打印出来，再和 AI 对话几轮就能修好这些细节。接着执行到 n 小于 0，此时 n 是 42。再执行 Q 等于 n 除以 10，执行后 n 等于 42，Q 等于 4，和调试器一样。这就展示了，确实可以用工具提取任意程序运行时的状态。

执行 X 等于 Y 加 Z 这样的语句，大家比较熟悉。但我发现，很多同学没有完全理解函数调用：执行函数调用语句时，状态究竟怎样迁移？

Tower of Hanoi：带输出的函数调用

用一道题检验一下：怎样写一个非递归的 Tower of Hanoi？大家都熟悉汉诺塔，这里用的是一个稍复杂的版本。

递归汉诺塔与返回的步数

要把 n 个盘子从 a 柱移到 b 柱，先把 n 减一个盘子移到 c 柱，再把一个盘子移过去，最后把 n 减一个盘子移回来，代码里就是这样写的。学 C++ 时，大家是否觉得这段代码难理解？我想应该有过。它和 Fibonacci Sequence 那样的函数不同。Fibonacci 可以写成 fn：n 小于等于某个值时 return 1，else return f(n-1) + f(n-2)。这和高中数学里的函数一样，把返回表达式换成 f(n-2) + f(n-1)，不会影响程序结果。

数学上的函数，无论多少次输入同一个数字，结果都相同。Tower of Hanoi 的两个调用却不能交换顺序，交换以后输出就不对了。大家把它改写成非递归程序时，往往会遇到困难。先非正式调查一下：假设上机期末考试闭卷，不能用 AI，让大家写一个非递归的 Tower of Hanoi，也不允许推导数学性质。因为根据当前状态、每个盘子的位置，本来可以直接算出把哪个盘子挪到哪里；这道题禁止用这种数学方法。有多少同学有信心在一个小时或一个半小时的考场上写对？可以举手，不举手也没关系。没有人举手，有点惊讶，不过也正常。老早几年，我们问来保研的研究生，他们也写不出来。

后来还有一道加强题，比 Tower of Hanoi 更复杂：F 和 G 相互调用，f 调用 g，g 调用 f。有时调用形式是 f(n-1) + g(n-2)。

函数相互调用及模型测试结果

调用 g 时，又会调用回 f(n+1)。大家可能想到动态规划或 memoization：每算出一个 F，就保存结果，从小到大计算，把程序改写成二重循环。但如果在 F 里加一个 printf 打印 F，在 G 里加一个 printf 打印 G，要求非递归程序按照递归程序运行的顺序，打印 F 和 G 的函数调用序列，也就是 FG 序列，就像刚才展示的那样，题就难了。我觉得，在能考上或保上南大研究生的同学中，能写对的很少。肯定有人能写出来，这也没有那么困难。

这一直是我测试 AI 的题，有三个版本：第一个是非递归的 Tower of Hanoi，第二个是非递归的 F 和 G，第三个是输出函数调用序列。第二题中，AI 有时会“逃课”，用一些出乎意料的方法得到正确结果，也确实没有递归，但没有完整模拟原来的执行。最难的还是输出调用序列。几年来 AI 的能力不断增长，GPT-3.5 刚出来时，我就试过这个例子。

它竟然能写出非递归的 Tower of Hanoi，我很吃惊。不过想一想，它可能在训练数据里见过，可能还不能说明什么，因为 F 和 G 相互调用的版本它就做不对。GPT-4 也做不对。后来情况变了，去年能推理的 DeepSeek R1 做对了相互调用。但要求输出 F 和 G 的函数调用序列时，它吐了非常多 token，写了一些伪代码，我估计它自己也觉得搞不定。

不过方向和思路基本正确，能推理的模型第一次能把 F 和 G 的调用序列做对。再看今天的模型，大家有没有感觉 DeepSeek App 上的模型降智了？我感觉挺明显，原本预期能答对的问题，现在答不对，还会产生幻觉。但这个题它做对了。现在不知道用的是什么模型，我们可能还在等一个更大的模型发布。据说现在跑的是一个较小的 200B 模型，不过没人知道这究竟是不是真的。

要把 Tower of Hanoi，乃至任意程序从递归改写成非递归，就必须搞清楚程序的状态。在简单例子里，说程序是一个 state machine，很容易产生一种错觉：状态就是当前 lexical scope 里的变量，以及一些全局变量。

print_num 的局部变量

比如 stdin 是全局变量，它有一个值。当前 lexical scope 还有其他变量，比如 n 等于 42、q 等于 n 乘以 10、q 等于 4。老师讲程序执行时，通常会说：当前有一个状态，再执行一条语句。比如 if q 不等于 0，就像 gdb 停在这个判断位置，执行后进入下一个状态，pc 可能改变；如果语句是 x 等于1，x 的值就改变。不过，这还不能完全精确地描述 C 语言程序的状态。我有时会说 everything is a state machine，当我们谈 state machine、state transition system 时，含义需要更精确。

程序状态、初始状态与状态迁移

比如数字电路里的 012 计数器，大家知道怎样列出状态转移方程。说 everything is a state machine，意味着讨论的对象有严格的数学定义，可以用离散数学的知识写出来。用集合、关系、函数这些最基本的对象，就能定义 C 语言的状态和状态迁移；状态迁移也是一个函数。

理论上可以这样定义。大家暂时没有做形式化方法，不必真的用集合论语言把一切都写出来，但需要知道：计算机世界里即使是复杂操作系统中的真实对象，也能有严格的数学描述。那么 C 程序的状态是什么？只放一个 pc 还不够。先看初始状态。我们暂时不讨论计算机系统基础里怎样把 C 程序放到硬件上运行，也不谈其中涉及的 application binary interface。在 C 语言课的模型里，程序从哪里开始执行？从 main 开始。状态机的初始状态里有一个函数调用栈，里面有一个名为 main 的栈帧，也就是 stack frame。

main 的栈帧包含所有局部变量；此外还有全局状态，比如 stdin，以及自己定义的各个全局变量，每个变量都有值。main 里可能有 argc 等于 1，argv 是指针，指向外面的某个位置，也可以定义其他局部变量。接下来要问：程序运行时，gdb 高亮的当前语句，也就是 pc，放在哪里？它放在 stack frame 里。这是一个重要区别。刚才那张只画一个 pc 的图画错了，在这个模型里不能只在外面放一个 pc。

当然也可以采用等价的定义方法。比较典型、容易接受的模型是，每个栈帧都有一个 pc。C 语言状态机每执行一步，就从 topmost frame 的 pc 位置取出一条语句，执行后让 pc 指向下一处。对这个过程还不太清楚也正常。

可以对照刚才程序执行的 trace，再看简单程序发生了什么。如果 pc 指向 x 等于 x 加 1，执行后 x 的值改变，pc 到下一条语句。如果当前状态下调用 foo，也就是 topmost frame 的 pc 指向函数调用语句，那么会在栈顶创建一个新栈帧。

无论原来有多少栈帧，都保留。新栈帧的 pc 指向函数入口，旧栈帧的 pc 设为 nextpc，这就是函数调用。刚听完可能还没完全反应过来，可以回去花些时间，对照非递归汉诺塔调试。计算机世界里的这些事情都没有魔法，都能用离散数学定义。

所谓 call，就是往栈上 push 一个 frame，把 frame 的 pc 设为 0，压入相应的值。return 则 pop 一个值。C 程序就可以这样描述。

显式栈与 call 宏

ret 宏与返回值

以非递归汉诺塔为例，先 call，把 n 个盘子从 a 移到 b，经过 c。注意，调用的是这个宏，它把一个栈帧压上去。接下来 C 程序的模拟器开始执行：从当前状态的 pc 位置取一条语句，机械地按语句含义执行；遇到函数调用，就执行函数调用的操作。

非递归模拟器的主循环

这样写出的非递归汉诺塔，和递归版本长得一模一样。当前 pc 是 0，表示在函数入口，先做入口处的操作；n 是 1 就 return。到下一条语句，也就是第二行，就调用 n-1，把 n-1 个盘子从一个柱子移到中间的柱子上。

按 PC 分派的单步执行

这个程序还可以做加法，算出总步数。Tower of Hanoi 的返回类型是 integer。第一次调用时，把递归调用返回的步数保存下来；第二次也保存下来，最后返回 C1 加 C2 加 1。C1 和 C2 都在栈上的这个 frame，也就是 localframe 里，正如 argc、argv 是 main 的局部变量。

保存两次调用的返回值并求和

每个 stackframe 都保存自己的局部变量。看非递归版本的 frame 定义，里面有 pc、所有参数和局部变量，参数也属于局部变量。这就解释了为什么 C 语言是一种高级的汇编语言：确实可以这样解释执行它。理论上所有编程语言都能解释执行，但最容易翻译成机器指令的，仍然只有 C。C 让我们可以完整掌握计算机的行为，这个小例子也能帮助理解计算机系统和程序。

把刚才的程序写成 C 语言模拟器以后，就不必分别考虑 f 和 g。pc 可以指向 f，也可以指向 g，相互调用自然就能处理。模拟时只遵循一条规则：从 topmostframe 的 PC 取出一条语句执行。这些规则叫作 C 语言的形式语义，不必记住这个 term。

只要严格遵循 C 语言的形式语义去执行，所有东西都应该是对的。
