第 09 课 · C 标准库原理

选择并编译 musl

原片 00:29:45—00:36:48

去年我试着让 AI 帮忙生成一个 Standard C Library，有了实现，却没有完全成功。当时还是 Sonnet 3.7，经常出错，连栈对齐都不对，需要手工 Fix。那时我觉得自己掌握的知识还有些用。到了 2026 年，我觉得小丑是自己：大号模型实现一个完整、具有教学意义的 libc，已经没有问题。偶尔做错，运行后看到 Error Message，也能很快修复。不过，我觉得仍然有必要学习已有的 libc 实现。系统里会有一个默认的 libc，也就是 glibc。

除了源码，还可以从网上下载 glibc 的全部调试符号，在机器上调试它的每一行代码。以前我的操作系统课还是变态版本时，真的会进入 glibc 调试一些函数，例如锁、互斥锁。今天虽然仍然可以，但我觉得大家已没有必要这样做。glibc 有很多历史包袱，像刚才的 Inline Assembly 一样，每来一个需求就打补丁，每当指令集增加功能，开发者就想用上，以提升性能。最后代码库不断膨胀，维护困难，新手的阅读体验也变差。总会有办法解决，问就行了：有没有比 glibc 更适合学习的 libc 实现？当然有，AI 知道，我也准备了。

直接看模型 thinking 的过程，就能看到 musl、Bionic 等候选，以及许可证更友好的 libc。它还会［听辨不清，00:32:13］。我停止它继续阅读项目，给大家准备了一份 libc 代码。按大模型的提示去网站，下载 musl-1.2.6.tar.gz 即可。不会解压缩也没关系。

以前操作系统课有一张图，问大家用过 TAR 吗？它太古老，命令行参数风格甚至不完全符合后来 Unix、POSIX 的标准。通常参数前面带杠，TAR 却可以直接写所需操作，再选一个文件解压缩。有个笑话：核弹十秒钟后爆炸，需要输入合法的 TAR 命令解压文件才能阻止爆炸，大概没人能写对。今天这也没问题了，解压后就得到这样的目录。编译稍微花时间，我备课时已经做过，课上不再重复。我在 Claude Code 中使用豆包模型，让它帮忙编译项目并生成调试信息，得到可调试的 musl libc。

这份 libc 就是 C 语言除语法、语义之外的运行库。Ctype.h 中直接定义了 C 的函数，熟悉的 stdio.h 也在这里。musl libc 比较现代，维护得工整，想甩掉 libc 的历史包袱，基于 Linux 的 API 实现，没有采用古老的 POSIX API。

这里的宏定义也容易读。fseek 和 lseek 需要用三个宏选择游标位置：从头、从当前位置还是从尾部开始。SEEK_SET、SEEK_CUR、SEEK_END 就直接定义在这里。计算机世界里没有魔法，BUFSIZ 对应的 Buffer 大小、4096 的文件名长度，也都这样定义。fopen、freopen、fclose 都是 C 编程课学过的内容。

打开 musl libc 后，我让 AI 编译这份代码，得到可用的 musl-gcc。它是专门使用这个 libc 编译程序的命令行工具。

musl-gcc 可以编译这些展示 libc 功能的小程序。例如，程序只有 int main 和 return 1；Makefile 使用 musl-gcc，CFLAGS 中有 -g3，用来携带调试信息。

dummy.c

int main() {
    return 1;
}

同时采用静态编译，得到的代码看起来仍然不少，但比 glibc 编译出的内容少很多。它带有调试信息，稍后可以查看源代码。

也可以调试它。今天要讲的就是 libc 中的这些程序。
