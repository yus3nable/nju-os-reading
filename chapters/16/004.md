虽然我们有一个代码，真的可以实现这样的计算图，在这里一模一样的代码，只不过我现在不需要用什么计数器去数，多少个predecessor 已经结束了，然后我也不需要在每一个边上，或者是怎么样设置一个条件变量，我只需要在每一条边上放一个互斥锁，在 main 函数里面首先把所有的这个锁都 acquire 了，相当于先把所有的玩具都没收了，没收了以后我再创建若干个 worker，每一个worker 他都会看有没有指向自己的边，如果有一条指向自己的边。

```
struct edge {
  int src, dst;
  mutex_t lk;
} edges[] = {
  {0, 1}, {0, 2}, {0, 3},
  {1, 4}, {2, 4}, {4, 5},
};
```

![图 8：先获得入边上的锁，计算后释放出边上的锁（00:10:25）。](/assets/images/16/0008.webp)

```
for (int i = 0; i < LENGTH(edges); i++) {
  if (edges[i].dst == tid) {
    mutex_lock(&edges[i].lk);
  }
}
printf("Computing node #%d...\n", tid);
sleep(1);
for (int i = 0; i < LENGTH(edges); i++) {
  if (edges[i].src == tid) {
    mutex_unlock(&edges[i].lk);
  }
}
```

他就会试图去获得这把锁，当然如果没有入边的节点，没有入边节点天生就这个循环就是空循环，对吧，因为没有入边所以这个 26行的条件永远都不会达到，他就不会执行任何 mutex\_lock，所以没有入边的节点他就直接会，会直接到 32 行开始做计算。但是任何如果有任何有入边的节点，他都需要在这儿 acquire lock。然后如果假设那些没有入边的节点都运行的时间比较长的话，他一开始就会等待。然后等待等待完了，直到比如说没有入边的第一个 a 这个节点，他算完了。算完以后就会把所有他的出边上面的这个锁全部都给释放掉。

然后释放了以后，这样 x 就可以继续继续执行，这样，然后你如果真的编译运行它的话，是可以看到它确实实现了正确的效果的，和之前的演示是一样的，对吧，然后 123 同时出 45，然后 complete，所以这个代码虽然逻辑上是正确的，但是我们的线程库其实是不允许干这件事的，这其实是一个 undefined behavior，它要求你的上锁，acquire 和 release 是必须发生在同一个线程的，因为它里面有很多 fast path 的优化。
