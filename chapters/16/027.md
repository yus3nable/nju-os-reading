生产者消费者可实现 waiter thread 管理哲学家。可能觉得串行管理性能低，多处理器应该各线程并行。但调度实现高效时，检查能否分配叉子，可能只是 hash table 等数据结构操作，几纳秒就完成，时间复杂度很可能 O(1)。任务划分合理，开销就很小。

若每次吃饭需几秒或几十毫秒，几纳秒可以忽略。也可能有 128 核、256 核系统，web 请求各花十几毫秒，一秒涌入几万请求，单个 waiter 造成明显延迟。那就用两个 waiter。

![图 58：先发请求，再等待许可；结束后发消息归还叉子（01:24:46）。](/assets/images/16/0058.webp)

图 58：先发请求，再等待许可；结束后发消息归还叉子（01:24:46）。

一半 CPU 交给一个 waiter，另一半交给另一个，仍可同时控制复杂性、降低延迟。做 System 先解决问题，实际有性能问题，再针对解决。我们的经验是，这些问题总有办法，只要任务划分合理，性能损失基本可以忽略。
