日常终端却不完全像原始字符交换。比如 \./a\.out 或 cat，cat 用 read 从 stdin 读取 buffer、size，再输出。按刚才的模型，Terminal 每个字符都送给计算机。

cat 收到就应直接 write，为什么按 A 后 read 还没返回？用 strace cat，确实能看到它仍在等待。

![图 46：strace 显示 cat 的 read 仍在等待（00:41:24）。](/assets/images/08/0046.webp)

图 46：strace 显示 cat 的 read 仍在等待（00:41:24）。

输入错了，还能退格重打，比如 bbbbbbb，直到回车，read 才返回。因为字符先送操作系统，默认由它加工，再给应用。刚才的演示程序则请求系统不要处理，直接交付原始字符。

默认有行编辑模式。Foot、Kitty、iTerm 等 Terminal Emulator 模拟终端，和操作系统一起提供可编辑的 canonical mode。再看看终端从启动到登录的过程。

1970 年代、VT100 时代，终端是最重要的人机交互 I/O 设备，坏了就没法用电脑，所以启动时就要初始化。Firmware 先运行，再交给操作系统，完成部分初始化、扫描终端后，init 调用 getty。

getty 会 opens a TTY port，再 prompt for login name and invokes the login command。假设实现操作系统，初始进程可能还没有 0、1、2，也不知道自己关联哪个终端，系统又可能有五六个。init 用命令行参数，要求 getty 分别在第一、第二、第三终端运行。linux 按 Ctrl Alt 加 f1，［切换虚拟终端时，录屏画面变黑。］这里是日志控制台，Ctrl Alt F1，再 Ctrl Alt F2。

还有 F3，各处能看到登录提示，那是 getty 程序。当前我在 Ctrl F7、第七屏幕、TTY7，图形界面就在它上面。可以在指定设备、term 上启动 login。

getty 真正打开 /dev/tty1 这样的终端，把 0、1、2 都指向它，再配置初始化。baud rate、波特率表示真实接口传输速度。实体 VT100 需要正确值，才能与系统握手；模拟设备不太重要，但 Pseudo Terminal 仍会显示 38400 的 baud rate。

这时终端才与进程关联，再启动 Login。远程登录略有不同，sshd 会 Fork 自己、分配 Pseudo Terminal，完成初始化，再做类似 Login 的操作——未必运行 Login，可能自己切换权限，因为 sshd 本来有高权限。Login Program 的说明是 Used to establish new session with the system。用户像坐在终端前，这个 Controlling Terminal 与 Session、会话关联，一会儿再讲。

Login 手册也写 Begin Session on the system，这个 Term 有点混乱，但无论哪种登录方式，都会有关联终端。
