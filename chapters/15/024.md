这里准备了计算图实现代码，可作为模板。只要任务有足够并行度，就能利用多个处理器，使用共享内存，将中间结果放进数据结构、队列或树。后续任务激活后，可以直接读取前驱计算节点写入的结果。

采用简单模型，扫描全部边，统计每个节点的 pending dependency，知道要等几个任务完成。每个任务创建一个 T\_worker。计算图可以任意指定，这里 0 happens\-before 1、2、3。

```
struct edge {
    int src, dst;
} edges[] = {
    {0, 1}, {0, 2}, {0, 3},
    {1, 4}, {2, 4}, {4, 5},
};

struct task {
    int pending_deps;
    cond_t cv;
} tasks[NTASKS];
```

还有 1 happens\-before 4、2 happens\-before 4、4 happens\-before 5。0 必须先执行，之后 1、2、3 能同时执行，再继续后面任务。有一系列 tasks，每个 T\_worker 都用模板，先加锁，lock、unlock 配对；执行条件是所有 pending dependency 降到 0。

条件未满足就 wait。每个任务各有条件变量，无须唤醒所有任务，但整个实现仍只用一把互斥锁。每个 worker 模拟计算一秒钟。

![图 64：T\_worker 等待依赖清零，解锁后计算（01:13:18）。](/assets/images/15/0064.webp)

```
void T_worker(int tid) {
    tid--;
    mutex_lock(&mutex);
    while (!(tasks[tid].pending_deps == 0)) {
        cond_wait(&tasks[tid].cv, &mutex);
    }
    mutex_unlock(&mutex);

    printf("Computing node #%d...\n", tid);
    sleep(1);
    // 后面更新后继任务的依赖。
}
```

计算部分可以不加锁，前提是没有共享数据结构的并发访问。通常只需短时间持锁，例如从队列取任务。任务带指针，指向的一大块内存在这段时间只由当前线程访问，确认不存在并发 sum\+\+ 之类问题，就能放心解锁，得到多处理器并行的好处。计算后重新加锁，更新图中依赖。

这里简单扫描每条边，找到当前节点的出边，将每个后继的 pending dependency 减一。只要降为零、可能让线程继续，就 broadcast。这里 signal 也可以，但我选择保守实现，不必为一点尚不存在的性能问题给自己制造麻烦。

```
mutex_lock(&mutex);
for (int i = 0; i < LENGTH(edges); i++) {
    struct task *t = &tasks[edges[i].dst];
    if (edges[i].src == tid) {
        t->pending_deps--;
        if (t->pending_deps == 0) {
            cond_broadcast(&t->cv);
        }
    }
}
mutex_unlock(&mutex);
```

还有 join，也能用类似方式实现。运行看看，node0 先执行，随后 123 同时执行，之后是 4、5。

1、2、3 的顺序仍不确定，上次 213，这次 123。只要计算部分没有并行冲突，就能利用多个处理器。回顾今天，同步、条件变量是并发控制的重要技术。想清同步，就是多个线程在某个点达到全局可描述的状态，知道彼此发生了什么。多个线程同时 sum\+\+，谁快谁慢都不确定，除非看清全部处理器状态，否则很难理解。同步给了简化状态的机会：A happened before B，意味着一定有一个时刻，A 已结束、B 还没开始。之后双方仍可各自分叉执行，但这个点有确定状态。

理解每种同步条件即可。每节点一线程，要等全部前驱完成；线程池、executor pool，则等队列中有任务。

队列非空，线程取一个任务；空就等待。创建或激活新任务后再入队，就可能唤醒其他 worker thread，让它们取任务执行。
