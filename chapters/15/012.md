别人的同步条件可能满足时，可以调用 Signal 或 Broadcast 这两个 API。Signal 唤醒这个条件变量上的一个等待线程；Broadcast 将所有睡在这个条件变量上的线程都唤醒。所以 Broadcast 开销可能稍大。

它有时会唤醒暂时无须唤醒的线程，让它多检查几次，但我仍推荐：任何线程只要可能使同步条件满足，都用 Broadcast，以保证正确性。条件变量版乐团也是先 lock，条件不满足就 cond\_wait。

这意味着什么？

```
cond_t cv = COND_INIT();

void wait_for_beat(int current_beat) {
    mutex_lock(&lk);
    while (!(current_beat < conductor_beat)) {
        cond_wait(&cv, &lk);
    }
    mutex_unlock(&lk);
}

void release_beat() {
    mutex_lock(&lk);
    conductor_beat++;
    cond_broadcast(&cv);
    mutex_unlock(&lk);
}
```

while 循环内外都能按循环语义写 assert：内部条件未满足，外部条件已满足。这里始终还要考虑持锁。cond\_wait 虽会释放锁，受到 Broadcast、Signal 唤醒后，却会重新 acquire，直到获得同一把互斥锁。

锁未必能马上拿到，别人可能持有它，甚至发出 broadcast 的线程此时还持着锁。因此被唤醒，也不能立刻继续后面的逻辑，cond\_wait 必须先取回锁。返回后，马上重新执行循环条件检查。

所以它和前面的 spin loop 逻辑相同，只是条件未满足时可以睡眠，是高效版本的等待循环。
