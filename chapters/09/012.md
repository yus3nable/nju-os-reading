系统调用封装后仍然会返回错误。每个系统调用 API 的手册都有 ERRORS，说明可能的出错原因。例如 fork 的 return value：成功时，父进程得到子进程的 PID，子进程得到零；返回负 1 则表示失败。负 1 对应很多种失败原因。

![图 74：fork 的成功返回值和失败返回值（01:06:55）。](/assets/images/09/0074.webp)

图 74：fork 的成功返回值和失败返回值（01:06:55）。

fork 的失败原因相对较少。例如 EAGAIN 表示暂时不行，可以稍后再试；forkbomb 时则可能返回 ENOMEM。很多系统调用会暂时失败，现在失败、过一会儿肯定成功，就返回 EAGAIN。再看 open 的 ERRORS，错误类型会多得多。

![图 75：fork 的 EAGAIN 与 ENOMEM 等错误（01:06:58）。](/assets/images/09/0075.webp)

图 75：fork 的 EAGAIN 与 ENOMEM 等错误（01:06:58）。

每种可能的错误都有编号。常见的 EACCES 表示 the requested access to the file is not allowed，或 permission is denied，即请求的文件访问不被允许或权限被拒绝。还有 EEXIST：如果 path 已存在，并使用 O\_CREAT，就会报错。

![图 76：open 的返回值与 EACCES（01:07:57）。](/assets/images/09/0076.webp)

图 76：open 的返回值与 EACCES（01:07:57）。

错误类型很多，libc 必须妥善处理每个系统调用的错误。大家做 oj 的一个问题，是它从来不要求处理错误，OJ 会告诉你错了，程序必须百分之百正确。实际使用中错误不可避免，例如用户输入错误，对不存在的程序执行 gcc，它必须给出好的错误提示。

![图 77：EEXIST 对应的路径和打开标志（01:08:10）。](/assets/images/09/0077.webp)

ls 一个 nonexist 时，会提示不能访问 non exist：No such file or directory。加入 LANGUAGE 环境变量，提示就完全变了，ls 的行为却相同。这解释了为什么有些同学看到中文 error message，我看到英文。它们是同一个 ls 程序，访问同一组系统调用，试图 open 目标后失败。ls 为什么能区分不同语言？

这由 libc 处理。其中有一个 perror 函数，大家是不是在操作系统课上第一次学？此前的课程应该教过，它属于 standard C library。

![图 79：perror 与 errno 的声明（01:10:00）。](/assets/images/09/0079.webp)

图 79：perror 与 errno 的声明（01:10:00）。

老师应该教大家这些内容。C library 的调用都可能失败，有些错误需要容忍。例如依次尝试打开三个文件：第一个不存在就打开第二个，再尝试第三个；都不存在就退出，这时可以不打印 error message。但写 ls、gcc 这样给别人用的工具，文件不存在时需要向用户报告错误，就应该用 perror。它先打印指定的提示字符串，再获取上一个系统调用或库函数调用的错误原因，打印对应字符串。libc 会根据当前语言环境的配置，输出友好的 message。

![图 80：perror 手册中的系统错误信息说明（01:10:49）。](/assets/images/09/0080.webp)

图 80：perror 手册中的系统错误信息说明（01:10:49）。

看 ls 的输出，ls 冒号是指定的提示，剩下的“没有那个文件或者目录”等内容由 perror 打印。内部还有 errno 变量，C 可以访问它，得到对应错误类型。自己实现工具时使用 perror，也能以正确语言输出错误信息。这种实现具有 portable 特性，也是一种好习惯。这就是系统调用的封装。
