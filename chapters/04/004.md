接下来讲技术部分：怎样用好大模型。刚才介绍过，它根据 context 输出下一个 token，一个重要机制是 self\-attention、注意力。这也像人。看难数学题的题解时，经常会发现解题者注意到了自己没想到的地方。

## 如何用好大模型：attention engineering 与问题分解

![图 42：如何用好大模型：attention engineering 与问题分解（00:58:29）。](/assets/images/04/0042.webp)

图 42：如何用好大模型：attention engineering 与问题分解（00:58:29）。

一旦注意到那个条件，题就解出来了，推导都对，但自己没想到。人的注意力可以训练，能从问题结构、词语之间找到联系；困难时也要像 reasoning model 一样，推理、尝试。提示词工程，在一定程度上就是 attention engineering：让模型看见希望它注意的信息，引导正确行为。比如只让 AI 写小说，结果可能不满意；只说“写入党申请书”，所有 attention 就放在这几个字上。它作为读过大量书的模型，会写出中庸、平庸、平均的申请书，形式很好，却未必符合需要。此时要补个性信息，比如自己是什么人、希望怎样写，提供足够上下文，让 self attention 能关注这些内容。

今天仍需要适时帮助 AI 分解问题。虽然 Claude Code 的 Plan Mode 会规划，一会儿的例子也有计划，但分解能力仍是 AI 时代很需要的能力。一个 crazy 想法，直接交给 AI，可能只得到平庸答案；以独特视角分解，就可能得到可用、甚至达到产品要求的成果。这涉及构建合适的抽象。

syscall 下面可能是千万行代码的复杂、高性能操作系统，上面的生态也很大，中间接口却相对很小，实际需要用的更少。直接让模型实现操作系统，可能写着写着就失败。但仔细设计创新的抽象层，比如设想未来的 syscall 应该换一套形式，再带着 AI 实现，就可能做出下一代热门操作系统。

指令集也是经典抽象。底下是硬件，上面是整个 OS application、整个计算机世界。RISC、RISC\-V，RISC 的 reduced，就是精简指令集。这是生态中的中间接口，在单个应用里也能用抽象分解复杂性。大家写程序，会把功能封装成函数。

这样按协议分离几个 subsystem，就能让 AI 分别实现，甚至多个 AI agent 并行实现工具。若是 monolithic 库，全部依靠函数互相调用，并行 agent 就有风险，两个 agent 同时改同一文件，还要处理冲突。架构设计好，更容易维护。

我觉得现在 AI 还不太擅长这件事。但既然算力就是智能，它也应该能做到；到那一天，人类的末日可能就到了。现在还剩一些时间，准备接受翻车：完全交给 AI，Vibe Code 一个 OS kernel，测试国产模型能力。
