## 在 \_start 中无限循环

![图 40：在 \_start 中无限循环（00:44:14）。](/assets/images/02/0040.webp)

图 40：在 \_start 中无限循环（00:44:14）。

第一条指令停在 hello\.c 的第二行，正是跳转指令，接下来进入死循环。如果想让程序返回，把 \_start 写成空函数，会正常返回吗？它会 crash。为什么？按前面的定义，C 程序从 main 开始，每次执行 topmost frame，也就是栈顶 frame 的 pc 所指的语句。假如 main 返回了呢？

main 返回以后，函数栈就空了，topmost frame 不再存在，也取不到 pc。前面的模型没有定义下一个状态。数学上当然可以补充定义，允许程序在这时终止。但编译器把程序翻译成直接在硬件执行的状态机时，初始状态和刚才的模型不同。每个程序、每个进程加载时，都有自己的初始状态。

![图 41：main 返回后与初始机器状态（00:45:58）。](/assets/images/02/0041.webp)

图 41：main 返回后与初始机器状态（00:45:58）。

一个 \.c 程序在机器上有相应的 register 和 memory 初始状态，之后逐条执行指令。函数返回时，相当于执行 pop，把当前栈顶保存的 PC load 到 PC。进程初始化时也有栈和 stack pointer，比如大家熟悉的 rsp。指令会机械地完成自己的操作。看这个 a\.out，先是一个什么也不做的 nop，再 return。return 的语义是从栈上 pop 出 PC。初始 rsp 是多少？调试一下。

PC 变成 0，指向非法的内存页，程序发生 crash，报告 segmentation fault，这就解释了刚才看到的结果。这意味着编译器工具链处理的程序，并不直接从 main 开始。System V 的 ABI 规定进程的初始状态，后面会专门用一节课讲，今天没时间说明整个进程在二进制意义上的完整初始状态。现在只要知道，PC 会先指向初始化代码；代码完成准备后 call main。main 返回以后，初始化代码继续执行，但它自己不能再返回，接下来要执行系统调用。这才引出今天要讲的内容：最小 Hello World 可以直接用汇编写。我准备了 x86\-64 和 ARM 两个版本，我的机器需要 ARM 版本。

先看大家更熟悉的 x86\-64。要打印 Hello World 并正常退出，必须请求操作系统，因为 C 语言本身没有退出这件事。操作系统和 C 之间约定了一条指令。从应用程序看，操作系统就是一组 API。

这些 API 通过系统调用指令实现。x86 上是 syscall；实验中可能还用过 int 0x80，也就是 32bit 的 0x80 中断，64bit 系统使用 syscall。调用前，要把正确的参数放进正确的寄存器。对 x86 来说，先把系统调用编号，也就是要执行哪一个系统调用，放入 RAX，再把剩余参数依次放入其他寄存器：第二个参数放 RDI，第三个放 RSI，第四个放 RDX，接着执行 syscall。这相当于一次很远的跳转，转到操作系统代码。之后的操作不再由程序控制，操作系统可以向外写数据。syscall 返回后，程序继续执行，但操作系统也可能修改程序内部状态，甚至直接结束程序。要退出，就调用 SYS\_exit，这个 1 是程序返回值。ARM 也一样，第一个参数放 X0，第二个放 X1，第三个放 X2。它们分别表示文件描述符，也就是往哪里输出、往哪里写。

另外两个参数表示写入数据的地址、要写多少个字符，也就是把一个 buffer 缓冲区送给操作系统。再把系统调用编号放入 X8，执行 svc 这条 Software Interrupt 指令，产生软件中断。

![图 51：手册中的各架构参数寄存器（00:52:42）。](/assets/images/02/0051.webp)

系统调用指令与其他指令有重要区别。简化一点说，几乎所有大家见过的数据移动、访存等指令，都只能改变当前进程的 memory 和 register。对应到 C 语言模型，赋值、分支、循环都只改变这个抽象状态中的变量值，无法改变另一个进程的状态。只有 syscall 可以做到，但前提是把控制权完全交给操作系统。

用两个比方解释一下。先看手术：先和医生签好 contract，说明要做什么，之后躺下闭上眼睛，醒来时可能已经变成女生。调用操作系统也要先约定 contract，说明想做什么。在任意状态执行 syscall，或 ARM 的 svc、RISC\-V 的 ecall，就把控制权交了出去。

之后执行的是操作系统代码，程序看不到，也访问不了。操作系统根据约定工作：程序事先把参数写入寄存器，操作系统知道请求内容后，检查是否合理、有没有越权。越权就拒绝，返回失败；合理就执行，完成以后返回。执行期间也可能修改进程状态，比如 read 系统调用可能把一些数据搬到进程地址空间里。

假设这里有一个 buff，执行 read 的 syscall，返回时操作系统可能已经填好了 buff。比如从键盘读到 hello，共五个字符，系统调用返回值就是五，buff 里也有相应内容。这就像麻醉后醒来，可能什么也没发生，可能已经变成女生，也可能再也醒不过来。若 syscall 是 exit，就是最后一种情况。

调用 exit 后，程序永远不会返回，所有资源都被操作系统清理，进程也就没有了。这个理解类似全身麻醉，期间什么也不知道。还可以想象一个科幻世界：有一个全能的上帝，只要对天祈祷，下一秒事情就实现了。程序也感知不到操作系统处理请求的过程，只是通过 syscall 交出控制权，操作系统完成事情以后再返回。

这页 slides 是整个操作系统课最重要的一页。要理解它，需要前面关于程序是什么、怎样从高级语言变成低级指令，以及哪些东西不能被优化的讲解。当然，这里的说法还不绝对严谨，后面会看到应用程序和操作系统可能共享内存，情况会复杂些。但假设 syscall 是唯一的交互接口，那么除了 syscall，其余东西都可以优化；只要所有输入下产生的 syscall 序列完全相同，优化就是正确的。只需要在 syscall 处保留这些行为。
