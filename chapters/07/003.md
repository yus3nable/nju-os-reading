操作系统为开发者提供服务。从写应用的角度看，大家在高级程序设计做游戏等作业，除了算法，把数据结构或数字转换成结果，比如棋盘 AI、状态空间搜索，还需要完成非计算任务。比如我让 coding agent 读 POSIX 手册，查命令行参数规范，读取网页就要靠库函数和操作系统。文件写入、进程通信也是如此。

这些任务都涉及操作系统对象。写上节课的游戏修改器时，脑中先想的是所需功能，未必是 FD 等于 open。可能希望用 Python 的 pathlib，读取 proc 下 1234 的 maps 文本。

今天就讲它背后怎样实现。开发者还可能想要更方便的 GetMemoryMap，给 PID 就返回数据结构，描述各段起止地址、权限；或者 ReadProcessMemory，指定 PID、address、buffer、size，读出一段进程内存。

设计者则要满足应用需求，提供通用机制，支持生态发展。最早 UNIX 没有网络，后来才逐渐增加套接字等 API。目标是简单、稳定、通用的接口，也就是抽象层。

可以直接提供 GetMemoryMap，也可以像 UNIX、Linux，把进程信息作为文件放进 /proc，复用文件、目录 API，无须新增专门调用。比如 Open、open、read、write，目录也可以 Open。

再用 Read Directory Entry 扫描目录项，就能实现 GetMemoryMap、ReadProcessMemory 等功能。Linux 用现有一套接口，不代表其他系统必须如此。Windows 从软件工程看设计得很好，接口风格不同。Unix、Linux 带着 Hacker 的思路，用简洁的 hack 把信息放在 Proc 下，也会有代价。

内核原本保存数据结构，为提供 procfs，先序列化成 maps 文本；pmap 读出后，再解析、加工成输出。这样有浪费。如果直接取得内核数据结构，计算量就能减少。

还有 Asynchronous 等方式。文件不存在时，用 O\_CREAT 创建。这是 Unix 的历史遗留拼写、Typo，没有写完整的 Create。Ken Thompson 当时为了省一个字符、一个字节，就缩短了名字。

![图 20：O\_CREAT 的拼写与文件创建行为（00:16:06）。](/assets/images/07/0020.webp)

图 20：O\_CREAT 的拼写与文件创建行为（00:16:06）。

后来字节不再值钱，却不能轻易改：后续系统为了兼容，一直沿用。Windows 则提供 CreateFile、WriteFile、SetFilePointer，访问其他进程有 OpenProcess。虽然并非 Open Source 的 System，但 API call 把参数直接传内核，能高效实现 OpenProcess、ReadProcessMemory，VirtualQueryEx 可以查询地址空间，比 procfs 文本解析更直接。Linux 的另一种选择，也带来后面要讲的影响。

那就是 Unix Philosophy。今天有了大语言模型，哪种方式更好又难说了，世界一直在变化。需要理解设计理念：操作系统 API 服务于程序员想做的事情。这是重要的 first principle。
