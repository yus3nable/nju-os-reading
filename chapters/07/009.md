简单设计在真实系统里也有复杂后果。文件是字节数组，比如 log\.txt，打开得到描述符 3，先写一个字节 1，再写 2，文件依次写下 1、2。写 hello。

再写 world，就得到 helloworld。内核实现可以用 file 结构体，buff 指向数组，offset 表示当前位置。write 根据描述符定位结构。

从 0、1、2 这些编号中，找到 3 对应的文件，按 offset 写 1，再把 offset 加 1，下次写 2 就接在后面。但若这时 fork 呢？内存、寄存器复制很好理解。

![图 58：文件偏移量随 write 向后移动（01:01:00）。](/assets/images/07/0058.webp)

图 58：文件偏移量随 write 向后移动（01:01:00）。

```
write(3, "1", 1);
write(3, "2", 1);
```

除了返回值寄存器，父进程得到子 PID、子进程得到 0，用户态状态相同。内核资源怎么复制？假设先写 1，再 fork，再写 2，就有两个进程写 2。

它们该覆盖同一位置，还是追加，最后看到一个 2 或两个 2？设计者可以选择。若连 file、offset 都独立复制，两份 offset 相同，写入互相覆盖，只留下一个 2。

也可以浅拷贝，让 p2、p1 的 3 指向同一 file，第一个写 2 后，offset 前移，第二个再写，继续前移，就留下两个 2。复杂软件系统都会面对这种取舍。

fork 看似只是复制，但进程持有的每类资源都要定义复制后的语义，几乎与每种系统调用、内核对象有关，带来大量复杂性。有人因此主张课程别再教 fork，论文叫 A Fork in the Road，作者有不少知名研究者。

可以读读。系统每处设计都要考虑与其他部分交互。UNIX 选择让 P1、P2 写两个 2，原因就是这里可能是 log\.txt。

![图 59：fork 后共享文件对象与 offset（01:04:10）。](/assets/images/07/0059.webp)

图 59：fork 后共享文件对象与 offset（01:04:10）。

```
write(3, "1", 1);
fork();
write(3, "2", 1);
```

父子进程共享、追加日志时，通常希望保留双方数据，避免后写覆盖先写，造成意外丢失。于是 UNIX 让两个指针共享 offset。想要独立 offset，需要另一个做法。

重新打开文件即可。fork 默认继承许多资源，也带来问题。Windows 的 Handle 默认不继承，创建或配置时可以通过 bInheritHandles 等选择，让未来 Spawn 的子进程继承。

我觉得 Windows 的最小权限原则在软件工程上更好。父进程若打开敏感文件，fork 后 execve 运行其他程序，忘记关闭描述符，子进程就有访问权限。即使没有恶意，bug 也可能导致误写系统文件。

后来 Linux 增加 O\_CLOEXEC，使描述符在创建子进程时不被继承。API 演化到今天也有许多问题，好在 AI 理解这些行为。遇到真实问题，需要意识到潜在复杂性，能够 reason about 程序执行。以上是文件描述符 API。
