参数虽然都是整数，不同 malloc 的场景却不同。分配 1 兆、10 兆、100 兆的大对象，可能是 hash table 装不下，resize 到 1\.5 倍，需要新分配或回收大块内存；也可能需要大缓冲区、映射磁盘等大文件。

分配大对象，之后应当频繁读写。如果申请 100 兆，只用几个字节就 free，是 performance bug，应换数据结构。例如开 100 万的 hash table，只放三个元素就 free，应该换更紧凑的 set 或 map，避免申请大块内存。

从这个观察可知，真实 malloc、free workload 远比数据结构课中“插入一个区间、删除一个区间”复杂。

可以推论：对象越小，创建分配越频繁。例如临时字符串，在本次请求中拼到最终文本后就不用了，数量多、琐碎、生命周期短。中等对象，如生成 HTML 请求的字符串、小容器，生存期往往稍长。几兆、几百兆的大对象可能长期保存系统全局状态；对象越大，结构越倾向稳定，在内存中停留更久。要通过实验，几乎只要管好小对象。
