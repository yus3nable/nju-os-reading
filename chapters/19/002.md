在实际的系统里面，我们不像你们学算法数据结构课的时候，你们总是盯着那个 worst case，你们需要这个 worst case 尽可能的特别的好。然后这样你们才能通过那个算法题，对吧。所以你们脑子里面拿到任何一个问题，你们想的都是这个 worst case 是 O(1)、O(n) 还是 O(n log n)，因为你们总是被问这样的问题。但其实对于实际的系统来说，你们需要的是在真实的一个分布下，因为你的，比如说你们考虑排序的时候，总是说排好序的顺序的时候是最差的，还是一个什么样精心构造的数据是最差的。

但是在实际当中你的业务系统收到的那个内存分配的序列，或者你的那个集合收到的 insertion deletion 的序列，它是符合一个现实物理世界中的概率分布的。然后你需要在这个现实的物理分布下要做的尽可能的好。同时你可能也希望这 worst case 不要太坏。因为如果你的 worst case 很坏，比如说你的算法有一个指数级的 worst case 的话，那这些别有用心的攻击者就会可以通过给你发这种特别差的请求，让你的系统变得非常非常的慢。其实我们的比如说像 apache 的 httpd，在很长一段时间里面都是整个互联网的核心的支撑。

然后你们都知道 HTTP 请求，你可以给他带一个参数，对吧？你请求一个问号，然后你可以 A 等于 B and C 等于 D 这样写一个这样的请求的字符串。然后这个字符串会被插入到一个 hash table 里。然后如果你精心构造这些字符串，使得他们所有的字符串的 key都映射到 hash table 的同一个桶里。OK，你就可以让 apache 的 server 变得很慢。然后这曾经是一个复杂性攻击的安全漏洞，对hash table。所以性能是一个很复杂的问题，但是无论如何你们在考虑优化性能之前都要考虑你到底需要什么样的性能。
