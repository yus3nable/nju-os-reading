前面假设互斥锁使用正确，实际却有很多用错的方法。acquire、release API 设计出来后，人类就不断犯错，当然没有“万劫不复”那么夸张。现在 Linux 内核仍有数不清的锁问题，因为 lock、unlock 都由程序员负责，和 malloc、free 一样：知道 malloc 后要 free，也未必每次都做得到。

每个 acquire 后都必须对应 release。函数首行 acquire、末行 release，中间却 return，程序就错了。觉得自己不会犯，可能只是代码集中在一个文件；真正有几十个文件、几十把锁，就很难做对。例如链表，可以用一把锁保护整个结构。

持锁就能访问整个链表。但要实现性能过得去的并发链表，就不能只用一把锁保护所有节点，而要每个节点各有一把。今天 reading 的 concurrent data structure 部分会讲。双向链表的概念很简单，有 previous、next，遍历却复杂起来。

需要边加锁边解锁。持有当前节点锁时，不能先释放，要先拿到下一个节点锁，保护中间的链接关系，否则就会出错。

图 16：沿链表移动时需要保护节点和相邻链接（00:26:17）。

到达下一节点后，才能释放前一个节点的锁，再尝试 acquire 后续节点。遍历已经这样复杂，插入、删除还要同时拿 previous、current、next 三把锁。最麻烦的是删除后的内存回收，必须确认无人持有指向该节点的引用，才能回收。

这比想象中难，做 lab 时很快就会遇到许多微妙细节。如果只有一把锁，需要原子性、stop the world 就 lock，再 unlock，世界会简单许多。手工管理复杂锁很麻烦，于是更能看出 make\_it\_work 的价值：写出链表，再由好编译器生成高效且正确的实现，无须手工翻译。我觉得离这一天可能不远，也许今天讲的内容很快就没用了。除了多把锁的逻辑问题，还会有小错误。下面看似用同一把锁保护 sum\+\+，错在哪里？

一把叫小写 l，另一把叫大写 I，锁就形同虚设。同一把锁才会互斥，I、l 两把锁可以并发。别笑，我也常犯这种错。几十把锁、几十个文件、函数相互调用，很难相信自己能记清。Linux 内核开发者也经常讨论锁问题，有些动态检查工具会在运行时发现漏锁。

查出后，再讨论谁出了问题、应该怎样修。操作系统课给初学者的建议就来自这些经验。
