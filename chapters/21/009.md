这就把两门课联系起来了。跳过网络课的内容，请求最终会到达数据中心的另一台计算机。这台机器大概率可能是一个 load balance，它承担代理工作，还没有实际为请求提供服务。

![图 18：负载均衡和课件中的响应示例（00:15:33）。](/assets/images/21/0018.webp)

图 18：负载均衡和课件中的响应示例（00:15:33）。

它每秒可能收到大量请求，自己不实际处理，手上可能有 16 个或 32 个 worker，再随机或按某种方式把请求映射到一个 worker，转发过去。转发代价远小于处理代价，逐层转发就能承受很大的业务量。到达另一台机器、处理完所有业务逻辑后，才能看到 response。我试过访问 api\.deepseek\.com，由于没有正确的 key，会收到 401。HTTP header 的 server 字段是 openresty，很可能又是一个 API 网关。访问 deepseek\.com 时，DeepSeek 的 server 给出的是 Cloudflare，也类似代理，还返回了 error request block。

![图 19：网站请求返回 Request Blocked（00:17:07）。](/assets/images/21/0019.webp)

图 19：网站请求返回 Request Blocked（00:17:07）。

它禁止了 curl 访问。每个 HTTP 请求都带 User\-Agent，继续和 AI 对话，就能了解这些应用层协议的行为。回到操作系统，这一切都由那几个系统调用实现。刚才的 strace 中可以看到 send receive、connect，也可以对文件描述符执行 read，得到文本形式的数据。我刚才用的命令好像是 curl \-i。

![图 20：API 根地址返回 401 和 openresty（00:17:41）。](/assets/images/21/0020.webp)

图 20：API 根地址返回 401 和 openresty（00:17:41）。

API 根地址请求的响应片段：

```
$ curl -i 'https://api.deepseek.com'
HTTP/2 401
server: openresty

Authentication Fails (governor)
```

数据经过网络链路时，每一层可能都要加头、加尾，像交“网络税”。回到应用程序后，收到的就是这样的文本信息。它背后具体发生了什么，应用程序并不知道。
