数据中心里的并发编程，光靠协程或异步事件编程还不够。产品体验对它们至关重要，需要高吞吐、低延迟的事件处理。绝大部分工作虽然只是增删改查，难度仍然超出想象。比如淘宝下单会涉及支付宝，支付宝还涉及银行，有多层业务逻辑，可能拉起一千多个模块。

在这种情况下保持系统性能很有挑战，很多程序的性能问题至今没有解决。比如微信小程序，大家能感到它的体验相对较差；使用 app 时，对网络延迟或网络故障的容忍度会好很多。大家做 malloc free 已经很痛苦，实现实际系统时，可能也想用简单的方法。

比如“一把大锁保平安”，会有什么后果？一个并发 hash table 已经有几十兆大，要 resize 时，旧数组就不能继续用了。需要重新 allocate 几十兆内存，再做几十兆的 memory copy，把旧内存复制到新内存。

还可能要遍历，代价比 memory copy 更高。完成后释放旧内存，把 hash table 迁到新版本。几十兆的 memory copy，延迟可能接近几十毫秒、上百毫秒。假如是一百毫秒，期间几万个或十几万个并发 client 都得等待一百毫秒，对 P99 latency 的影响是毁灭性的。

有个很有名的调研说，延迟每增加一百毫秒，用户就会成倍流失，因为他们觉得卡。最好按下一个键就立即有反馈，太慢会让人觉得服务做得不好。海量请求突然到达时，系统也可能扛不住。前两年雷总在小米汽车发布会上展示车里的小爱同学，喊了一声“小爱同学”。关注小米汽车的人通常是米粉，家里至少有一个小米设备，比如小米音响。通过电视看直播时，这一声可能也会唤醒家里的小爱同学。全国设备一起唤醒，就有点像 denial service attack，海量请求突然到达数据中心，来不及处理。那一刻，全国的小爱音响在小米汽车发布会上同步瘫痪了。

数据中心并发编程要解决的就是这类问题。当然，无法保证任意数量的 client 都能承受，目标是在较大的弹性范围内，接住突然增长的用户；峰值过后，再释放资源。同时还要保证很高的可靠性，谁都不希望 QQ、微信的聊天记录发生丢失。
