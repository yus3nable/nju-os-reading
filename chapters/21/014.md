就有了一个 1999 年的时候，Dan 提的一个叫 C10K problem，C10K，就是说我有一个 concurrent，有一个一万个 client concurrent 的问题，也就是说，在 1999 年的时候，他说，我们有一个 web server，已经那个时候的 web server，已经，或者说那个时候的应用的规模，已经增长到可能会有一万个 client，同时访问你的应用了。

![图 25：C10K 问题与按请求创建线程（00:30:49）。](/assets/images/21/0025.webp)

图 25：C10K 问题与按请求创建线程（00:30:49）。

课件中的按请求创建线程示意，依赖未展开的 Request、get\_request 和 handle\_request：

```
while (true) {
    Request *rq = get_request();
    pthread_create(&tid, NULL, handle_request, rq);
    // 如果软件写得不好，就无法支撑 C10K
}
```

然后那个时候的机器，其实，一个服务器，多多少少，其实是可以扛住这个计算量的，对吧？就像，那个时候，虽然多处理器系统还不流行，但可能，已经有一些在服务器领域，已经有一些多处理器系统了，然后你基本上还是可以扛住这个 10,000。但是你的编程语言的机制，你的软件写得不好，你是扛不住这个一万个，相当于每秒一万个请求的并发。对吧，如果你写的是一个我今天上课一开始的时候说，你可以用所有的并发编程都可以用，线程 spawn/join 的模型来理解。所以你可以去创建一个 request。

对吧，你每次就像我刚才在那个 strace 里面看到的一样，你用系统调用去得到建立一个连接，然后建立完连接以后，你就用pthread\_create，创建一个线程，然后这个线程你就去跑吧，然后如果软件写得不好的话，你就没有办法支撑这个 c10k。所以，就这样的动机，1999 年的时候，大家提的这个问题，就催生了很多的，很多的操作系统上的进步，包括 epoll 这个系统调用，在 epoll 之前，其实我们也有一个系统，它叫 select，select 和 epoll 它的功能基本上是差不多的，也是说我可以监听多个文件描述符。

然后我等到任何一个文件描述符里面有数据，我就可以继续，但是 select 的 API 设计，并不是为这个 c10k 准备的，所以它在解决这个的时候，会有严重的性能问题，然后催生了一系列的这种，像 NGINX，事件驱动的架构，包括 Goroutine 这样的并发模型，都是在这个历史的背景下产生。然后等到 c10k 问题解决以后，很快，我就发现我，我如果能服务 1 万个 client，我就可以服务 1 亿个client。所以就有了这个 c10 million 的这样的问题。

当然这是 1000 万，有 1000 万个并发，那在这个意义上，因为我们的摩尔定律，还是相当于来说缓慢的发展，它是以年为单位，18个月为单位的，如果你一下子要从 10k 变到 10million，而且还有各种各样的负载的要求的时候，那事情就完全变了。
