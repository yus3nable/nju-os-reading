1999 年，Dan 提出了 C10K problem。C10K 指一万个 client concurrent，也就是并发客户端的问题。当时 web server 或应用规模，已经增长到可能有一万个 client 同时访问。

![图 25：C10K 问题与按请求创建线程（00:30:49）。](/assets/images/21/0025.webp)

图 25：C10K 问题与按请求创建线程（00:30:49）。

课件中的按请求创建线程示意，依赖未展开的 Request、get\_request 和 handle\_request：

```
while (true) {
    Request *rq = get_request();
    pthread_create(&tid, NULL, handle_request, rq);
    // 如果软件写得不好，就无法支撑 C10K
}
```

那时一台服务器的计算能力大体能承受这个量。虽然多处理器系统尚未普及，但服务器领域已经有一些，基本能扛住 10,000。可编程语言的机制或软件写得不好，就承受不了一万个、相当于每秒一万个请求的并发。前面说过，并发编程可以用线程 spawn/join 模型理解：每个 request 创建一个线程。

像刚才 strace 里看到的，用系统调用建立连接，再调用 pthread\_create 创建线程，让它去处理。如果软件写得不好，就无法支撑 c10k。1999 年提出的这个问题，催生了许多操作系统进步，包括 epoll 系统调用。在 epoll 之前有 select，功能基本相近，都能监听多个文件描述符。

任意文件描述符有数据，就能继续处理。但 select 的 API 设计没有针对 c10k，处理时会有严重性能问题。这一背景也催生了 NGINX 这样的事件驱动架构、Goroutine 这样的并发模型。c10k 解决后，很快又希望从服务 1 万个 client，增长到服务 1 亿个 client，于是有了 c10 million 问题。

当然，这指的是 1000 万个并发。摩尔定律的发展仍然比较慢，以年、18 个月为单位。如果一下从 10k 变成 10million，还要满足各种负载要求，情况就完全不同了。
