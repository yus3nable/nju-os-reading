如果一定要 consistency 和 availability，可以用单机，假设这台机器可信，you're consistent，you're available。如果需要 availability 和 partition tolerance，构建超大规模分布式系统，就必须在一定程度上牺牲 consistency。需要 consistency 和 partition tolerance 时，有些请求可能要等待，比如等拉黑请求确认后，下一个请求才能完成。从早期 Google 的几个分布式系统开始，设计者可能花了十年左右，把系统做到今天的程度：用户几乎感受不到 CAP 这个不可能三角，觉得微信保存数据安全、从来不丢，服务稳定，也几乎没有明显卡顿。CAP 的约束仍在，系统通过许多办法提供良好的使用体验。

DeepSeek 的 API Key 也有同样的问题。Key 用于 Authentication，还要计费，Dashboard 上会显示花了多少 Token、多少钱，但计费信息有延迟。比如一次 API 输入了很大的 context input，response 已经返回。

但刷新页面时，可能还要等几秒钟或一分钟，计费才显示出来。API Key 可以被多台机器使用，也可以随时 disable，这与先拉黑再发朋友圈的例子相近：请求大语言模型 Inference 的 API，同时又能把这个 API 下线，就会遇到 CAP Theorem 的约束。DeepSeek API 这样的业务系统，在数据中心里涉及很多工作。

一台机器可能有多个共享内存的 T\_worker，机器之间通过网络连接，还可能有跨数据中心的网络包。写 malloc/free 已经很痛苦，现在程序除了共享内存、网络，还要面对机器随时 crash、网络 delay。分布式系统中，一台机器从机架上断开，可能是电源断了，也可能是网线断了。

机器数量足够多，这些故障就不可避免，编程时必须考虑。仅仅考虑 malloc 并发已经很头疼，再加上机器随时可能消失，可以这样理解。
