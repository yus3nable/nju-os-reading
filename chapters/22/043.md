有一个系统调用叫 ioctl。手册说明，它的 control api 能向设备发送相关指令，比如改变终端大小或模式。所有非 data 的设备功能都通过 ioctl 实现，因此这一个 api 承载了设备驱动世界的大量复杂性。ioctl 的参数不加解释，直接交给驱动。应用可以构造特殊结构体，设备也可能是总线设计时尚未出现的类型，比如自己发明的 GPU、GPU 与 FPGA 联合体，或者核弹发射器。总线不知道它们有什么功能，怎样与设备通信？

只有应用程序和驱动知道。厂商可能附带一个配置应用，比如支持宏编程的鼠标。应用把配置发给驱动，驱动再让配置生效，都是通过 ioctl。它还承载打印机的卡纸、清洁、自动装订等功能，以及键盘跑马灯的配置。

假设自己做一个 TTY，它仍然通过读写数据完成终端功能。要再增加跑马灯，就需要 ioctl，加一个特殊字段，在字段等于特定值时控制灯亮暗、怎样跑。磁盘健康状态、缓存控制等配置也通过 ioctl。这是水面下的冰山：arguments, returns, and semantics of ioctl vary according to the device driver in question。

刚才的发射器通过 password 控制，也完全可以改用 ioctl：传入特定字符串查询设备，或者传入密码执行发射。对发射器这样的控制操作，我认为 ioctl 更合适。

刚才用 read、write，只是展示 override struct file 中的 operation，就能得到读写设备的能力。ioctl 则成了层层堆叠的屎山。
