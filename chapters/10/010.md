下一个例子是写 C 时常用的 gettimeofday。定义 struct timeval 类型的 t1、t2，在某个时间点调用一次 gettimeofday，另一个时间点再调用一次，就得到两个时间值，其中有 second 和 microsecond，也就是秒和微秒。

![图 81：gettimeofday\.c：两次取时之间睡眠 200 ms（00:56:45）。](/assets/images/10/0081.webp)

图 81：gettimeofday\.c：两次取时之间睡眠 200 ms（00:56:45）。

gettimeofday\.c 中的 main：

```
int main(void) {
    struct timeval t1, t2;
    if (gettimeofday(&t1, NULL) != 0) {
        perror("gettimeofday(t1)");
        return 1;
    }
    usleep(200000);  // 200 ms
    if (gettimeofday(&t2, NULL) != 0) {
        perror("gettimeofday(t2)");
        return 1;
    }
    long sec = t2.tv_sec - t1.tv_sec;
    long usec = t2.tv_usec - t1.tv_usec;
    long elapsed_us = sec * 1000000L + usec;
    printf("t1: %ld.%06ld\n", (long)t1.tv_sec, (long)t1.tv_usec);
    printf("t2: %ld.%06ld\n", (long)t2.tv_sec, (long)t2.tv_usec);
    printf("elapsed: %ld us (%.3f ms)\n", elapsed_us, elapsed_us / 1000.0);
    return 0;
}
```

将经过的秒数、微秒数换算后相加，就能知道两个时间点之间经过多久。这个程序在两次获取时间之间睡 200 毫秒，运行后打印 t1、t2，测得间隔大约 200\.062 毫秒。

![图 82：测得间隔 200\.062 ms（00:57:28）。](/assets/images/10/0082.webp)

图 82：测得间隔 200\.062 ms（00:57:28）。

调用系统调用也需要时间，会产生误差，所以虽然睡眠设为 200 毫秒，实际测量会稍大，多运行几次也差不多。gettimeofday 是一个系统调用，因为进程状态只有寄存器、内存，进程自己无法感知时间。以前游戏修改器里有个“变速齿轮”工具：理论上，只要改变时间相关系统调用的参数和返回值，就能改变进程感知的时间。例如拦截 usleep，把每次睡眠时间缩短到十分之一；再将每次 gettimeofday 的时间轴按十倍速度校准，就能给它假的时间。进程本身没有时间概念，必须通过系统调用。用 strace 看，会看到什么？

有 nanosleep，却没有任何 gettimeofday。再增加两次睡眠，先睡 200 微秒，再睡 200 微秒。程序正常执行，出现三个 nanosleep，中间仍然没有 gettimeofday。

打印的 t1、t2 也正确，清楚看到三个 nanosleep 分别间隔 200 毫秒，中间没有 gettimeofday。现在 libc 是自己编译的，可以调试。先看 usleep，musl 的实现很简洁：对于 200 毫秒的睡眠，构造一个 timespec，tv 的 second 为零，nano second 是对应数值，然后 return nanosleep，继续进入 clock\_nanosleep，直接进行系统调用。

再看 gettimeofday。虽然没有执行系统调用，代码和指令仍然确实执行了。它会进入 getclock，也就是 clock\_gettime，其中有 VDSO\_CGT\_SYM 条件编译。

之前提过，进程地址空间里有 vvar 和 vDSO 两块特殊内容：vDSO 是操作系统内核给每个进程提供的一段代码。

![图 89：VDSO\_CGT\_SYM 条件下走 vDSO 路径（01:01:47）。](/assets/images/10/0089.webp)

图 89：VDSO\_CGT\_SYM 条件下走 vDSO 路径（01:01:47）。

vvar 则是每个 CPU 共享的数据，包括当前 CPU、clock 等。现在的操作系统可能每秒有一千次中断，也可以配置为 100 次、250 次。时钟中断到来时，CPU 将自己的 clock 加 1。若不需要那么精确的时间，可以直接从这里得到大约一千分之一秒精度的时间。CPU 还有指令能读取精确的 cycle count；做过 RISC\-V CPU 的同学知道这种计数。配合 cycle count，就能算出比较精确、与物理时间对齐的当前时间，也就是结合相对时间与较精确的 CPU 内部时钟。这里调用 cgt，第一次进入 cgt\_init，是 lazy 加载，也就是懒加载，沿着这条路径调用 \_\_vdsosym。

\_\_vdsosym 从哪里找到 Linux 2\.6\.39 的 \_\_kernel\_clock\_gettime？它直接解析 ELF，Program header 就是指向这片位置的指针。

VDSO 位置来自 auxv，也就是 Auxiliary Vector、辅助向量。进程初始化时，int 类型的 argc、argv 参数数组和环境变量后面，还有辅助向量。豆包也指出，其中有可用的真随机数种子和 VDSO 位置。遍历辅助向量找到 AT\_SYSINFO\_EHDR，就能找到 VDSO 程序头表，再像加载器那样解析 ELF，遍历其中的符号表。
