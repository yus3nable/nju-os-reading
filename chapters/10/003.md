怎样编译可调试的程序？大家都知道，对 test\_debug\.c 加上 \-g，再用 GDB 调试 a\.out，就能看到代码。

![图 7：加上 \-g 后停在 main 的 printf 语句（00:08:55）。](/assets/images/10/0007.webp)

test\_debug\.c：

```
#include <stdio.h>

int main(int argc, char **argv) {
    printf("Hello from main()!\n");
    return 0;
}
```

再 step 进去，进入的是动态链接的 glibc，又看不到源代码，这就是上节课失败的现场，原因是没有完成 libc 的编译。

图 8：继续进入系统 libc，源代码仍不可见（00:09:13）。

编译时会在二进制文件中打包一份源代码，某种程度上这就是 DebugInfo。库文件可能是 \.a、\.so，源文件也会先生成 \.o 再链接，例如 main 所在的 test\_debug\.c，这些都是计算机系统基础课的内容。把源代码相关信息放进去，调试时就能根据行号找到源代码。例如用 musl\-gcc \-static test\_debug\.c，再加 \-g，生成带调试信息的程序，现在就能看到 CRT 中的 crt1\.c，也就是 musl\-gcc 所使用的代码。调试信息到底是什么？ICS 课会告诉大家，加 \-g 就可以调试。

![图 9：使用自编译 musl 后进入 crt1\.c（00:10:06）。](/assets/images/10/0009.webp)

图 9：使用自编译 musl 后进入 crt1\.c（00:10:06）。

但它具体做了什么？问豆包，它会解释：在程序 ELF 文件的某些节中放入额外信息。可以用 readelf 查看这些调试信息。

看不懂时，可以把 readelf \-a 的完整输出交给大语言模型。它有足够的知识，能指出与调试相关的 section，说明它们是 DWARF 调试信息的标准 section。例如，\.debug\_aranges 是内存地址到编译单元的映射，一个 \.c 就是一个编译单元。

DebugInfo 还包含类型、变量、函数等核心信息，以及调用栈展开、调试字符串表、Locations 等。模型提到了 DWARF 这个调试标准，感兴趣可以查看。我不会在课堂上花时间读整份手册，觉得大家应该下载一个能读网页或手册的 Skills，用它遍历网上手册。这里还有命名梗：DWARF 是矮人，ELF 是精灵。DWARF 有 bytecode 指令集，功能超过把源代码的一行映射到某段汇编。即使没有任何 debug info，GDB 也能在一定程度上知道程序运行到哪里。

因为 ELF 有符号表，用 nm a\.out 可以查看。符号表给出一个个入口，例如 main 位于 text 的 0x4002e8。

![图 17：nm 显示符号与地址（00:14:11）。](/assets/images/10/0017.webp)

图 17：nm 显示符号与地址（00:14:11）。

PC 走到 0x4002e8，就知道 main 开始执行了。再调试看看，在 main 上设置断点，实际停在 2f8，比 2e8 更准确一些。

![图 18：main 的断点设置在 0x4002f8（00:14:30）。](/assets/images/10/0018.webp)

运行后，［听辨不清，00:14:38］，debug info 给出更精确的程序位置，忽略了函数前面的入口指令，提供更好的汇编与源代码对应关系。仅凭符号表，也能知道现在位于 main 加 16。

![图 19：main 入口 0x4002e8 与断点位置之间的指令（00:14:54）。](/assets/images/10/0019.webp)

图 19：main 入口 0x4002e8 与断点位置之间的指令（00:14:54）。

0x4002e8 对应 main 加 0。调试时有 PC 和符号表，就至少知道处于哪个函数，已经可以实现调试器；继续执行时，却不知道对应 main 中哪一处源代码。要更精确，就必须知道一条语句对应哪段 PC 范围。

![图 20：同一断点对应 test\_debug\.c 的第 4 行（00:15:17）。](/assets/images/10/0020.webp)

图 20：同一断点对应 test\_debug\.c 的第 4 行（00:15:17）。

这是假设编译器未优化。如果允许指令重排、内联，乃至打乱语句执行顺序，对应关系就会复杂，调试优化代码会遇到困难。未优化时，一条 C 语句基本能对应连续的一段汇编。前面 SimpleC 也展示了简化 C 直接翻译成汇编的能力。binutils 中有 addr2line 工具，可以把 PC 地址转换为源代码行。

![图 21：addr2line 的命令与选项（00:16:13）。](/assets/images/10/0021.webp)

图 21：addr2line 的命令与选项（00:16:13）。

以前知道这个工具后，需要读手册、花时间实验，确认其行为；现在可以让 AI 完成，只要知道 addr2line 有用，就能让它做实验。它执行 addr2line \-e a\.out \-f。以前 \-e、\-f 需要自己查手册，现在交给 AI 即可。这里查询 0x4002e8，也就是刚才的 main。

![图 22：addr2line 将地址映射到 main 和 \_\_libc\_start\_main（00:17:07）。](/assets/images/10/0022.webp)

图 22：addr2line 将地址映射到 main 和 \_\_libc\_start\_main（00:17:07）。

现场使用的地址查询命令：

```
addr2line -e a.out -f 0x4002e8
addr2line -e a.out -f 0x400594
```

它找到了 0x4002e8 对应 main，位于 test\_debug\.c 第三行，应该没问题。它又试了 0x400594，也找到 musl libc 中的 \_\_libc\_start\_main。凭这个工具就可以实现自己的调试器，这里确实得到了正确结果。

![图 23：地址、函数名与源文件行号的对应结果（00:17:33）。](/assets/images/10/0023.webp)

图 23：地址、函数名与源文件行号的对应结果（00:17:33）。

DWARF 中还包含一个小解释器，类似编程语言，可以访问寄存器。例如 EBP、RBP 这样的 frame pointer 标记栈帧位置，有时需要从寄存器取地址，再做算术，才能得到变量值。它甚至是图灵完备的指令集，有分支，理论上可以写程序恢复任何变量的值；设计用途则是描述某个 PC 范围内变量值在哪里、如何计算。调试 int x 时，X 可能在寄存器、内存中，也可能被优化掉，已经不存在，这些都要在 DWARF 中写清楚。有时看到 optimized out，就是无法查看值。调试信息一定程度上负责恢复这些值；调试信息生成得好，或者换调试器、换编译器，有时就能恢复更多信息，看到变量值。DWARF 的 bytecode 也用于 C\+\+ 异常的 stack unwinding。抛出异常会弹出栈帧，恢复到上一个调用者的位置，有点像上节课的 longjmp，也需要 debug info。这就是调试信息。
