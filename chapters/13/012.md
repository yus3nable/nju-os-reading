并发的麻烦还不止不确定性，系统的其他部分也会相互影响。今天一直使用 SimpleC 模型：C 程序由栈帧和全局变量组成，每次从 top frame 取一条指令或语句执行，模型很清楚。我一直想，能否找同学做毕业设计，或者做一个 hobby project，vibe code 一个 SimpleC 解释器。

它要 fully functional，能解释任何 C 程序，包括操作系统上复杂的图形界面程序，直接在源代码层面运行。做成可用的解释器后，就能像调试器一样做很多有趣的事。但实际世界比 SimpleC 复杂，所有人都追求性能，因为性能意味着钱：程序快一倍，解决相同问题只要一半计算机，成本降到二分之一。DeepSeek 把 token 价格降下来以前，用 OpenAI 模型很贵，大家都应该感谢它。可能因为还没大量用 token，大家感受不深；大量使用后就知道大模型仍然贵。今天性能更重要。为编译优化奠基的 Frances Allen 在 2006 年获得图灵奖，编程语言领域还有更多获奖者。

编译器会优化 SimpleC 中的纯计算。例如连续三个 x\+\+，因为计算 deterministic，初始状态确定，目标状态就确定，可以合并成 x \+= 3。有一类内容不能优化，就是 system call。如果 syscall 要使用 X，就不能跨过这条边界优化。syscall 前的三个 x\+\+ 可以合并为 x \+= 3，后面再有一个 x\+\+，却不能一起改成 x \+= 4，否则 syscall 使用的值、输出字符都变了，偏离预期。编译器把 system call 视为绝对不可优化的操作，在这个范围内则能任意修改。并发时，麻烦也随之出现：这些优化针对 Deterministic 程序，假设不必考虑其他线程此时把 X 写成别的值。

如果必须考虑其他线程随时改值，就无法做这种优化。例如两次 X 等于 X 加 1，中间别的线程可能写 X 等于 0，就不能合成 X 加 2。编译器假设程序顺序执行。
