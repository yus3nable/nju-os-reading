有了线程库，可能连一加一都不会求了。两个线程各执行 N 次 sum\+\+，最后还能得到 2N 吗？不一定。编译运行这个程序，多跑几次，结果各不相同，因为线程执行顺序不同，可能按 12121212 这样的顺序交错。一次 sum\+\+ 也包含多个步骤。

sum\+\+ 有三个操作：load，将 sum 读进寄存器；寄存器加加；再写回内存。如果写回之前，别人也执行了 sum\+\+，就可能覆盖对方写入的值。例如我读到 1000。

接着准备写 1001，第二个线程却已经依次经过 1001、1002、1003、1004、1005，写到 2000。此时我再写 1001，就把 2000 覆盖了。两个线程相互读取、覆盖，最后并没加多少。眼前还没有办法把它写对，连最简单的程序都很难理解。我曾把下面的问题用作期中考试题。

```
void T_sum() {
  for (int i = 0; i < 3; i++) {
    int t = load(sum);  // 假设单行语句的执行是原子的
    t += 1;
    store(sum, t);
  }
}
```

后来又做成 OJ 题，也可能成为大家期中、期末测验的概念题。创建三个线程，每个执行三次 sum 加加，每次先 load 到临时变量，再加 1，最后 store 回去。假设模型每次执行一行语句，可以选 T1、T2 或 T3 的一条语句。

sum 最小能是多少？第一反应往往是 3。当时的 OJ 要提交执行顺序，例如 123412，或者 T1、T2、T1、T2 这样交错，得到最小值，结果做得惨不忍睹。2025 年，DeepSeek R1 和 o3\-mini 这两个最强推理模型也都失败了。去年我可以比较安全地说，还没有人工智能能不调用第三方工具、只靠文本推理解决它。

但到 2026 年，国产模型也能做对：仍在灰度测试的 DeepSeek Expert、Qwen\-3\.5\-max、GLM\-5\.1，在禁止调用工具的条件下都做对了。小一号的 DeepSeek Instant、Qwen\-3\.6\-plus 还做不对，能力仍不够。困难在哪里？我 vibe code 了一个有多个线程的小游戏。

图 48：顺序一致性小游戏：全局读写顺序（00:50:29）。

绿色是线程 2，蓝色是线程 1，红色是线程 0。各线程内部事件、代码顺序固定，不能把 T0 的第一个事件移到第二个后面，但线程之间可以任意交错。每个事件读写哪个变量、读到或写入什么值，都已经给出。例如 T2 读到 X 等于 0，随后写 X 等于 2，T1 再两次读到 X 等于 2。这个 X 等于 2 的事件不能拖到最前面，还要调整其他事件，让每次读都看到最近写入的值，形成 123456 这样的全局顺序。再建一个 puzzle，这次顺序不对，为什么？

![图 49：小游戏报告不符合读值的顺序（00:51:37）。](/assets/images/13/0049.webp)

图 49：小游戏报告不符合读值的顺序（00:51:37）。

T1 先读 Y 等于 0，正确；再读 Y 等于 2，就不对。把 T2 写 Y 等于 2 的事件挪到前面，才符合读到的值。随机生成几次，会遇到怎么调整都绕不过去的题，因为给定每个线程各自看到的读写历史，再判断能否组合成全局顺序，是 NP 完全、NP complete 的问题。

这件事本身 NP 难，求 sum 最小值也 NP 难，需要不断尝试。答案可以是 2。构造方法是：让 T1 在最后一次循环 load 一个 1，最后 store 一个 2。先让线程 2 load 一个 0，暂时不写，等稍后再 store 一个 1。

相当于让它 sleep，到指定时刻才 store。线程 1 则做自己的三次循环：load 0、store 1，load 1、store 2，等预留的线程 2 写回 1 后，再 load 1，但延迟很久才执行最后的 store 2。在这次写入之前，让其他线程全部跑完。无论有多少线程，都能用这种极端顺序，最后得到 2。

这些细节只是智力游戏，像刚才的 verifying sequential consistency，可以让大家排列事件。重要的是，失去确定性以后，原本只有 syscall 不确定的顺序程序，变成每一步都不知道会选谁执行的模型。这正好对应 deterministic 与 Non\-deterministic 图灵机的区别，联系到 NP 问题。单线程与 non\-deterministic 多线程模型，有这种深刻的理论联系，带来的困难已经困扰人类很多年。
