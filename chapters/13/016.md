两个线程，t1 执行 x 等于 1、load y，t2 执行 y 等于 1、load x。给四个事件编号 1234，按线程内顺序执行，可以怎样排列？1234 时，load y 得到 0，load x 得到 1。也可以考虑以 12 开头，但 1243 不行。那么 1324 呢？

1324 和 1342 都可以。1324 中，13 执行完，x、y 都等于 1，两次读取都是 1；1342 也一样。无论怎样排，1、3 至少有一个先执行，线程内 2 不能在 1 之前，2、4 也不能先执行，所以 x、y 至少有一个是 1。结果可以是 10。

也可以是 01、11，但看不到 00。不过，考虑处理器也是编译器，就应该能看到 00。写 x 等于 1 时，只写入自己的内存，还没传到另一个 CPU。

对方的内存还没更新，就先读了。这种令人担心的行为能直接用代码观察。准备的代码稍长，和刚才举旗子相似，有 T1、T2 两个线程。

![图 68：实验代码中的原子 flag（01:19:30）。](/assets/images/13/0068.webp)

图 68：实验代码中的原子 flag（01:19:30）。

```
atomic_int flag;
#define F1 1
#define F2 2
#define FLAG \
    atomic_load(&flag)
#define FLAG_XOR(val) \
    atomic_fetch_xor(&flag, val)
#define WAIT_FOR(cond) \
    while (!(cond))    \
        ;
```

T1、T2 等我把两面旗子同时举起后执行，再打印结果。随后放下、重新举起旗子，反复运行实验。为把代码写对，用了不少大家尚不知道的内容。

例如 atomic\_load、fetch、异或。忠告仍是 don't play with shared memory。按前面的理论，应当看到 10、01、11；实际运行却几乎只看到 00。处理器为了快，写完马上就读，两个线程都在 x 等于 1、y =1 之后被中断的概率很低。

如果两者都被中断，之后的两次 load 就能看到 1，但这很罕见。可以多做实验，这也是我喜欢的 unix's philosophy。刚才的程序会无限重复实验。

加 head 就能限定次数，再排序、用 uniq 合并相同项，得到统计。这次做 10 万次，约 6 万次是 00、4 万次是 01，10 很少。

![图 72：十万次实验：head、sort 与 uniq 统计（01:21:11）。](/assets/images/13/0072.webp)

图 72：十万次实验：head、sort 与 uniq 统计（01:21:11）。

```
./test-rmo | head -n 100000 | sort | uniq -c
  60458 0 0
  39527 0 1
     15 1 0
```

这也和打印有关，没有出现 11。它说明此前用来理解程序的模型，到了并发中已经不够。这个模型对顺序程序很好，课堂也一直使用，但并发让这些认识失效。这就是“入门到放弃”要说明的重要内容。
