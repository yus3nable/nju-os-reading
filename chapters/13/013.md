假设想实现 Join。并发编程有一个我会反复讲的视角：把线程想象成人，各自有大脑，互相读不到想法，能读别人的想法会很危险。SimpleC 中，局部的 private 内容也一样：只要线程不主动泄露指向自己栈的指针，别人就读不到。每个人头脑里的 memory 对应自己的栈，教室中的物理空间对应全局变量。大家共享教室，可以同时对同一个物体动作，例如都伸手去拿它。由此可以设计协议。

想等别人算好某个结果再继续，就给对方一面旗子，用变量 flag 表示，初始为零。自己执行 while(\!flag) 等待，相当于看着那位同学，只要旗子没举起来，就继续等。

某一刻对方写 flag 等于 1，举起旗子，等待线程退出 while，继续执行。看起来程序应该能实现等待，但实际上可能不行。编译器认为没人会改 flag，会怎样处理这个循环？

例如循环中有 sum 加等于 x 加 1，编译器发现 x 没改，就能把计算提到循环外，写成 t 等于 x 加 1，再在循环中 s 加等于 t，t 还可以直接放进寄存器。编译器会不断等价改写，让代码更快。同样改写 while (\!flag)，会发生什么？

它可以先 if (flag)，为真就什么也不做；flag 为零，既然假设没人改它，就永远无须再读，直接进入死循环。也就是把判断提到循环外：旗子已举起就退出，没举起就再也不会举起，于是一直循环。

```
if (flag) {
} else {
  while (1);
}
```

以前的论文中，很多有经验的系统程序员会写这种 ad hoc synchronization，觉得很快，却在某次编译时惹出麻烦。我觉得到了 AI 时代，再也不会有人犯这种错。再看编译优化究竟带来多大影响。
