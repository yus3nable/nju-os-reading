看一个简单例子：创建两个完全一样的线程，执行同一段转 100 块钱的代码。第三行设定账户只剩一百块，每个线程也要转一百块。

![图 34：alipay\.c：两个线程各扣 100（00:42:37）。](/assets/images/13/0034.webp)

图 34：alipay\.c：两个线程各扣 100（00:42:37）。

```
#include <thread.h>

unsigned long balance = 100;

void Alipay_withdraw(int amount) {
  if (balance >= amount) {
    balance -= amount;
  }
}

void T_alipay() {
  Alipay_withdraw(100);
}

int main() {
  spawn(T_alipay);
  spawn(T_alipay);
  join();
  printf("balance = %lu\n", balance);
}
```

余额足够，就扣掉转账金额，当然还可能给另一个账户加上。第一个线程发现够一百块，就扣掉；第二个线程再检查，发现不够，走 else 分支，不再扣。实际运行，余额为零，看起来没有问题。但执行过程中，速度稍有变化会怎样？

![图 35：检查后插入 usleep（00:43:35）。](/assets/images/13/0035.webp)

图 35：检查后插入 usleep（00:43:35）。

脑中要同时考虑两个线程。如果两者一样快，同时执行第五、第六行判断，都会认为余额足够。账户只有一百块，却都想扣一百块，于是扣了两次，余额变成负数。变负以后会怎样？

![图 36：余额从 0 变为无符号大数（00:44:19）。](/assets/images/13/0036.webp)

图 36：余额从 0 变为无符号大数（00:44:19）。

这里用 unsigned integer，账户里就像多出了无穷的钱。我记得类似 bug 并不少见，未必由并发导致。大家还没入学时，食堂附近有台打印或其他用途的机器，能用类似方式把余额变负，然后无限继续使用。我不记得具体 bug，但应该实际 reproduce 过。这类问题在实际系统也会发生。再看一个游戏复制物品的 bug，属于并发事件，未涉及并行执行，和前面将 check、检查与写入分开的情形很像。先打开包裹，分离出一块钱。

把要复制的物品丢到地上，关闭包裹，再用鼠标点击地上物品，人物就会走过去拾取。此时手上有一块钱，点击它会产生鼠标事件，需要把一块钱这个对象放进某个变量。

图 41：点击地上物品并打开包裹（00:45:44）。

这个变量表示“拿起来的东西”。人物马上拾取地上物品的瞬间，再点起包裹里的一块钱，原本写入的一块钱对象，就被地上物品覆盖了，应该是某个全局变量被覆盖。结果物品复制成两份，相当于一块钱换来两份物品，现在有 198 块钱。

![图 42：拾取瞬间点击包裹中的金币（00:46:30）。](/assets/images/13/0042.webp)

图 42：拾取瞬间点击包裹中的金币（00:46:30）。

一百块分出一块，剩下 99，再变出两份 99，最后得到 198，可以无限复制。游戏例子是事件并发，支付宝例子是在多处理器上实际并行，两种不确定性都会带来破坏性后果。
