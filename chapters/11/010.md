接下来看动态链接的 a\.out 怎样加载。这里有一个静态链接的程序，也可以用 musl\-gcc 编译 a\.c，得到动态链接的 ELF 文件。不过，它的 interpreter 和 gcc 生成的不同，再对照看看。

![图 71：musl\-gcc 与 gcc 生成不同 interpreter（00:57:59）。](/assets/images/11/0071.webp)

图 71：musl\-gcc 与 gcc 生成不同 interpreter（00:57:59）。

稍后再解释 interpreter 是什么，以及为什么不同。调试之前先想静态链接和动态链接的差别，会遇到一个先有鸡还是先有蛋的问题：所有文件都有一个 \_start。

![图 72：动态链接程序的加载：crt1\.o、入口与解释器（00:58:06）。](/assets/images/11/0072.webp)

图 72：动态链接程序的加载：crt1\.o、入口与解释器（00:58:06）。

无论静态链接还是动态链接，ELF 文件里都有一个 entry，指向 \_start 符号，\_start 在 crt1\.o 中。那么 crt1\.o 是静态链接还是动态链接的？它还会调用 \_\_libc\_start\_main，这个函数又应该怎样链接？\_\_libc\_start\_main 已经属于库函数代码，应该在系统中只有一份副本，以节省空间，所以要动态链接。动态链接的 a\.out 映射到内存后，到底由谁加载 \_\_libc\_start\_main？仔细想，会发现有很多细节，答案就藏在文件里。

对 musl\-gcc 编译出的动态链接 a\.out 执行 file，会看到一个叫 interpreter 的域，即解释器。

![图 73：ld\-musl\-aarch64\.so\.1 链接到 musl libc\.so（01:00:13）。](/assets/images/11/0073.webp)

图 73：ld\-musl\-aarch64\.so\.1 链接到 musl libc\.so（01:00:13）。

interpreter 决定加载初始阶段要做什么。动态链接二进制文件执行的第一条指令位于 interpreter 的 \_start，程序自己的 \_start 此时还没有执行。我觉得期末考这个题，至少一半同学可能会做错。静态链接的 a\.out 用 start i，会停在程序的 \_start，我们调过很多次；动态链接的 a\.out 则不同。看看 interpreter 的符号链接：ld\-musl\-aarch64\.so\.1 直接链接到 musl libc 的 so。用 gcc 编译 a\.c，interpreter 则是 glibc 中的 ld\-linux\.so；如果用 x86，就是 ld\-linux\-x86\-64\.so。

![图 74：crt1\.o 的 \_start 与 libc 中 \_\_libc\_start\_main 的关系（01:01:07）。](/assets/images/11/0074.webp)

图 74：crt1\.o 的 \_start 与 libc 中 \_\_libc\_start\_main 的关系（01:01:07）。

这就是所有动态链接程序统一的加载器入口。回到 musl\-gcc 的程序，还是用 start i 调试。这次停在 \_dlstart，a\.out 的 \_start 还没执行；这里的 \_dlstart 由 entry 指定。

![图 75：starti 停在 interpreter 的 \_dlstart（01:01:43）。](/assets/images/11/0075.webp)

图 75：starti 停在 interpreter 的 \_dlstart（01:01:43）。

切到汇编，可以看到前面有一小段跳板代码，随后进入 \_dlstart\_c，这时就能看到源代码。这是 musl libc 中的加载器。process initial stack，即进程初始栈，仍然一样：sp 指向 argc、argv、envp 和辅助向量。

![图 76：\_dlstart 的汇编入口（01:01:59）。](/assets/images/11/0076.webp)

图 76：\_dlstart 的汇编入口（01:01:59）。

现在执行的是动态加载器的 interpreter 代码。它会妥善安排参数等内容，再做动态加载，负责加载程序需要的全部动态链接库，包括 libc。在这个 musl 程序中，不需要额外加载库函数，因为 musl libc 的 ld\.so 与整个 libc 链接在一起，前面看到的就是这个符号链接。

![图 77：\_dlstart\_c 从栈中读取 argc、argv 与辅助向量（01:02:31）。](/assets/images/11/0077.webp)

图 77：\_dlstart\_c 从栈中读取 argc、argv 与辅助向量（01:02:31）。

![图 78：动态加载器中的后续处理（01:02:41）。](/assets/images/11/0078.webp)

图 78：动态加载器中的后续处理（01:02:41）。

ld\.so 直接符号链接到 libc，所以不需要再加载额外的库。加载器完成所有动态链接库的加载后，才调用程序的 \_start。这里的 5555 就是程序 \_start，也就是之前调试过的 crt1\.o 中那一小段代码。

![图 79：加载后回到 a\.out 的 \_start（01:03:26）。](/assets/images/11/0079.webp)

图 79：加载后回到 a\.out 的 \_start（01:03:26）。

![图 80：a\.out 的入口进入 crt1\.c（01:03:30）。](/assets/images/11/0080.webp)

图 80：a\.out 的入口进入 crt1\.c（01:03:30）。

它再跳到 libc 的 start\_main，即 \_\_libc\_start\_main，再由它跳回 main。这部分代码在 libc 中，crt1\.o 不包含它，动态加载阶段已将它加载进来。过程有些绕，需要记住 a\.out 中有 interpreter 域，用 readelf \-a 可以看到。

![图 81：继续进入库代码时的调试状态（01:03:51）。](/assets/images/11/0081.webp)

图 81：继续进入库代码时的调试状态（01:03:51）。

Program Header 中有 interpreter，写着 Requesting program interpreter，路径是 /lib 下的 ld\-musl\-aarch64\.so\.1。

![图 82：Program Header 中的 interpreter 路径（01:04:15）。](/assets/images/11/0082.webp)

图 82：Program Header 中的 interpreter 路径（01:04:15）。

这是字符串，可以强行修改。例如把 64 改为 65，做一次非法操作。再执行 a\.out 就失败了，因为找不到 interpreter。用 readelf \-a 看，会发现 Requesting program interpreter 已改成需要 /lib 下的 ld\-musl\-aarch65\.so\.1。

![图 83：修改 interpreter 路径后执行失败（01:04:56）。](/assets/images/11/0083.webp)

图 83：修改 interpreter 路径后执行失败（01:04:56）。

现在创建这个文件，给 aarch64\.so\.1 做一个链接，让 ld\-musl\-aarch65\.so\.1 指向 ld\-musl\-aarch64\.so\.1。文件存在以后，a\.out 就能执行了。

![图 84：将 aarch65 解释器路径链接到已有的 aarch64 文件（01:05:17）。](/assets/images/11/0084.webp)

图 84：将 aarch65 解释器路径链接到已有的 aarch64 文件（01:05:17）。

创建解释器符号链接的命令：

```
sudo ln -s /lib/ld-musl-aarch64.so.1 /lib/ld-musl-aarch65.so.1
ls -l ld-musl*
```

再调试时，需要留意 interpreter 完全由 program header 中的一段字符串决定。可以在 AI 帮助下重新读内核 ELF 加载器代码：字符串写什么，加载器就找到那个文件，把它作为 ELF 加载到内存。

刚执行 starti，停在第一条指令时，musl 的 libc 就已经在地址空间中了。这是操作系统加载的 ld\.so。

![图 86：musl 程序第一条指令时的地址空间（01:06:21）。](/assets/images/11/0086.webp)

图 86：musl 程序第一条指令时的地址空间（01:06:21）。

这个文件已经映射到进程地址空间，其他库还没有映射。glibc 的情况类似：执行 starti 后，用 info proc mappings 查看地址空间，a\.out 已经加载，vvar 和 vDSO 也已经加载。

![图 87：glibc 程序第一条指令时尚未映射 libc（01:06:50）。](/assets/images/11/0087.webp)

图 87：glibc 程序第一条指令时尚未映射 libc（01:06:50）。

这些由内核完成，ld\-linux 这个 interpreter 也已加载。但 glibc 的 libc\.so 此时还不在地址空间中。可以在 \_start 或 main 处打断点，这里选 \_start，再 continue。重新看地址空间，libc 就已经加载进来了。这样就能精确描述进程第一条指令执行时的状态。

![图 88：运行到程序 \_start 时，libc 已映射进来（01:07:23）。](/assets/images/11/0088.webp)

图 88：运行到程序 \_start 时，libc 已映射进来（01:07:23）。

执行第一条指令时，有 sp 指向的 initial stack，其中包括 argc 等内容；有 a\.out 中需要加载的部分；还有 Program Header 的 interpreter 所指定的二进制文件，它也是 ELF。这就是真实 linux 中 a\.out 的初始状态，没有其他内容。接着程序开始执行指令，此时 pc 指向 interpreter 的 \_start。可以看一下，现在是 glibc 的 \_start。

![图 89：glibc 动态加载器自己的 \_start（01:08:32）。](/assets/images/11/0089.webp)

图 89：glibc 动态加载器自己的 \_start（01:08:32）。

地址在 7ff 这里，二进制文件自己的 \_start 还没开始执行。初始 pc 指向解释器 ELF 的 entry。解释器就是 Program Header 中 requesting 后面的字符串指定的内容。这个字符串确实能改，刚才就把 64 改成了 65。

![图 90：进程初始状态与 PC 指向的 interpreter（01:08:57）。](/assets/images/11/0090.webp)

图 90：进程初始状态与 PC 指向的 interpreter（01:08:57）。

文件不存在时，内核拒绝加载；文件存在，就可以正确加载。加载器也可以换成自己实现的版本，回去 vibe code 一个动态加载器，它确实可以工作。这就是动态链接和动态加载。我觉得这个细节很重要：从简单的 static、musl\-gcc 开始，逐步讲到真实 Linux a\.out 的初始进程状态。
