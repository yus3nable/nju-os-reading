bloat\.c：

```
__attribute__((noinline, used))
void bloat() {
    asm volatile(
        ".rept 10485760 \n\t"
        "nop\n\t"
        ".endr\n\t"
    );
}
```

编译花的时间比预期长一些。看一下，这是一个 4 兆的……ARM 上一个 nop 是四个字节；x86 上一个 NOP 是 0x90，占一个字节。所以这里生成的文件有 40 兆大，libbloat\.so 中有 40 兆的 nop 指令序列。sample\.c 会先调用 dlopen。

这部分是 vibe coding 的：我要求加载 libbloat\.so，再调用 bloat 函数，也就是刚才那段内联汇编。

![图 59：sample\.c：dlopen、dlsym、调用和休眠（00:50:09）。](/assets/images/11/0059.webp)

图 59：sample\.c：dlopen、dlsym、调用和休眠（00:50:09）。

sample\.c 中的 main 片段：

```
int main() {
    // This is vibe-coded. Asked AI to load dynamic library.
    void *handle = dlopen("./libbloat.so", RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "dlopen error: %s\n", dlerror());
        _exit(1);
    }
    void (*bloat)() = (void (*)())dlsym(handle, "bloat");
    if (!bloat) {
        fprintf(stderr, "dlsym error: %s\n", dlerror());
        _exit(1);
    }

    bloat();
    printf("Executed bloat() at %p\n", (void*)bloat);
    sleep(1000);
}
```

执行完 40 兆的 nop 后，用 %p 打印执行的 bloat 地址。现在可以运行 sample，也可以放到后台。多运行几次，后台就有不少 sample，会看到它们打印的地址位于各自地址空间的不同位置。

![图 60：多个 sample 后台进程及各自打印的地址（00:50:49）。](/assets/images/11/0060.webp)

图 60：多个 sample 后台进程及各自打印的地址（00:50:49）。

这是地址空间随机化的结果。调用 mmap 时，如果没有要求必须映射到指定位置，它就会根据地址空间布局找一个有一定随机性的地址。虽然都在 7FF 这个范围内，bloat 的映射位置仍然不同。整个操作系统中，bloat 是否只有一份内存副本？先把这些进程都杀掉。一个 libbloat\.so 有四十兆，创建 1000 个进程看看。直接开一个 agent，要求 run 1000 个 sample in background，连写脚本都不用单独要求。它写好脚本，并报告已在后台启动 sample 1000 次，看看有没有。

每个进程各占 40 兆，合计就要约 40G 内存。如果每个后台 sample 都有独立拷贝，系统早就出问题了，但现在仍然流畅。这就证明，sample 使用的这段很长的二进制库函数，在整个系统中，磁盘和内存都只有一个副本。还可以继续问。记得 /proc 下 pid 的 fd 吗？管道可视化中多次用它查看进程打开的所有文件。也可以看 mmap 的情况。例如查看 sample 进程 20542 在 /proc 下打开的文件描述符，再看它的 maps。
