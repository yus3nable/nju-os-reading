加载器还有一个隐藏特性，叫 Shebang，shell 的 bang。大家写脚本时都用过，看看它怎样工作。

这里可以写 bash、python，或者任意一个可执行文件。这样，脚本也可以当作可执行文件来执行。

![图 44：输入 \#\!/bin/bash 和 echo Hi，Vim 提示尚未保存（00:35:56）。](/assets/images/11/0044.webp)

图 44：输入 \#\!/bin/bash 和 echo Hi，Vim 提示尚未保存（00:35:56）。

a\.sh：

```
#!/bin/bash
echo Hi
```

我这里有一个 a，也可以把它改成 a\.sh。

![图 45：file、chmod \+x 和脚本文件权限（00:36:02）。](/assets/images/11/0045.webp)

图 45：file、chmod \+x 和脚本文件权限（00:36:02）。

刚才用 chmod \+x 把 a\.sh 设为可执行，现在直接执行就得到 Hi。但它是文本文件，为什么也能执行？大家用过这个特性，有没有想过用 strace 看一下？假如有一个 a\.txt，能 strace 吗？用 bash 读取 a\.txt，可以打印 hello。后缀名无所谓，里面写的是 echo hello。

![图 46：执行 a\.sh，以及通过 bash 读取 a\.txt（00:36:49）。](/assets/images/11/0046.webp)

图 46：执行 a\.sh，以及通过 bash 读取 a\.txt（00:36:49）。

那能 strace a\.txt 吗？应该用点杠 a\.sh，不能用点杠 a\.txt；后者会失败，提示 Permission denied。strace 点杠 a\.sh 则可以看到完整日志，说明 execve 可以执行脚本。换句话说，可以直接写一个 c 程序。

![图 47：strace 日志从 execve("\./a\.sh") 开始（00:37:03）。](/assets/images/11/0047.webp)

图 47：strace 日志从 execve("\./a\.sh") 开始（00:37:03）。

在 c 程序中 execve a\.sh 或 execve a\.py，都可行，会得到这样的系统调用序列。a\.sh 可以执行，这个行为百分之百也在 Linux 内核加载器中实现。同样可以像刚才那样，直接问 Linux 内核里的代码。fs 下有 binfmt\_script\.c，也是加载器的一部分；刚才看的是 binfmt\_elf\.c。Linux 内核支持 ELF 格式和 script 格式的二进制文件，各自有对应的加载器。这里有一段硬编码在 Linux 中的判断：先读文件头，再根据内容识别 ELF、a\.out 或 buf\[0\] 对应的格式。Linux 现在应该已经不默认支持 a\.out 格式了。

BSD 还可以加载 a\.out 二进制文件。只有 buf\[0\] 和 buf\[1\] 分别为井号、叹号时，加载器才会继续，把它当作 script 执行。看这个例子：我有一个 a\.c，编译后打印全部参数。执行点杠 a，后面写 12345。上次课前有同学问 argv0 是什么，它就是命令行里的参数。当我写一连串点杠时……

![图 48：A 程序打印 argv\[0\] 及各个参数（00:39:10）。](/assets/images/11/0048.webp)

图 48：A 程序打印 argv\[0\] 及各个参数（00:39:10）。

argv\[0\] 就是命令行中这个写法，后面才是传入的其余参数，可以是 12345、hello、world，也可以是 123456。用引号括起来会当作一个参数，没有引号就会分成几个参数，所以 argv\[1\] 是 hello，argv\[2\] 是 world，argv\[3\] 是 123456。这就是 A。再写一个名为 S 的 script，采用熟悉的 /bin/bash 那样的井号叹号写法。但这里指定的二进制文件是 A，bash 没有用于这个例子；还给 A 传入 B 和 C，即 a 和 b 和 c。执行 \./S 会怎样？

![图 49：脚本 S 的第一行：\#\!A B C（00:39:57）。](/assets/images/11/0049.webp)

图 49：脚本 S 的第一行：\#\!A B C（00:39:57）。

S 的内容：

```
#!A B C

#!/bin/bash

This can be any script.
```

执行 \./S，就会像指定 /bin/bash 一样，调用我写的 A，任何可执行文件都可以。再给 \./S 传一个 123，会看到它最终调用的是 A\.c 编译出的 A，因为 S 中写了 A。调用时，argv\[0\] 是 A，S 第一行剩余的 B C 整体作为参数传给 argv\[1\]，接着还会传入脚本本身。

![图 50：Linux 将 B C 作为一个参数传入（00:40:44）。](/assets/images/11/0050.webp)

图 50：Linux 将 B C 作为一个参数传入（00:40:44）。

S，也就是这个 s 脚本的路径，会按原样传入。点杠可以写好几个，表示当前路径下的 s，加载器会保留这个写法。比如 a\.sh 1 2 3，最终变成 bash a\.sh 1 2 3。执行 S 时，会 execve A，依次传入 B C、脚本文件，再传入其余参数。这样 bash 或 python 就能知道哪个文件是脚本并执行它。不过 POSIX 没有规定第一行参数的处理方式：B 和 C 之间有空格，应该作为两个分开的参数，还是一个参数？

![图 51：脚本路径按调用时的写法传入参数（00:41:47）。](/assets/images/11/0051.webp)

图 51：脚本路径按调用时的写法传入参数（00:41:47）。

linux 会把后面剩余的内容整体作为一个参数。我昨天专门在 mac 上试过，同样的代码会把 B C 分成两个参数，argv\[0\] 是 A，argv\[1\] 是 B，argv\[2\] 是 C，之后才是其余参数。跨系统的行为并不一致。这算是 unix 留下的一个彩蛋：unix 和 linux 中硬编码的这段小代码，提供了实现脚本的有趣机制。

也能由此知道：即使文件不合法，只要以井号叹号开头，加载器仍会尝试执行它指定的解释器。例如这里的点点，会被当作路径。路径本身合法，却可能不存在；即使存在，也可能无法作为合法可执行文件。执行 \./bad 时，exec 报告 the file specified interpreter，指出这里的点点。

![图 52：解释器写成目录 \.\. 时执行失败（00:43:05）。](/assets/images/11/0052.webp)

图 52：解释器写成目录 \.\. 时执行失败（00:43:05）。

它是目录，目录不能执行。也可以改成 nonexist；执行时同样会报错，说指定内容无法作为可执行文件。解释器没有执行权限等情况，也都会导致错误。

![图 53：解释器 nonexist 不存在时执行失败（00:43:27）。](/assets/images/11/0053.webp)

图 53：解释器 nonexist 不存在时执行失败（00:43:27）。

这就是 Shebang。
