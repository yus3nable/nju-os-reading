mount \-t proc 挂载 procfs，getdents64 等行为由 procfs 代码实现，理论上可以做任何事。tree /proc 看起来是庞大目录树，实际没有预先创建所有这些文件对象，它们是临时构造的。

内核另有自己的数据结构。Linux 用 struct task\_struct 表示每个可调度线程，里面有大量线程信息；自己实现操作系统也会设计类似 struct。

![图 70：procfs 的目录树（01:08:13）。](/assets/images/24/0070.webp)

图 70：procfs 的目录树（01:08:13）。

其中包括 pid\_t、pid 等。每个 cpu 还有 run queue，里面有许多 task。

![图 71：内核中的 task\_struct、CPU 队列与 procfs（01:08:43）。](/assets/images/24/0071.webp)

图 71：内核中的 task\_struct、CPU 队列与 procfs（01:08:43）。

这些都是相互连接的内核数据结构。openat 打开 /proc 时，还没创建全部目录项；真正调用 getdents64，procfs 才遍历 struct task\_struct，边遍历边生成结果。看似完整目录树，实际由代码按需返回。只要 api 返回所需值，就能提供这种文件系统。像 \-/proc/\[pid\]/mem，也没有实体文件，文件系统实现了相应行为。

所以显示什么、隐藏什么，都由它决定。也就可以继续想，怎样给文件增加任意属性。
