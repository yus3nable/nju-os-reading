不上锁可以避免死锁，那给每次共享内存访问都上锁，能否消除所有问题？例如每次 sum 加加都加一把保护 sum 的锁，确实可以消除数据竞争，不再出现这种 weak memory model 行为。但给每个 memory access 上锁，仍没有解决全部并发问题。回想刚才伤人性命的 bug。

编程时太容易假设顺序执行，我们是 sequential creature。大一学编程，函数调用和返回天然带着同步，课上可能都没专门教“函数调用是同步的”，因为函数自带 all or nothing 的原子性预期：交出控制流后，它最终执行完所有事情再返回。

没有 bug 时，我们期望调用总会返回，并带回正确结果。Therac\-25 的模式切换若能瞬间完成机械移动，或者全部操作同步，机械开始移动时禁止执行其他指令，就不会出现刚才的问题。

同步等待会让操作员体验很差；瞬间完成当然没有问题，但实际语义是异步操作，到未来某刻才完成。编程却让人形成了“操作立即生效”的习惯：做 switch mode to x\-ray，就觉得模式已经切过去，忽略了中间的等待。现有并发控制机制又要求后果自负，lock、unlock 没用对，或者条件变量没处理好，都是自己的错。这引出 atomicity violation 和 order violation。前者即使给每次共享内存访问加锁也可能发生。例如想让观察到的 sum\+\+ 结果始终为偶数，却分别执行 lock a、sum\+\+、unlock a，再来一遍。可以在两次操作外再加 lock b、unlock b，大家都这样写就能保证偶数。但某天某个线程外层错用了 lock c，内部仍是 lock a、sum\+\+、unlock a，就可能出问题。所有 sum 仍由同一把锁正确保护，不存在能同时发生、至少一个是写的那对内存访问，也就没有 data race，却仍有 ABA。

我们希望 A 整体 atomic、原子执行，顺序完成，结果被别人的 B 插入打断，程序就错了。另一类 order violation 是条件变量、信号量或其他同步没有做好，造成执行顺序错误，同样常见。这也引出了 Threads cannot be implemented as a library 这个 argument。

现在有 AI，完全可以请它用更安全的方法实现并发，无需直接用底层线程库。操作系统课、计算机专业仍需要了解底层同步技术，大家还得学这些。但实际写代码时，我认为 Threads cannot be implemented as a library 的 argument 是对的：锁能把程序写对，也很容易让自己出错。

我们希望彻底消除这种出错可能，用更高级的语言描述需求，由编译器保证生成的代码满足需求，避免这些并发问题。
