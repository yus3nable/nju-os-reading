以前操作系统课有一个我认为很有代表性的 bug，它与操作系统代码、框架代码联动。data race 的定义很简单，也容易想象它是 bug，但“内存”可以是地址空间中的任意指针：全局变量、堆上新分配的内存，也可以是栈内存。栈上同样可能发生 data race。

共享数据结构上的内存访问，通常会想到加锁，AI 也能帮忙。但访问还可能来自别人写的代码、库函数，让自己的代码与其他代码发生 Race，连一条 return 指令都可能涉及。以前一个 lab 要求实现能在多处理器上正确运行的操作系统内核。

一旦允许将进程，或者理解为线程，从一个 CPU 迁移到另一个 CPU，同学们就怎么也做不对，会遇到神秘重启。AI 应该能找出这个 bug。原因是我的 x86 框架代码在中断返回时借用线程的栈。做过 x86 NEMU 就知道，iret 会从栈上 pop 出 PC 等信息，RISC\-V 的情况不同。

![图 39：线程从 CPU 1 迁移到 CPU 2，返回指令还在使用旧栈（00:51:43）。](/assets/images/17/0039.webp)

图 39：线程从 CPU 1 迁移到 CPU 2，返回指令还在使用旧栈（00:51:43）。

这样才能回到操作系统或其他位置执行。但这条指令完成之前，线程的数据结构已经挪到 CPU2。即便给并发数据结构上了锁，CPU2 上的线程也可能开始执行并使用这个栈，从而形成栈和栈之间的 data race。一部分代码由同学写，一部分来自我的框架，这会让大家吃很多苦。

我一般会在课上讲这个例子。它很难解决，需要同步：等 iret 执行完，T1 才能在另一个 CPU 上启动。但这做不到，因为 iret 之前不能持有任何锁，也无法同时完成这条指令再 release 一把锁。一旦把线程数据结构放到另一个 CPU，线程就可以直接运行。

![图 40：栈和栈的访问也需要正确的同步（00:52:50）。](/assets/images/17/0040.webp)

图 40：栈和栈的访问也需要正确的同步（00:52:50）。

解决这个 bug 时，会发明一种同步方法：Read\-Copy\-Update。一个正确办法是，等当前 CPU 完成一次完整线程调度后，才允许 T1 在另一个 CPU 上被调度。Linux 内核现在到处都有这种机制；它大概花了十年，把很多锁迁移到这种读操作几乎可以无锁的 Read\-Copy\-Update 机制。

这个故事说明了复杂性。死锁四个必要条件、data race 等定义虽然简单，实际问题不能想得太简单。
