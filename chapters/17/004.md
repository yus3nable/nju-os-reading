现在可以让 AI 直接写程序。我也让它写了一个 AA deadlock 演示：acquire 后再 acquire。这对 AI 是很简单的任务。我 spawn 一个 T\_lock，也可以直接在 main 中做：先 acquire，打印一条消息，再 acquire 同一把锁，再打印一条消息。如果没有死锁，线程和整个 main 函数就会结束。编译运行后，程序卡住了。死锁的 symptom 比较容易观察：预期只做一点事情，例如生产者消费者打印 100 个括号，应该在能感知的时间内很快结束。这个线程原本可能 0\.1 毫秒就结束，现在却一直没有结束，第二条 message 也没有打印，说明可能出了问题。

![图 6：aa\-deadlock\.c：第二次获得同一把锁（00:06:00）。](/assets/images/17/0006.webp)

图 6：aa\-deadlock\.c：第二次获得同一把锁（00:06:00）。

T\_lock 中的两次加锁：

```
mutex_lock(&lock);
printf("Thread %ld acquired lock\n", (long)arg);

// 同一个线程再次获取同一把锁 → 死锁
mutex_lock(&lock);
```

![图 7：程序只打印第一次 acquired lock，然后停止推进（00:06:20）。](/assets/images/17/0007.webp)

图 7：程序只打印第一次 acquired lock，然后停止推进（00:06:20）。

如果采用刚才设想的线程本地计数器，应该能看到两次 printf，现在没有，说明确实发生了死锁。我经常观察 AI 写代码的过程，同学们也可以这样做。我可以给 Claude Code grant 读写权限，让它不再提示，也可以用 dangerously skip all permissions，跳过所有提示；这样它删库也就删了。最近这两天好像又有人被 Claude Code 删库，导致生产环境下线，最后回滚到备份。

做操作系统实验时，完全可以让 Claude Code 帮忙搞定。它可以 fetch URL，去网上读实验手册，也可以 browser use，最后自行提交。提交后还可以到 Online Judge 查看是否通过，没通过就继续 fix。但这样会失去学习中重要的观察和思考：换成自己，会这样做吗？

自己能否做得比 AI 好？我也经常看见 AI 犯蠢，有时很想按 Ctrl\+C 打断它，再骂它；它就会说“You're absolutely right”。也可以不打断，观察它怎样一步步解决问题。今天的 AI 明显会犯错，但也能把错误修好，我觉得这是很厉害的能力。

这个过程中，AI 会不断输出信息，包括思考的中间过程。还可以在 CLAUDE\.md 中加一个 prompt，让它以老师的身份多解释思考过程，再继续做。这样可以学到库函数的使用、写代码的 best practice，也能看到各种命令行工具。有些工具可能从没用过，先留个印象，知道做这件事时可能用得上。

AA 型死锁看起来很傻：lock A 后再 lock A，似乎可以打赌自己绝不会这样做。但真实系统可能有几十个文件、多层函数调用、递归，以及 callback、信号、中断等隐藏控制流，远比只有一个线程、十行代码的 oversimplified case 复杂。例如，处理代码时已经 acquire 一个 lock。

这时按下 Ctrl\+C，信号处理代码认为需要保护某个并发数据结构，又 acquire 同一把 lock，就形成了 AA 型死锁。一旦程序并发、异步，控制流就很难完全想清楚。互斥机制可以阻止并发发生，也有代价，包括这样的死锁。可以回去问 AI，现实中有哪些 AA 型死锁，它会给出很多例子，其中有些确实在生产环境中造成过问题。
