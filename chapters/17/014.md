永远不上锁，能否彻底避免死锁？四个必要条件的第一条要求钥匙只能由一个人拿到，拿到才能继续；没有钥匙也能继续，就取消了锁。但这会面临另一个更麻烦的问题：data race，数据竞争。

图 33：数据竞争的定义、赛跑结果与语言行为（00:42:47）。

现在正式引入概念，前面已经遇到过很多例子。支付宝先判断余额足够再扣款，其他线程同时改余额，再读就可能读到它写入的值；两个线程做 sum 加加也是 data race。Peterson 协议中往门上贴字、举手、观察对方，同样涉及 data race。定义是：不同线程同时访问同一内存，至少有一个是写。为什么要求至少一个写？假设 T1、T2 都读 X，过去发生的事都是正确的，就能保证两者读到相同的值。

![图 34：两个线程读取同一个 X（00:43:50）。](/assets/images/17/0034.webp)

图 34：两个线程读取同一个 X（00:43:50）。

一旦至少有一个线程写，它们就开始赛跑，快慢造成 non\-deterministic，也就是非确定性结果。读得快、写得慢，就读不到新写入的值。例如原来 X 等于 0，另一个线程写 X 等于 1，先读就得到 0；写稍快一点，WX 等于 1 先发生，读到的值就变了。并发程序中的 X 可能是这个值，也可能是那个值。一旦有两种可能，理解程序的复杂度就会指数增长，还会遇到 weak memory model 的行为。

![图 35：一个线程写入后，读取的先后改变结果（00:44:58）。](/assets/images/17/0035.webp)

图 35：一个线程写入后，读取的先后改变结果（00:44:58）。

例如一个线程写 X 等于 1、Y 等于 1，另一个读 Y、读 X，明明至少写过一个，仍可能读到旧值。写写 Race 也一样：一个线程写 X 等于 1，另一个写 X 等于 2，先写的值被后写的覆盖，运行快慢影响最终结果。在没有保护、也没有明确理解后果时，这非常危险。C、C\+\+ 将这样的 data race 定为 Undefined Behavior，后果可以很严重，理论上把电脑炸了都可以。C 直接编译成指令，由进程执行；一旦内存 corrupt，PC 可能跳到攻击者写入地址空间的一段代码，任意代码都可能执行。

![图 36：写写竞争：后写入的值覆盖先写入的值（00:46:05）。](/assets/images/17/0036.webp)

图 36：写写竞争：后写入的值覆盖先写入的值（00:46:05）。

假设机器还接着核弹发射器，就可能发射核弹，对物理世界造成不可逆伤害。这就是 Undefined Behavior 的危险，使用它就是自己的错误。C、C\+\+ 为兼容各种体系结构、系统实现和编译优化，干脆将 data race 定为 Undefined Behavior，要求使用者小心。Java 则尝试定义 Race 可能造成的行为，给出最低保证：例如没人写过 42，就希望读取时不会凭空得到 42，避免那种糟糕的安全漏洞。data race 是忘记上锁时常见的一类 bug。
