ASPLOS 2008 的工作，离现在约 20 年，2018 年得到了 most influential paper award，为研究并发开了一个好先例。它做 empirical study，即实证研究，查看 MySQL、Apache 等当时顶尖程序员维护的项目；LibreOffice、OpenOffice 可能不算这一类。

例如 Mozilla Firefox，Rust 就出自他们团队，有顶尖程序员，却仍能在这些真实系统中找到 105 个并发 bug。研究者从中 Learning from mistakes，寻找有意义的结论：现实程序员仍会写出 ABA 之类的问题。图中 atomicity violation 的例子大概是 data race，是常见模式。

它与支付宝例子一样：先用 if 检查条件，满足后就执行。余额大于要扣的钱，就扣款；指针非空，就向其中写入数据。结果即使上了锁，若另一个人释放了资源，仍会 crash。ABA 问题很多，还可能导致 use\-after\-free。

例如将指针交给另一个线程后，那个线程或整个系统以为不会再访问，便安全地 free 了它；后来再次读取这块内存，就变成 use\-after\-free。

检查与使用 proc\_info 的片段，其余语句省略：

```
if (thd->proc_info)
{
  fputs(thd->proc_info, ...);
}
```

这很危险，可能读到不属于自己的数据，泄露隐私。内核有很多这种严重的 use\-after\-free 漏洞。如果 free 时顺手把指针清成 NULL，程序也可能 crash。问题既会出现在自己的程序中，也会出现在系统里。

支付宝的例子也叫 TOCTTOU，time of check to time of use，检查与使用之间存在时间差。if condition 之后，原本期望可以 assert condition；没有正确互斥、上好锁，assert 就可能不满足。条件变量是经典且好用的同步机制。

用 while not condition 循环时，它可以保证退出等待后的 condition 为真。但有时系统里连这种保证也很难做到。
