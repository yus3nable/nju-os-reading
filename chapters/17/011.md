现在很火的 Harness Engineering，译作“驾驭工程”，是一种软件工程。我故意反过来说：软件工程就是 Harness Engineering。大型软件系统设计有一个基本原则：做最坏的假设，做最防御性的编程。先假设程序是错的，未测代码永远是错的；除非竭尽所能仍无法证明它有错，才相信它 somehow 是对的。写完程序，只过样例或只编译通过就交 OJ，在大型系统中是个坏习惯。我觉得 AI 时代从第一门编程课起，应该已经在扭转这种习惯。要驾驭程序员、驾驭复杂性，在锁的使用上可以先假设：程序员写了 lock，很可能在某些罕见路径忘记 unlock。

为此，需要规定程序的写法。Linux kernel 有一个很好的 pattern：goto release。对 C 代码而言，它可能损失一点性能，但所有申请的资源都在 release 处统一检查，包括运行时 allocate 的 buffer。

程序还会 acquire lock。每次申请的资源都要在 release 中检查，尚未释放的就释放。return 很危险：它只让栈帧消失，资源可能仍然存在，锁还占着，buffer 也没回收。buffer 不回收就是 leak，会浪费资源。

写 OJ 时任由它 leak，也是坏习惯。看到 return，就要检查 cleanup 是否全部完成。用 goto release 统一释放资源后再安全返回。在 C 缺少其他保证机制时，这种写法能明确表达释放所有资源的要求。当然，它仍有局限。

例如 release 中仍可能漏掉一个申请过的 buffer。C\+\+、Rust 有 RAII，Resource Allocation Is Initialization：创建一个对象，让它在 scope 中管理资源。无需限制在函数级别，代码块中也可以定义局部变量，让变量不要 leak 到作用域外，是很好的 practice。

例如在 C\+\+ 中创建 lock object，编译器保证进入代码块时调用构造函数，离开时调用析构函数，无论通过 return 还是其他方式离开。可以在构造时获得锁、析构时 release，确保锁在该作用域内生效，防止上锁后忘记释放。

Linux kernel 还要求有明确的 lock ordering，必须按指定顺序上锁，否则会出现各种问题。
