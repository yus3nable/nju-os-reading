Wikipedia 对必要条件的陈述明显更客观、公正，也更符合 computer science 从业者的表达。让脚本过滤这些 spam，返回中文词汇以后，我们继续逐条分析四个条件。mutual exclusion 就是互斥：钥匙只能由一个人拿到，拿到才能继续，这是互斥锁的定义。百度百科却说，在系统设计、进程调度方面，要注意如何不让这四个必要条件满足。

这句话没错，但缺少客观的讨论。就像我那天在知乎发帖，说 AI 有中文名“人工智能”，大家可以不叫 AI，可“人工智能”又太长，于是我找了一个字。我觉得这个字能表达当前人工智能的四大含义，又短又上口，就应该当作中文翻译。这里不说是什么字了，但光这样说不 work，需要一个 reasoning model。

需要仔细考虑，为什么这四个条件很难打破。打破“钥匙只能被一个人拿到，拿到才能继续”，就改变了锁的定义，需要彻底重构代码设计，不能再使用互斥锁。例如在 Dining Philosophers 中引入 waiter 线程，再提供 send、receive API 与它通信。实现 send、receive 时仍需要锁，但有了通信机制，使用者只需与 waiter 通信。分布式系统的 master worker 结构也采用这种设计，通过集中管理解决锁的问题。第二个条件是拿到钥匙的人还想要更多钥匙，可以用一把大锁，再消灭 AA 型死锁。

这样就不会有其他死锁，但性能低，可能也不符合需求。有没有兼顾性能的方法？早就有人想在 C、C\+\+ 或其他语言中引入 atomic 关键字，类似 database transaction。不熟悉事务也没关系：atomic 块中可以写任意代码，比如 sum\+\+；理想情况下还希望能写系统调用。但系统调用像泼出去的水，很难收回。

atomic 的意思是，这些代码看起来要么像 stop the world 一样全部执行完，要么一次也没有执行。例如一个 atomic 块里有两个 sum\+\+，另一个线程也一样，那么只能看到 24680，永远看不到奇数。这就是 all or nothing 语义，例如支付宝的操作可以先在里面 check。

先检查全局状态再 modify，就能保证 all or nothing 的结果。但 transaction memory 很难实现，涉及系统调用时更难。这仍是人类追求的目标，我觉得 AI 时代也许又会兴起。第三个条件是不能抢别人的钥匙。抢锁会带来混乱：假设用一把大锁，另一个线程持锁并执行两个 sum 加加，我想抢锁，就要处理它已经造成的 side effect。可以等它做完，但这样就谈不上抢；若强行将它赶出房间，就必须回滚这些副作用。这又指向 transaction memory：能够回滚持锁线程执行过的操作，才有办法打破不可抢占。

System deadlocks 的价值在于，仔细思考每个条件都能引出新的研究分支，可能让编程变得更好。百度百科那句空话没有表达这些讨论。为了实现其中的想法，需要投入很多精力，可能上千篇 paper 都与 transaction memory 有关。我觉得这是推动人类进步的好 idea。
