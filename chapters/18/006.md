继续讲并发，回到 sum\+\+。它是并发编程里常见的 pattern，虽然例子过度简化：创建 T\_sum，在里面获得互斥锁，持锁执行 sum\+\+。无论多少线程，如果一共加了 1 万次，最终 sum 一定等于 1 万，互斥可以保证正确性。

实际程序中，锁保护的常是数据结构操作，比如往 buff 中写东西。两个线程 printf 时，共享进程中的一个 buffer，它也有锁。

课件中的 T\_sum，依赖课程线程库中的互斥锁接口：

```
void T_sum() {
  mutex_lock(&lk);
  sum++;
  mutex_unlock(&lk);
}
```

加锁后才能向 buffer 写入。两个线程可并发执行，但这把锁会阻止它们并行写 buffer，让 stdout 的数据不被打乱。另一个常见 pattern 是 key value dictionary：加锁保护更新操作，数据结构就安全。

前几次课对比过多种 sum\+\+ 实现。直接用汇编实现原子 sum\+\+ 最快，连获取和释放锁的过程都没有。还有 pthread 锁，以及手写 spinlock，不断尝试从桌上拿钥匙。

线程越多，性能越差。到了 4、8、16 个线程，mutex、atomic 性能基本不变，至少不再下降，但仍不理想。理论上，设计好的算法，一颗 CPU 花一秒，两颗应花 0\.5 秒，四颗花 0\.25 秒。每颗 CPU 都能独立执行指令、响应中断，好的实现应将计算力 100% 用起来。这里却是一颗 CPU 最快，两颗变慢、四颗更慢，八颗、十六颗开始饱和。我们希望 CPU 越多，每秒完成的操作越多；Mutex Lock 最好也只是达到上限，继续增加 CPU 不再损失性能。

Mutex Lock 将操作串行化，阻止并行，没有达到需求。
