后面还会讲并行数据结构、malloc。要实现 scale up、scale out，应该怎么做？

![图 20：将计算任务的本地运算与同步分开（00:20:43）。](/assets/images/18/0020.webp)

图 20：将计算任务的本地运算与同步分开（00:20:43）。

课件上的任务执行片段，job 的定义与调度器省略：

```
mutex_lock(&lk);
job = get();
mutex_unlock(&lk);

job->run();   // mostly thread-local computation
job->done();  // enable other jobs
```

任何并行计算问题都对应计算图。例如矩阵上的动态规划，每个节点是一项计算，每条边表示依赖。dp\[i\]\[j\] 是 dp\[i\-1\]\[j\]、dp\[i\-1\]\[j\-1\]、dp\[i\]\[j\-1\] 这几个数值的函数，构成依赖图。如果每个节点计算量很大，且不涉及共享变量、无需上锁，就有机会提高性能。

这样可以让加解锁之间串行化的区域很小，系统便能 scale up，也能 scale out。但若每个 dp\[i\]\[j\] 都作为一个节点，计算图设计就很差，因为还需要加锁确保可以运行。

![图 21：动态规划中每个节点与前驱的依赖（00:21:49）。](/assets/images/18/0021.webp)

图 21：动态规划中每个节点与前驱的依赖（00:21:49）。

可以用条件变量 wait，也可以用信号量：有三个 predecessors，就 P 三次，前驱各 V 一次，V 三次以后才能执行。这些同步、互斥都有代价，付出后却只做 dp\[i\]\[j\] 等于 dp\[i\-1\]\[j\]\+1 之类的一两三步算术运算，接着又花很多代价同步。即使后来并行度足够高，也未必是好算法。解决 LCS 时，可以调整计算图：开始的小三角形合为一个节点，串行计算几百个元素，本来就很快，无需过多同步；并行度上来后，沿对角线切，例如切成二和三两份，再往后也切成二和三。

再多一些时可以切成三份，一二三。只要算完一层就能算下一层，无需完全照原问题的逐元素写法，或 max 加一的表达来划分。可以分块，块之间保持依赖关系，就符合 scale up、乃至 scale out 的模式。

同步上锁时间很少，绝大部分时间用于各自本地运算。
