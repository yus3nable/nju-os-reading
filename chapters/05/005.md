为什么要有 fork？

![图 85：fork bomb 的指数增长（00:50:30）。](/assets/images/05/0085.webp)

图 85：fork bomb 的指数增长（00:50:30）。

先介绍 fork bomb，帮助记住 fork。它像核弹链式反应，中子撞击更多 U 原子核，数量指数增长。写 while (1) fork()，执行一次就从一个进程变成两个，p1、p2 都停在 fork 后面，接着又回到循环，再执行 fork。

p1、p2 各变两个，再从两个到四个、四个到八个，指数增长，很快耗尽资源。比如 CrazyOS 用静态数组保存进程，最多容纳 128 或 256 个，耗尽后就不能再创建，系统会卡住。

![图 86：反复 fork 带来的指数增长（00:51:31）。](/assets/images/05/0086.webp)

图 86：反复 fork 带来的指数增长（00:51:31）。

今天 Linux Kernel 有 out of memory 处理，资源、内存不足时会杀一些进程，也能发现有问题的进程组，结束 fork bomb。这里不演示，机器可能完全卡死。shell 版的写法看起来像倒着的人，左边是头、张着嘴。因为 shell 允许用冒号这类字符作函数名。

换成具名函数，就容易看懂。里面用 unix 管道，分号相当于换行。

![图 87：将 Shell 中的 fork bomb 写成具名函数（00:52:40）。](/assets/images/05/0087.webp)

图 87：将 Shell 中的 fork bomb 写成具名函数（00:52:40）。

```
fork_bomb() {
    fork_bomb | fork_bomb &
}; fork_bomb
```

fork bomb 启动两份自己，用管道相连，再放到后台。管道连接本身不重要，这样就引爆了 fork bomb，老式 unix 一行代码就可能卡死。fork 也能受控使用，通过返回值区分父子进程。课前的问题是：为什么设计 fork，spawn 又有什么不同？

## 全量状态快照：预处理、并行搜索与恢复

![图 88：全量状态快照：预处理、并行搜索与恢复（00:53:19）。](/assets/images/05/0088.webp)

图 88：全量状态快照：预处理、并行搜索与恢复（00:53:19）。

spawn 更直观，比如指定 hello\.exe，创建从初始状态开始的子进程。fork 则支持其他用法。为了用好多处理器，可以把大计算分成 16 份，交给 P1、P2、P3 等独立进程，最后输出结果。spawn 能完成，但若每个任务都有公共预处理，例如先计算 10 的 9 次方或 10 的 12 次方范围内的素数表呢？

后续计算不同，但 16 个或更多进程都用同一素数表，该怎样做？

![图 89：多个任务共有的初始化部分（00:54:31）。](/assets/images/05/0089.webp)

图 89：多个任务共有的初始化部分（00:54:31）。

先用一个进程算表，再 fork。完整复制状态后，父子进程各领不同任务，都能访问准备好的素数表。今天 Linux 的 fork 高效，不会像 CrazyOS 逐字节复制。如果只读、不再修改，创建 1000 或 1 万个子进程，大素数表也只有一份副本。

安卓启动应用，就用了 zygote process。我这台不是安卓，不过还有一台。Android 生态用 Java 建立，一个能在苹果竞争下立足的原因，是当时有大量 Java 程序员，容易转做安卓。Java 的问题是，main 开始前可能要加载成百上千个类，逐个初始化、verify bytecode，流程很长。第一台安卓手机只有几百兆赫兹主频，我不确定那时是否已有 Zygote，可能就有。

![图 90：预处理后 fork 共享已经准备好的状态（00:56:00）。](/assets/images/05/0090.webp)

图 90：预处理后 fork 共享已经准备好的状态（00:56:00）。

如此长的初始化会让 APP 启动很卡。Android 把公共库加载、部分应用初始化，放到 zygote process，先准备共享状态。点击原神启动，在 Linux 意义上会 fork；原来的 zygote 返回，仍保持不变。zygote 是受精卵，像最初的母细胞、干细胞，可以不断分裂成其他细胞，之后分化为心脏、骨骼，像不同应用成为原神、计算器。zygote 本身保持原样，fork 后的副本再变成应用，解决冷启动慢。这是 Unix 遗产在离今天较近时的应用。还有 fork\-based DFS，可以用 DFS 搜索。

我们组就有。问题求解课遇到跑不完的搜索，想跑得快些，可以让 AI 实现 fork\-based DFS。fork 是完整程序状态的快照，复制一份探索一个方向。还能做故障恢复：比如 HTTP 服务器有 bug，每隔几秒做快照，让快照像 Zygote 一样停着，实际进程提供服务。一旦它 crash，再让快照接替，即使某个请求触发 bug，整个服务也没有崩溃。全量内存、完整程序状态快照，提供了这些 hack 的空间。
